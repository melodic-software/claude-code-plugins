# Steps that carry `continue-on-error: true` for a reason OTHER than feeding the
# aggregator, each paired with that reason. Read by
# scripts/check-lane-coverage.sh, which otherwise requires every such step to be
# read back as `steps.<id>.outcome` by a feed row in its own job — because
# `continue-on-error` absorbs the failure, so a gate step nothing reads turns
# nothing red.
#
# Format: one `<job-id>/<step-id>  <reason>` per line, matched against
# .github/workflows/pr-require-checks.yml. The reason is the rest of the line, and an entry with
# nothing after it FAILS, the same way a bare `# lane-coverage-ok:` annotation on
# a job does. Whole-line `#` comments and blanks are ignored; the file is parsed
# by scripts/lib/read-list.sh in `leading` mode, like every other list here.
#
# Checked in BOTH directions: an entry naming a step that does not carry
# `continue-on-error: true`, or one the feed reads anyway, fails as stale. The
# list cannot rot into a silent allowlist.
#
# ADDING A NEW GATE? Do not reach for this list. A gate step missing from the
# aggregator feed should FAIL here; that failure is the tool working. This list
# is only for a step whose `continue-on-error` exists to let a FAILURE FALL
# THROUGH to a fail-open default, which is the opposite of a gate.

select-tests/detect  the resolver's own step: a failed detector must leave its outputs unset so every consumer resolves toward RUNNING its lane, and feeding that outcome to an aggregator would red the run for the one case it exists to survive
select-tests/match  the resolver's own filter-group step, on the same fall-through contract as select-tests/detect; the pair is gated instead by the non-continue-on-error detector self-test above them and by scripts/check-docs-only-gate.sh
select-tests/mq_scope  the merge-group scope dark launch only logs what a narrower run would skip: nothing reads its outcome, so a failure must change no lane, and scripts/merge-group-scope.test.sh holds that no output or condition reads it
ci-status/base_config  the hold steps' sparse checkout of the base config: a failure must fall through to those steps, which read steps.base_config.outcome through BASE_CONFIG and fail closed (human-gated, hold-lift, merge-group) or keep the hold (cost-hold) on it, so feeding it to the aggregator would add no gate the steps do not already enforce
ci-status/queued_author  the merge queue's author read that lets the two verdict-read steps below skip a pull request whose author pr-verify does not judge: a failure leaves its outputs unset, so those steps run as they did without it, and the lanes-hold step still tests the author itself
ci-status/verdict_reads_restore  the merge queue's read of pr-merge's carried verdict reads (its run-cache artifact): a miss or a failure must fall through to the lanes-hold step, which judges a cold reader itself (it reads only with GITHUB_TOKEN headroom, and holds otherwise), so feeding it to the aggregator would add no gate the hold step does not already enforce
ci-status/verdict_reads_carry  the run cache the merge queue starts from those reads, on the same fall-through contract as ci-status/verdict_reads_restore: a failure leaves no run cache, which the lanes-hold step reads cold only with headroom and holds otherwise
select-tests/standards  the resolver's one resolve of the run's standards commit (download-standards, checkout false): a failure leaves standards_sha empty, and each later job's standards checkout then reads standards main, so feeding it to the aggregator would red the run for a fallback that still reads standards
lint-repo/standards  the lint job's standards checkout: a failure leaves STANDARDS_DIR empty, so run-zizmor.sh and check-changed-links-online.sh read standards' config from standards_repository main through the API (run-zizmor.sh only when the base commit has no config of its own) and the gitleaks, lychee and editorconfig composites take the run's standards commit, else main, as standards-ref, and the runner-policy install fails without the checkout; each of those steps is fed and fails on its own
ci-status/standards  the hold steps' standards checkout: a failure leaves STANDARDS_DIR empty, so trusted_list fails and those steps fail closed or keep the hold, so feeding it to the aggregator would add no gate the steps do not already enforce
