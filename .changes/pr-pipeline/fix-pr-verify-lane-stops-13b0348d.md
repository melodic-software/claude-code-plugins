### Changed

- pr-verify reads text the lanes App wrote before the pull request existed as spec: an issue body it filed (a lower number than the pull request) or last edited before the pull request was created, and intake triage's refinement comment (opening with refine.mjs's marker) last updated before then. Before, any App-written body was a null spec, so a lane pull request for an App-filed issue failed at every head. Text the App wrote after the pull request, any other Bot's or App's text, `github-actions` included, and unlisted accounts' text stay out. `resolve-pr.mjs` `specTrust` and the merge gate's `_trusted_spec` and `_spec_comments` hold the same rule, and a test runs both.
- A trusted spec edit after a pass no longer strands the head at `verify:spec-changed`. `resolve-pr.mjs` judges a head again, with reason `spec-changed`, when every counted pass there started before the spec's last change (an issue body edit, a spec comment added or edited, or a body edit of a pull request that is its own spec), and the lost-run reconciler re-runs, once and with a record, the passed `pr-require-checks` run of such a head so pr-verify starts. The gate decides on the passes of the newest run at the head, so the new verdict replaces the stale one. A changed closing set or a removed spec comment still waits for a person.
- The verifier prompt no longer fails a pull request for touching workflows, CI, hooks, scripts, agent instructions, package manifests, lockfiles, path or file-type refusals or a `merge: human` setting; those are judged as ordinary code. It fails a change to the takeover set (the trusted-actor list, the `check-trusted-trigger`, `check-kill-switch`, `request-lane-token` and `resolve-config` actions, `CODEOWNERS`, submodules) whatever the spec says, and fails unrequested work only when it loosens a hold the owner keeps, rather than whenever it touches one.
