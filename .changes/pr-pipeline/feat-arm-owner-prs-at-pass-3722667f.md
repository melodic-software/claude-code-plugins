### Added

- pr-merge's `enable-auto-merge` arms a trusted person's pull request (a `User` whose id is kind `human` on the trusted-actor list) at the head pr-verify passed, with the lanes App token and `expectedHeadOid` that head, when it is not a draft, armed, queued or a stack layer, carries no hold label (`do-not-merge`, `pr-verify-failed`, `security: outside-actor`, `needs-human` or the human-gated label), has no `Hold:` or "do not merge" body line, changes no lane source pr-review-main reviews, and the verdict reader counts a PASS or PASS-NOTES at the head. It skips every lane-source pull request until a reader decides whether pr-review-main's findings at a head are settled. A trusted bot's pull request keeps its own path. It posts the lanes App's pin at the head before arming; the next scheduled run disarms one whose newest pin names another head or was edited, then posts the lanes App's `babysit-merge-unpin` record, which `pinMoved`, `pinned` and `pinHold` read as no pin, so a person's later arm at a head the sweep refuses is not held for the stale pin.
- The pr-verify wake and the eval-release wake serve the lanes App's pull requests and a trusted person's, the two the token broker mints the wake for; the scheduled sweep is the fallback for any other. The pr-verify wake downloads the trusted-actor list only for a `User`'s pull request.
- `ci-status` in the merge queue holds every pull request that is not the lanes App's, whatever `merge.verify-authors` says, when its newest lanes App pin names another head, was edited, or its edit time does not read (`merge-holds.mjs` `pinHold`), so a trusted person's pull request armed at a passing head and pushed again does not merge the unjudged head; a trusted approval of the live head, or the lanes App's unpin, lifts it.
