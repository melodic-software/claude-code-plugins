### Added

- `docpage-digest-batch` workflow ([#7369](https://github.com/melodic-software/claude-code-plugins/issues/7369)): digests several documentation pages with every Phase 3 digest agent and both Phase 4 verifier arms dispatched by the workflow script, so no agent has to spawn another and no page skips verification. `/knowledge:docpage-digest` documents it as its Batch path and `/knowledge:map-corpus` launches it for a multi-page queue. Its stages run as the new `knowledge:digest-worker` agent.
- The workflow rejects a page URL that is not https on a public host, or that carries a quote, `$`, a backtick, whitespace or another shell metacharacter, before any agent sees it; it returns rejected and deferred pages with a reason code each and a `verification` of `unverified: not run: <code>`, which map-corpus records. The single-page path runs the same checks on the canonical URL before any shell command carries it. Verifier B runs as a same-vendor refuter, recorded degraded in its header, because `codex:codex-rescue` returns raw stdout that cannot carry a structured verdict.
- Every agent reply passes one strict parser per stage (own properties, exact types and enums, single-line capped strings) before the script reads it. Agents supply no path, skip flag, gate name or reason text: the script derives each page's slug from the launched URL by the single-page slug guard, refuses a setup that reports another slug or a redirect (the single-page path takes that page), builds every path from that slug, holds the standing-gate set, and builds each page's `verification` from its own reason codes in one decider, which sets `verified` only when this run's verifier A and B verdicts both pass and no attempt of either returned `FAIL`. The batch path has no resume and no correction rounds; a page whose verifiers fail ends `failed: verifier-fail` and is rerun on the single-page path.
- The checklist gains a `Verification status` line (`verified`, `unverified: <reason>`, `failed: <reason>`), copied into the interview handoff's first line and each map-corpus `queue.json` entry. A page heading for `verified` carries `unverified: awaiting-launcher` on disk until the launching session writes the final status from the workflow result, so disk never says `verified` ahead of the decision.
