# Work-item tracker seam — first-principles scrutiny report (agent B)

Posture: existing state treated as one candidate design, not the presumption. Facts, options, trade-offs only — no recommendations. Produced 2026-08-17 for the pocock-shipping-breakdown interview.

## 0. Ground facts (inventory)

- **Binding**: single tracked file `.work-item-tracker.json` at repo root; one provider; discovery = climb from CWD to filesystem root, first match wins; env override `WORK_ITEM_TRACKER_BINDING` (CONTRACT.md:20-45; `lib/binding.sh:11-28`). `config.lease_ttl_hours` is REQUIRED — a binding without it is invalid (CONTRACT.md:42-45; binding.sh:61).
- **Adapters**: three bundled (`github`, `jira`, `local-markdown`); resolution is consumer-local-first (`${CLAUDE_PROJECT_DIR}/tools/work-item-tracker/adapters/<provider>/`), plugin-bundled fallback; `WIT_ADAPTERS_DIR` override (CONTRACT.md:112-131; `work-item-tracker.sh:31-45`).
- **Conformance machinery**: an abstract suite (`conformance/run-conformance.sh`, 262 lines) parameterized by `bindings/<name>.sh`, exercising every verb, exit codes, JSON shape, ID grammar, claim-race back-off, lease lifecycle, capability-gated exit-6 skips, CR-free stdout (run-conformance.sh:65-259). Plus per-verb `*.test.sh` beside every adapter script, `tests/lib.sh`, `e2e-probe.sh`, and unit tests for `binding`/`lease`/`frontier`/`json`/`id` libs.
- **Cross-plugin consumers of the binding path**: 37 files reference `.work-item-tracker.json`, including the `autonomy` plugin's `resolve-prerequisites.mjs:205` (hardcodes `join(repoRoot, ".work-item-tracker.json")`) and `prompts/loops/loop-lane-prompts.md:73-101` — the location is not encapsulated behind the seam; several surfaces `jq` the file directly (e.g. role resolution mandated at every action entry, `reference/tracker-seam.md:129-139`).
- **Config-cascade convention** already tracks this surface as a deviation row: "`work-items` | `.work-item-tracker.json` | team only | single-layer; resolves by CWD-to-root climb rather than anchoring at the repo root" (docs/conventions/config-cascade/README.md:218).

## 1. Binding file — location, layering, format

### Findings

**F1.1 — The climb can escape the repo.** `wit_find_binding` climbs from CWD to the *filesystem root*, not to the git toplevel (binding.sh:17-27). A stray `~/.work-item-tracker.json` (or one in any ancestor directory) silently binds every repo underneath it that lacks its own binding. The config-cascade convention's own resolution algorithm forbids exactly this ("Anchors at the repo root … Never a CWD-relative path", config-cascade/README.md:127-130), and the convention's implementers table already flags the deviation (line 218). Contrast: `setup` itself anchors at `${CLAUDE_PROJECT_DIR:-git rev-parse --show-toplevel}` (setup/SKILL.md:38-39), so the writer and the reader disagree about the search space.

**F1.2 — Wholesale-replacement env override.** `WORK_ITEM_TRACKER_BINDING` replaces the whole file (binding.sh:12-15) — the cascade contract calls whole-file replacement "forbidden" for file layers but tolerates it as an explicit per-invocation flag (the `disk-hygiene --policy` precedent, config-cascade/README.md:186-188). The override is documented as tests/conformance-only (CONTRACT.md:33-34), which matches that precedent.

**F1.3 — One tracked `auth_email` for the whole team (jira).** The tracked binding carries `auth_email` (CONTRACT.md:376-394; example `"ci@company.com"`). Jira Basic auth is *per-account* email+token. With a single-layer tracked binding, either the team shares one service account, or each user must locally edit a tracked file. The token itself is safe (env-var-name indirection, `auth_env`, CONTRACT.md:362-367), but the identity half of the credential pair is team-frozen. This is the concrete secrets-adjacent case a gitignored `.local` overlay (or user-global layer) would change.

**F1.4 — Per-user PROVIDER override is structurally unsafe for coordination; per-user *some keys* is coherent.** Claims are provider-side state: assignee + lease comment on the provider's item (CONTRACT.md:216-263); the frontier filter derives from provider-side assignees/labels (frontier.sh:29-47). If user A binds Linear while the team binds GitHub, A's claims/leases land in Linear and are invisible to every GitHub-bound frontier — the race-safety the seam exists for evaporates. So the cascade model's "user-global layer" cannot safely carry `provider` for a *shared* repo. But it degrades gracefully for keys that travel *inside* the lease record: `ttl_hours`/`ttl_minutes` are stamped into the lease JSON at claim (CONTRACT.md:221, 227-229), so readers honor the writer's TTL regardless of the reader's config — a per-user TTL is coherent today. `role_labels` must stay team-shared (every session queries the same provider labels; a per-user remap would fracture the frontier filter — setup/SKILL.md:462-464 shows the sensitivity). The solo-dev-wants-Linear case only works when the *whole repo's* coordination lives in one place per person — i.e. it's a per-repo fork of the binding, not a per-user overlay of it.

**F1.5 — `.claude/` write-guard tension is documented and cuts both ways.** The standards convention deliberately locates its team layer *outside* `.claude/` "because writes under `.claude/` are permission-guarded" (standards/README.md:41-43), and the cascade doc records that location choice as "observed, not ratified" (config-cascade/README.md:177-181). Meanwhile the topic-docs convention *does* put its team concern file at `.claude/topic-docs.yaml`, written by interactive setup rungs (topic-docs/README.md:315-374), and 9+ surfaces in the implementers table live under `.claude/` (config-cascade/README.md:205-221). The write cost is once-per-repo (setup `apply`); reads under the working directory are prompt-free either way. So the guard argues against `.claude/` only to the degree the repo cares about a prompt during a one-time interactive bind — and *for* `.claude/` if unattended `apply` (setup/SKILL.md:259-285 explicitly supports autonomous first-time bind) must never hit a permission prompt: an unattended `gh`-ready bind currently writes the root file promptlessly; under `.claude/` it could stall.

**F1.6 — Format precedent is split; the parser is not.** Team-config precedent in the fleet: YAML for `.claude/topic-docs.yaml` and `.claude/standards.yaml` and `ecosystems/<eco>.yaml`; JSON for `autonomy/binding.json`, `disk-hygiene.json`, and this binding. The seam is bash+`jq`; `jq` is already a hard prerequisite (CONTRACT.md:10). YAML would add a `yq`-class dependency or a fragile hand parser to `binding.sh`, `setup`'s probes (SKILL.md:139-147), *and* the autonomy plugin's Node reader. JSON's cost is human ergonomics (no comments — notable for a file whose keys like `allow_custom_domain` deserve inline rationale).

**F1.7 — "Weird root file" ergonomics.** The root dotfile is discoverable-by-collision (visible in every root listing) but unexplained: the file carries no self-describing pointer — `schema_version` and `provider` only (CONTRACT.md:23-31). A teammate who has never installed the plugin finds a JSON dotfile with no comment capability and no URL. Under `.claude/` it would be co-located with other tool config (self-explaining by neighborhood) but invisible to people who don't open `.claude/`.

### Options

**(a) Status quo — tracked repo-root single layer, CWD climb.**

- For: zero migration (37 referencing files, incl. another plugin's compiled-in path); no `.claude/` write-guard exposure for unattended bind (F1.5); the binding genuinely is one-provider-per-repo team fact, and single-layer is honest about that (F1.4).
- Against: convention deviation stays open (config-cascade README:218); climb-past-repo-root capture bug persists unless separately fixed (F1.1); jira `auth_email` team-frozen (F1.3); no sanctioned home for any personal deviation; root-file ergonomics (F1.7).
- Note: F1.1 is fixable inside (a) without any layering change (anchor the climb at git toplevel).

**(b) Move to `.claude/<name>` + full cascade (user-global / team / `.local` overlay).**

- For: closes the convention row; one `.gitignore` line already covers the overlay (config-cascade README:108-121); `.local` overlay gives `auth_email`/`auth_env` a per-user home (F1.3); per-key merge semantics already specified fleet-wide (README:54-77); neighborhood ergonomics.
- Against: largest migration (37 references plus the autonomy plugin's independent reader — cross-plugin breaking change needing a compatibility window or dual-path read); write-guard prompt risk on unattended first-time bind (F1.5); the cascade's *user-global* layer is a trap for the `provider` key specifically (F1.4) — needs a declared exception ("provider is team-layer-only"; precedent: autonomy's security-axis exemption, config-cascade README:182-185); discovery must change from climb to root-anchor (behavior change for monorepo users who may rely on nested bindings — nothing documents that use, but the climb permits it today).
- Sub-choice: keep JSON (F1.6) even though `.claude/` neighbors are mostly YAML, or accept a new parser dependency.

**(c) Keep repo-root location, add cascade layers (`.work-item-tracker.local.json`, optional `~/.claude/work-item-tracker.json`).**

- For: minimal path churn (team layer's 37 references unchanged); solves F1.3 via the overlay; avoids write-guard entirely; the overlay spelling `*.local.*` matches the fleet convention even outside `.claude/` (standards convention does exactly this in `<standards_dir>/`, standards/README.md:110-115).
- Against: entrenches the location deviation the convention row tracks; a second root dotfile worsens F1.7; consumer needs a bespoke `.gitignore` line (the one-line recursive `.claude/**/*.local.*` promise doesn't cover repo-root overlays — the exact drift the convention laments at README:228-235); still needs the provider-key exception if a user-global layer is added.
- Minimal variant: overlay only (no user-global) — dodges the F1.4 provider trap entirely while still fixing F1.3; matches the `disk-hygiene`-style partial-layer precedent (declared deviation, README:213).

**(d) Make the location itself configurable.**

- For: maximal "consumer defines locations" alignment; precedent exists (`standards_dir` via `.claude/standards.yaml`; `contract_dir`/`memory_dir` via topic-docs).
- Against: bootstrap regress — a locator file is needed to find the config file, so either the locator lives at a fixed path (moving, not solving, the fixed-location question) or discovery probes N candidate paths; the binding is read by shell, Node, and prose-instructed model surfaces, so each locator implementation is a drift surface; payoff small unless real consumers have demanded a different location (no in-repo evidence of that demand; the demand-gated pattern of CONTRACT.md:274-277 could apply here).

**Format sub-question (any option):** JSON status quo costs comments; YAML costs a parser in three ecosystems (F1.6); a third path — keep JSON but add a `"_comment"`-tolerant or documented-in-CONTRACT posture — is the zero-cost degenerate. The `.claude/topic-docs.yaml` precedent shows YAML chosen where the *model*, not shell, is the main reader; this binding's hot readers are `jq` in shell scripts, the opposite profile.

## 2. Adapter shipping model — bundled vs consumer-generated

### What exists today

- Bundled: `github` (10/10 verbs), `local-markdown` (9/10, `reclaim:false`), `jira` (3/10, consume-only); consumer-local adapters already shadow/extend without forking (CONTRACT.md:121-127; dispatcher `wit_resolve_adapter_dir`, work-item-tracker.sh:31-45); setup documents the "another provider" path pointing at the consumer-local directory (setup/SKILL.md:88-91). Setup explicitly does **not** author adapters ("What this skill does NOT do", SKILL.md:491-493).
- The verification story a generator would need **largely exists**: the abstract conformance suite runs any adapter through the core CLI only, including negative cases, race back-off, lease lifecycle, exit-6 gating (run-conformance.sh:65-259); a new provider needs only a `bindings/<name>.sh` with `cb_setup`/`cb_teardown` (run-conformance.sh:49-55). The GitHub binding shows the sandbox-repo pattern for live providers (CONTRACT.md:429-434).
- What does **not** exist: any generator/interview skill; any conformance coverage of *read-path normalization fidelity* against a live provider (jira's read verbs covered only by mocked-curl unit tests; live pass explicitly deferred, CONTRACT.md:438-441) — the suite proves an adapter speaks the envelope, not that it *truthfully maps* the provider's semantics (state categories, blocker-link types, parent linkage). Those are precisely the per-instance facts the jira adapter had to externalize as config seams (`done_category_keys`, `blocked_by_link_type`, CONTRACT.md:402-410).

### Options

**Bundled-only.** Not the status quo (the shadow path exists) and cuts against the stated goal; main virtues: one owner for security-sensitive shell (credential-egress guard class, CONTRACT.md:368-374) and no version-skew story needed. Cost: the provider tail (Linear, Azure Boards, GitLab, Trello…) is bounded by maintainer time; every new provider is a plugin PR.

**Generated-only (interview + live exploration; ship no adapters).**

- For: maximal consumer-defined shapes; the jira experience is evidence *for* the interview-with-live-exploration model — two normalization facts could not be settled without inspecting the consumer's actual instance (CONTRACT.md:406-410), exactly what an agent-driven live pass does per-consumer.
- Against: (1) *Trust*: generated bash that receives credentials and hits network is the highest-risk artifact class; the bundled jira adapter needed deliberate hardening (token never in argv, host validation, deny-by-default egress) that a generator must re-derive every time; the conformance suite asserts protocol shape, not credential hygiene. (2) *Cold start*: every consumer pays an interview + generation + live-conformance session before the plugin does anything; the unattended first-bind path (setup/SKILL.md:276) becomes impossible. (3) *Coordination correctness is subtle*: claim-race sequence and reclaim revalidation (CONTRACT.md:242-263) encode hard-won invariants (open-only blocker counts vs GitHub's misleading `blockedBy.totalCount`, CONTRACT.md:164-166; comment-id race arbitration); the suite checks the happy race case but cannot enumerate every provider's sharp edge in advance. (4) *Fleet drift*: N consumers hold N divergent copies; a contract fix ships to none of them automatically. Maintenance transfer, not reduction: burden moves from plugin maintainer (few, expert) to each consumer (many, novice), mediated by generator-skill quality.

**Hybrid (bundled majors + a generator skill for the tail).** The structure is half-built: resolution order, `WIT_ADAPTERS_DIR`, and the conformance suite are already generator-ready; missing pieces: the interview/exploration skill itself, a conformance *binding* generator (each new provider needs `bindings/<name>.sh`), and a normalization-fidelity check the suite lacks.

- For: keeps hardened, maintained implementations for common providers (and the offline reference), while the tail gets live-exploration treatment; generated adapters land in the consumer's repo where the consumer's own review/CI owns them (consistent with CONTRACT.md:128-130).
- Against / open costs: **version skew** — nothing gates a consumer-local adapter's contract version: the dispatcher reads only `.verbs` from the manifest (work-item-tracker.sh:140-144) and never compares the adapter's `schema_version` to the core's expectation, so a generated 1.0 adapter runs silently under a future 2.0 core (see F3.6). **Two-tier support surface** — bug reports against generated code the maintainer has never seen. **Security review** of generated shell remains the consumer's problem unless the generator skill bakes in the jira-style guards as templates, which partially recreates the bundled-maintenance burden in template form.

## 3. Adversarial findings

**F3.1 — Cross-provider topology: the single-provider binding forecloses read-Jira/publish-GitHub, but the ID grammar already does most of the enabling work.** The binding permits exactly ONE provider (CONTRACT.md:20-21), yet the jira adapter is *designed* as a consume-only "source" surface (CONTRACT.md:347-354) — a shape that only pays off standalone, since binding jira disables `/work-items:work`, `track start`, and decompose publication (CONTRACT.md:352-354; setup SKILL.md:86-87). A "read from Jira, publish/coordinate on GitHub" topology would require: (i) a binding schema change — either a second `source` binding key or a role-typed provider list ({coordination: github, sources: [jira]}); (ii) dispatcher routing — for id-taking verbs nearly free because IDs are fully qualified with a provider segment (`jira:site/KEY#n`, CONTRACT.md:190-192), "opaque to core, parsed only by the adapter", so `get-item` could route on the id's provider prefix instead of the binding; (iii) the id-less verbs are the hard part — `list-items`/`list-frontier`/`create-item` have no id to route on, so a frontier over two providers needs either explicit `--provider` scoping or a merged-envelope semantics (and merged frontiers re-open the blocker question: a Jira item can't hold a *native* edge to a GitHub blocker — `cross_repo_edges` is already `false` for both non-GitHub adapters, so cross-provider edges would be text pointers, exactly the degradation local-markdown documents at CONTRACT.md:328-330); (iv) leases/labels stay coordination-provider-only, which the role-split binding would make explicit rather than accidental. Cost of *not* doing it: the entire jira adapter remains usable only in a repo that gives up coordination.

**F3.2 — GitHub issue/PR shared numbering: unaddressed anywhere in the repo.** GitHub allocates issue and PR numbers from one per-repo sequence. Decompose publishes every approved slice as an issue in the *coordination repo* (decompose/SKILL.md:117-138); work-loop lanes file self-observations there too; no file in the plugin mentions the numbering interaction. Topologies that avoid inflation, with their costs: (i) **separate issues-only repo** — supported in principle by `--repo <o>/<r>` on `create-item`/`list-frontier` (CONTRACT.md:51,59) and `cross_repo_edges:true` in the GitHub manifest, but breaks the derive-owner/repo-from-CWD default (CONTRACT.md:35-38), the branch-name→`Closes #N` pipeline (`Closes #N` closes same-repo issues only; tracker-seam.md:170-178 and the pull-request skill assume same-repo linkage), the "Open linked PRs" in-flight check (`closedByPullRequestsReferences` queried on the *code* repo's issue, github/README.md:196-264), and sub-issue intersect logic (child in another repo = documented truncation, CONTRACT.md:104-106); (ii) **different provider for items** (Jira/Linear as source-of-record) — lands on F3.1; (iii) **local-markdown for agentic churn** — avoids number consumption entirely but is "NEVER a coordination surface" and single-branch-confined (F3.4). Every avoidance topology collides with at least one load-bearing mechanic; the binding's one-provider-one-repo assumption is the common root.

**F3.3 — Lease protocol edge cases.**

- *Clock dependence*: liveness is `renewed_at + ttl` vs the local clock (lease.sh:69-77); nothing addresses cross-machine clock skew. TTLs are hours-scale so tolerance is high, but sub-hour leases (`lease_ttl_minutes`, #1034) shrink the skew margin.
- *Reclaim revalidation is not atomic*: CONTRACT.md:260-263 requires re-validating "immediately before the mutation", which narrows but cannot close the TOCTOU window — GitHub offers no CAS on unassign+comment-edit; two concurrent reclaims can both pass revalidation. Consequences bounded (same terminal state; idempotency claimed at CONTRACT.md:255) but the contract asserts "never a mutation" for the losing side, which the mechanics can't strictly guarantee.
- *Activity signals miss the main worker output*: reclaim's activity check is comments + PR cross-references; branch pushes explicitly deferred (CONTRACT.md:264-266). A worker that pushes commits for hours without commenting or opening a PR is indistinguishable from a crashed one and loses its claim at TTL — the exact autonomous-worker profile `/work-items:work` creates (worker commits/pushes before returning, PR opened later by the orchestrator, work/SKILL.md:236,244). Mitigation exists (renew-lease) but no step in work/SKILL.md instructs a long-running lane to renew mid-flight.
- *ttl 0 leases are never live*: `((ttl_seconds > 0)) || return 1` (lease.sh:74) means a `--ttl-hours 0` claim (used by conformance, run-conformance.sh:252) is born expired; two such claims both "succeed" without the race back-off ever seeing a live competitor. Harmless in tests; undocumented as contract behavior.
- *Same-login arbitration relies on provider comment-id monotonicity* (CONTRACT.md:248-251) — true for GitHub; a generated adapter for a provider without ordered comment ids would silently break the arbitration the conformance suite exercises only once (run-conformance.sh:224-225). Conformance *does* cover the cross-item renew guard (231-234) and back-off-supersede selection (243-248) — that part is solid.

**F3.4 — local-markdown single-branch confinement is structural and mostly undocumented.** The store is a tracked directory; items, edges, and leases are files in the working tree. Consequences: (i) items created on a feature branch don't exist on main until merge — a frontier read from another branch/worktree sees a different backlog; (ii) the "single-writer monotonic counter" (max file number + 1, CONTRACT.md:317-319) collides across branches — two branches each mint `42.md` and merge into either a conflict or two histories for one id; (iii) a claim (lease appended to the item file, CONTRACT.md:322-323) is a *working-tree edit* — uncommitted, invisible even to another worktree of the same branch; committed, it demands lease-churn commits. The contract's "NEVER a coordination surface" (CONTRACT.md:313-314) is the honest umbrella disclaimer, and expired-lease compensation in `list-items` (CONTRACT.md:336-340) papers over the missing reclaim — but the branch-confinement consequences appear nowhere (no "branch" mention in the local-markdown section). The work skill's orchestrator model (workers in isolated worktrees, work/SKILL.md:236) is maximally incompatible with this adapter: each worker's worktree has its own copy of the store.

**F3.5 — Dangling ADR reference.** CONTRACT.md:6 cites "ADR 0022"; `docs/adr/` holds only 0001–0013 (no file mentions 0022 anywhere else in the repo). The direction-locking rationale for the whole shipping model is uncitable in-tree.

**F3.6 — No contract-version handshake at the adapter seam.** Envelope objects carry `schema_version` (CONTRACT.md:134-136) and manifests carry one too, but the dispatcher never checks the manifest's version against its own (work-item-tracker.sh:109-144 reads only `.verbs`). Bundled adapters can't skew; consumer-local/shadowing/generated adapters can and will. The standards convention shows the fleet's pattern for exactly this (directional tolerant-reader, standards/README.md:196-201); the tracker seam has no analogue. Precondition for any generator-skill future and live *today* because shadowing is already supported.

**F3.7 — Hard-coded strings, each with a recorded posture.** (i) Container label `work-map`: `readonly` constant (frontier.sh:20), remap explicitly deferred to first real request (CONTRACT.md:274-277) — deferred-by-design. (ii) Role-label defaults: remappable via `config.role_labels` with silent fallback, but the *defaults themselves* are triple-defined — binding.sh, frontier.sh:30, and the dispatcher's inline fallback (work-item-tracker.sh:199) — three places to drift. (iii) Lease TTL: fully externalized, REQUIRED — strictest posture; cost: no binding can be minimal. (iv) `[Maintenance]` title prefix and `.github/recurring-schedule.json` path are fixed strings across setup/work/track with no remap seam — same class as (i) but with no recorded deferral.

**F3.8 — Two root-anchoring regimes coexist.** The seam climbs from CWD (binding.sh); every skill snippet anchors at `${CLAUDE_PROJECT_DIR:-$(git rev-parse --show-toplevel)}`; the adapter resolution uses `${CLAUDE_PROJECT_DIR}` only, with *no* git fallback (work-item-tracker.sh:37-43) — with `CLAUDE_PROJECT_DIR` unset (bare shell, CI), consumer-local adapter shadowing silently doesn't happen while the binding is still found by climb. Three different answers to "where is the consumer repo" in one seam.

**F3.9 — Decompose/work integration inherits the binding's one-repo assumption invisibly.** Decompose publishes via `create-item` without `--repo` (decompose/SKILL.md:132-137); work claims by qualified id but enumerates via CWD-derived repo. The `--repo` override exists at the seam (CONTRACT.md:36-38) but no skill surface plumbs it — a consumer wanting the issues-only-repo topology has a seam that could support it and a skill layer that can't express it.
