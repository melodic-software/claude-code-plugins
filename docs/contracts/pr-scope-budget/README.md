# PR scope budget: how big an agent-authored improvement PR may be

Owner doc for **the size limit on a pull request a skill authors on its own initiative**: a tidy,
a coupling reduction, an improve-one-thing fix. One home per the
[convention registry](https://github.com/melodic-software/claude-code-plugins/blob/main/docs/plugin-philosophy.md#convention-registry); skills point here and
never restate the numbers.

## Boundary

This doc owns the target and hard cap, what counts toward them, and the rule that a run never grows
a PR past the hard cap. It does not own:

- **What a skill hunts or how it ranks candidates.** Each adopter's own body decides that.
- **What happens to the remainder.** Whether overflow is planned, filed, or ledgered, and where
  deferred items are named, belongs to each adopting skill.
- **Human-requested work.** A PR a person asked for at a given size is theirs to size.

## Budget

| Metric | Target | Hard cap |
|---|---|---|
| Lines changed (additions + deletions) | ≤200 | ≤400 |
| Files changed | ≤8 | ≤15 |

The target is the shape to aim for: reviewable in one sitting and revertable in one step. The hard
cap is the bound no run exceeds; anything past it is overflow.

Basis: review effectiveness falls off above roughly 200 lines and reviews above roughly 400 lines
find few defects, per SmartBear's study of code review at Cisco (Cohen, *Best Kept Secrets of Peer
Code Review*, 2006). A skill whose runs keep hitting the cap has a scope
that is too coarse: narrow the scope, never raise the cap.

## What counts

- Lines: additions plus deletions, formatter-only whitespace included, because a reviewer still
  scans past it. Machine-generated lockfiles (`uv.lock`, `package-lock.json`, and similar) do not
  count.
- Files: every file with a non-whitespace edit. A rename counts once.

## Overflow

A run never grows a PR past the hard cap. What happens to the remainder is each adopter's own
overflow handling, stated in its skill body.

## Plugin-shipped copies

An installed plugin cannot read this repository's `docs/`, so an adopting plugin carries a
byte-identical copy at `plugins/<plugin>/reference/pr-scope-budget.md`, generated by
`scripts/sync-shared-copies.sh` from this file and registered in `scripts/shared-copies.txt`.
Edit this file, never a copy, then rerun the script.
