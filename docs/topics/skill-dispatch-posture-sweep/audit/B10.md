# B10 — dispatch-posture audit

Criteria: [`LEDGER.md`](../LEDGER.md).
Decisions: [`docs/topics/discovery-subagent-dispatch/PLAN.md`](../../discovery-subagent-dispatch/PLAN.md).

None of the 16 skills in this batch carries `context: fork`, an `agent:` key, or
`disable-model-invocation: true`. Frontmatter is uniform: `user-invocable: true`,
`disable-model-invocation: false` (omitted only on `/source-control:commit`), with `shell: bash` on
`skill-quality:check`, `babysit-prs`, `commit`, `pull-request`, `resolve-conflicts`, `worktree`.

| Skill | Verdict | Mechanism | Rationale |
|---|---|---|---|
| `/skill-quality:check` | DISPATCH-OPTIONAL | `plugin-agent` | The named-skill run is a cheap script call whose whole output (`PASS/FAIL` + `FAIL:` lines) is what the user acts on — no context to save. The no-name run ("enumerate each immediate subdirectory of the skills root that contains a `SKILL.md` and run the script once per skill") is a bulk inventory over ~138 skills and is the dispatch case; progressive disclosure applies there — a rollup index plus a per-skill sidecar rather than every skill's `FAIL:`/`WARN:` block inline. |
| `/songwriting:co-write` | NO-CHANGE | — | Not a dispatch candidate: "Co-write facilitation is coaching, not monologue… surface choice points, do not decide for the writers." The deliverable (titles, labeled option menus) is the in-conversation material itself; it loads a handful of small `context/pat-pattison/research/*.md` files, not a corpus. |
| `/songwriting:diagnose` | NO-CHANGE | — | Not a dispatch candidate: the output is a critique delivered to the writer ("Name the dominant problem; offer one focused revision"), and audit boxes are "presented as a deliberate choice point, pass/fail/skip" — a turn-by-turn exchange, not a report the parent would file and skim. |
| `/songwriting:meter-prosody` | NO-CHANGE | — | Not a dispatch candidate: scansion of a pasted line is a single short reasoning pass over 1–3 small context files; "Stability is a tool, not a verdict… the writer chooses" makes the output conversational by contract. |
| `/songwriting:object-writing` | NO-CHANGE | — | Not a dispatch candidate: "If the user asks for a prompt, generate one usable timed exercise immediately" — a one-shot generative response whose whole value is the text in the conversation. |
| `/songwriting:practice` | NO-CHANGE | — | Not a dispatch candidate: "issue one daily craft prompt immediately"; the only file work is persisting the day's practice to `songwriting/practice/<YYYY>/<date>.md`. Nothing is read at volume. |
| `/songwriting:rhyme` | NO-CHANGE | — | Not a dispatch candidate: "Surface 8-15 labeled candidates across tiers, never a single winner" — generation, not retrieval. Its one external call is a single bundled `datamuse.sh` lookup used only as a supplement. |
| `/songwriting:song-form` | NO-CHANGE | — | Not a dispatch candidate: recommends "the smallest structural change that fixes the problem" against a pasted draft; loads 2–3 small method files per action and answers in-conversation. |
| `/songwriting:suno` | DISPATCH-OPTIONAL | `plugin-agent` | Prompt-craft actions (`prompt`, `style`, `lyrics`, `clean`, `tags`, `troubleshoot`) are generative and stay inline. The `research <topic>` action and `genre` **research mode** are genuine external fan-out — "On-the-fly external research — artist sonic profiles, current trends, niche genres… (WebFetch / Perplexity) to fetch BPM range, instrumentation, vocal style, production character. Cite sources" — page content the parent never re-reads; an escape hatch belongs on those two paths only. |
| `/songwriting:workflow` | NO-CHANGE | — | Not a dispatch candidate: it is the plugin's front-door router ("route straight to the concern skill… do not re-explain here") and its `coach` action is an explicit interactive loop — "ask ONE question, wait, apply Pat's tool, surface the next choice point." Routing is the cheapest possible main-context work. |
| `/source-control:babysit-loop` | NO-CHANGE | — | Already dispatches: conflict/blocker work goes "through babysit-prs's own fan-out and conflict-worker contract," at the frontier capability tier with a subagent discipline preamble on every dispatch prompt. No *outer* dispatch wrapper is constructible either — the lane self-paces with `ScheduleWakeup` ("At the end of every cycle that does not stop, schedule the next with `ScheduleWakeup`, whose delay clamps to `[60, 3600]` seconds"), launches via `/loop`, and runs an `AskUserQuestion` mini-interview on ambiguous interactive config; all three are dropped in every subagent. Same posture as its sibling `babysit-prs` on the same two grounds. |
| `/source-control:babysit-prs` | NO-CHANGE | — | Already dispatches, by design: "spawn one fresh, unbiased sub-agent per actionable PR up to the concurrency cap" (default `babysit_worker_concurrency_cap` = 10), each worker owning its own lease and isolated worktree, plus a mandatory extractor-subagent dispatch for any comment carrying ≥3 findings (review-discipline §2). The orchestrator itself must stay in main context anyway — Step 7 "Self-pace: schedule the next wake per the cadence contract" is `ScheduleWakeup`. |
| `/source-control:commit` | NO-CHANGE | — | No context problem to solve: it reads `git status` / `git diff --cached --stat` summaries via `!` pre-computed injections and emits one SHA + subject. Its heavy prose is mechanism (heredoc form, staging guards), not volume of material read. Dispatching would add a hop and hide the message-drafting gate. |
| `/source-control:pull-request` | INLINE-ONLY | — | **Blocker: mandatory mid-flow user decision gates on an irreversible action.** The "Decision gates (pause for user)" table (prep findings triage, commit message content, CI fix proposal, "Merge confirmation — irreversible action") plus the interactive create→monitor checkpoint ("ask the user whether to proceed to Phase 3"). This is *not* the `/explore` case PLAN.md allows to degrade — there, open questions are advisory output the parent re-surfaces afterward. Here each gate is a precondition the flow cannot pass without an answer, so deferring it to a returned summary either stalls the run or lets an irreversible merge land unconfirmed. It already dispatches the sub-part that warrants it: "For ≥3 findings, MANDATORY subagent dispatch" (review-discipline §2), and Phase 1 prep delegates to review agents when present. |
| `/source-control:resolve-conflicts` | DISPATCH-OPTIONAL | `plugin-agent` | Real dispatch signal: intent archaeology reads full patches per side per path (`git log -p "$BASE"..MERGE_HEAD -- <path>`, `git show REBASE_HEAD -- <path>`, PR bodies via `gh`) plus a whole-tree semantic sweep, and the parent needs only the step-5 resolution table — an index-plus-sidecar artifact (table as index, per-path intent evidence as sidecars) fits. Inline stays the default because the user usually wants per-hunk judgment visible, the agent would be mutating the parent's live in-progress merge in a shared worktree, and the "stop and ask the user" fallback degrades to text the parent must re-surface. |
| `/source-control:worktree` | INLINE-ONLY | — | **Blocker: turn-scoped session state the parent must observe live** — confined to the `EnterWorktree` terminal, not to provisioning. `create` ends with "`EnterWorktree(path: "<printed-path>")` as the final action — working directory changes and session state transitions on that call"; in a subagent that transition moves the subagent, not the parent, defeating the whole action. The skill already documents the dispatchable complement and deliberately keeps it out of this action: an orchestrator that "must stay resident to keep dispatching… cannot invoke `create`" and instead provisions non-interactively — the worker "runs the shared `worktree-create.sh` helper directly… then works the worktree via `git -C <path>` **without entering it**" (`#572` owns that lifecycle). So the *skill action* stays inline while the underlying provisioning is already available to dispatched callers by another route. `cleanup` compounds the inline case — Step 4c "Emit `git branch -D` + self-worktree removal for the USER to run, never inline." |

## Notable

- **Both `INLINE-ONLY` verdicts are *harness*-blocked, not judgment calls, and neither rests on
  `AskUserQuestion` alone.** PLAN.md already establishes that an `AskUserQuestion` need normally
  *degrades* (`/explore` returns its open questions as text and the parent re-surfaces them), so
  "this skill asks the user something" is not by itself a blocker anywhere in this sweep. What
  blocks here is narrower: `pull-request`'s gates are mid-flow preconditions on an irreversible
  merge, and `worktree create`'s `EnterWorktree` terminal must move the *invoker's* session. Both
  are named entries on the checklist's hard-blocker list; neither needs a discretionary override.
- **The `babysit` pair takes one posture, not two.** `babysit-prs` and `babysit-loop` are both
  NO-CHANGE on identical grounds — each already dispatches (per-PR workers under leases, isolated
  worktrees, and a concurrency cap; the loop reaching that same fan-out for conflict work), and each
  self-paces with `ScheduleWakeup`, so no outer wrapper is constructible for either. An earlier draft
  split them; the split was wrong and is worth guarding against at the ledger merge, since the two
  read very differently in isolation. Both are the batch's best reference shape for `plugin-agent`
  dispatch elsewhere in the sweep — particularly the rule that narrative guidance handed to an
  invoked skill is not enforcement (the loop's deterministic pre-partition exists precisely so a
  merge-capable invocation only ever *receives* rung-eligible refs), which applies to any
  dispatched-agent prompt this project writes.
- **The `songwriting` plugin is a clean negative control: eight of nine are simply not dispatch
  candidates**, and for one structural reason, not nine ad-hoc ones — every skill's contract makes the
  *emitted text* the deliverable (options, critique, prompts, scansion) and gates it behind a
  mandatory in-conversation `response-filter` pre-flight that names each box's pass/fail/skip. The one
  exception, `suno`'s `research`/`genre`-research paths, is external web fan-out that arguably should
  not grow its own dispatcher at all — it is a candidate to delegate to `/discovery:research` once
  that skill dispatches by default.
