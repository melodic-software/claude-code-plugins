## Notable

- **The plugin's tier metadata already encodes a dispatch-adjacent taxonomy.** Each corrector
  carries `metadata.re-anchor-batch` (`core` / `situational` / `never`) and
  `re-anchor-batch-rank`. `never` is assigned exactly to the three skills this audit verdicts
  NO-CHANGE (`do-your-research-deep`, `recheck-against-upstream-deep`, `scrutinize-dont-coast`) —
  i.e. the plugin has already, independently, separated "runs in the main batch" from "has its own
  heavier execution tier". Any dispatch posture added here should read that metadata rather than
  introduce a parallel classification (which `reuse-or-replace` would itself flag as a silent
  second way).
- **Fork cost is measured and cuts against dispatch-by-default for this family.**
  `sweep-all-disciplines` records: "each fork consumed ~170K tokens (inherited transcript), so an
  8-in-scope pass in two waves of four ran ~1.4M tokens for the audit phase alone. Budget the sweep
  as a deliberate spend, not a reflex." Because a history-inheriting fork's cost *scales with
  transcript length*, dispatch here gets more expensive exactly as the session gets long — the
  inverse of the Brief's context-saving premise, which rests on fresh agents that carry no history.
- **Three fan-out skills report their ledger inline and none mandates a durable artifact** —
  `do-your-research-deep` ("Report a per-item ledger — 100% of the inventory", 5 fields per row over
  a full-session inventory), `recheck-against-upstream-deep` ("report an **inline** divergence
  ledger"; its only persistence is a best-effort checkpoint "when one is available … proceed without
  it rather than asserting a persistence surface"), and `sweep-all-disciplines` ("Report one
  consolidated ledger" across up to ~10 correctors). All three are progressive-disclosure candidates
  under Brief decision 4, and the Brief's own constraint applies verbatim: `TaskCreate`/`TaskGet`/
  `TaskList`/`TaskUpdate` do not survive the background filter, so any ledger a dispatched agent
  maintains must be a file on disk.
- **`recheck-against-upstream-deep` explicitly declines to mandate a store**, which will collide
  with Brief decision 5's mandatory-checklist-file posture if that posture is generalized. This is a
  live design conflict, not a drafting slip — the skill argues the case ("never mandates a store or
  invents one").
- **Two skills currently over-claim nothing but under-persist.** No skill in this batch writes a
  durable artifact today. Any dispatch verdict above therefore also implies inventing the artifact
  contract, not just moving execution.

## Audit/correct separability

Recorded per the batch instruction. Every corrector runs the same four-step shared loop; the
question is whether steps 1–2 (re-anchor + audit) detach from step 3 (correct forward).

**The general answer: separable in principle, but only via one mechanism, and step 1 never
detaches.**

- **Step 3 (correct) is main-thread-bound by contract.** Not because a subagent cannot edit files —
  it can — but because the shared method doc defines the deliverable as salience: "A corrector
  re-injects the discipline near the context tail, where it regains the pull the standing rule has
  lost, and forces an active audit-and-correct pass instead of a passive reminder." A subagent that
  re-anchors in its own context and exits leaves the main thread's posture untouched, which is the
  entire product.
- **Step 2 (audit) detaches only to an Agent-tool `fork`.** `sweep-all-disciplines` establishes and
  justifies this: fresh/typed subagents and skill-level `context: fork` both start blind, so neither
  can audit this conversation. It also states the degradation honestly — fork-spawning is
  rollout-gated (`CLAUDE_CODE_FORK_SUBAGENT`), and "if forks are unavailable, report that the
  inheriting audit fan-out cannot run and stop, rather than auditing blind." Note this degrades to
  *stop*, not to *inline*, which is a sharper failure mode than the Brief's graceful-degradation
  pattern elsewhere.
- **Per-skill separability of the audit half:**
  - *Transcript-bound (audit half detaches only to a fork)* — `do-your-research`,
    `mind-your-maxims`, `use-your-skills`, `tighten-your-output`,
    `script-the-deterministic-work`, `reason-dont-recite`, `scrutinize-dont-coast`.
  - *Mixed, with a genuinely detachable read/fetch sub-phase* — `follow-our-standards` (standards
    doc retrieval), `recheck-against-upstream` (vendor doc fetch + divergence classification),
    `pick-for-the-problem` (field survey, already routed to `/discovery:research`),
    `point-dont-copy` and `reuse-or-replace` (artifact-located findings a fresh agent could locate
    given a diff, though the session-authored half is not).
  - *Fully detachable, no transcript dependence* — `recheck-against-upstream-deep` only.
- **`scrutinize-dont-coast` inverts the rule and says why.** Its fresh-context pass must be
  *non*-fork — "A fork inherits the parent conversation and carries the bias forward, so it does not
  satisfy this." So within one plugin, `sweep-all-disciplines` requires fork and
  `scrutinize-dont-coast` forbids it, for the same underlying reason (what the agent must and must
  not see). Both are correct; a single blanket dispatch mechanism cannot serve both.

## The `-deep` split — what it means today, and whether dispatch-by-default collapses it

Two `-deep` siblings exist: `do-your-research-deep` and `recheck-against-upstream-deep`.

**Mechanically, the split is execution tier plus audit breadth, not discipline.** Both `-deep` files
explicitly hold no copy of their discipline — "The discipline this re-anchors and its portable
baseline live in the sibling … There is no separate copy of the discipline here — update the sibling
and this tier follows." The delta is:

- *base* — one pass, inline, over the single claim or single surface in play.
- *-deep* — enumerate a full inventory (every claim in the session / every upstream-dependent
  surface in the subsystem), fan throttled fresh-context subagents over it in bounded waves, retry
  only the failed subset, report a per-item ledger.

`do-your-research-deep` adds a second axis the other lacks: a configurable depth
(`tiered` | `full`) resolved by argument → `${user_config.research_deep_verification}` → `tiered`.

**Would dispatch-by-default collapse them? No — for a reason specific to this plugin.** Brief
decision 1's collapse question presupposes the *parent* can dispatch. Here it cannot: nine of the
eleven base correctors are INLINE-ONLY on a transcript/salience blocker, and the two rated
DISPATCH-OPTIONAL keep inline as the default. A parent that stays inline cannot absorb its `-deep`
sibling's fan-out, so the pair remains genuinely two tiers. This is a **material contrast with the
`discovery:research` / `research-deep` pair**, where the parent is the one adopting dispatch and the
deferred question is live — the answer there should not be generalized to this family. If the answer
there is "the parents become dispatchers and the `-deep` skills retire", re-anchor is a named
counterexample: its `-deep` skills survive on their own merits.
