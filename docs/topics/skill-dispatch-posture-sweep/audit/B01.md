## Notable

- **`!`-precompute is the batch's biggest unverified dependency.** Six of eleven (`improve`,
  `bug-report:write`, `claude-config:audit`, `audit-automation-gaps`, `claude-memory:audit`,
  `stateless`) declare `shell: bash` and open with a `!`-prefixed pre-computed context block — and for
  `stateless` and `claude-memory:audit` that block *is* the skill's discovery step. Whether that
  command substitution executes when a skill arrives via a subagent's `skills:` preload (rather than
  through a `Skill` tool invocation) is **not** covered by the Brief's verified harness facts. If it
  does not fire, every dispatched agent silently starts with `unknown`/`0` values instead of real
  state. This needs an empirical check before any of the five DISPATCH-DEFAULT rows ships — it
  affects far more than B01.
- **No skill in B01 sets `disable-model-invocation: true`, `context: fork`, or `agent:`** — the
  plugin-agent mechanism is available to all eleven. Nine declare `disable-model-invocation: false`
  explicitly; the two `claude-memory` skills omit the key entirely (default is `false`, so preload
  works either way — but the inconsistency is worth a hygiene pass).
- **The audit-family cluster is the real prize, and it is already half-built.** Four of the five
  DISPATCH-DEFAULT rows are `*audit*` skills sharing one shape: read-only sweep → severity-rated
  findings table → optional approval-gated fix. Two already persist a report to
  `${CLAUDE_PLUGIN_DATA}/.../last-audit.md` and one already fans out per-surface subagents. The
  recurring split is identical in all four — **the read-and-report phases dispatch; the
  `--fix`/`--implement` phase stays with the parent because it is approval-gated** — which argues for
  one shared audit-agent pattern rather than four bespoke agent definitions.
- **Nested fan-out is load-bearing for three rows, not incidental.** `audit-instructions`,
  `audit-automation-gaps`, and `improve` all spawn their own subagents. Decision 3's
  optional-detected-capability posture covers the first two (sequential degradation, same coverage),
  but `improve`'s Design-It-Twice branch is *defined* by parallel orthogonal designers — a sequential
  degradation changes the method, not just the speed.
