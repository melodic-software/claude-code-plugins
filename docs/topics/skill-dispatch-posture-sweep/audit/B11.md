## Notable

**§1 — The Agent-unavailability rule (decides four rows; state once, do not re-derive).** `Agent` is
removed from every subagent unless `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` is set, and PLAN Decision 3
makes that env var an *optional detected capability*, not a requirement. Therefore: **a skill whose
contract requires nested spawning cannot adopt a dispatch-by-default posture** — its invariant would
silently break on any machine without the env var. It decides `/work-items:work` (orchestrator-never-edits
depends on dispatching workers) and reinforces `/work-items:work-loop`. It does **not** decide
`/verification:confirm` or `/testing:run-e2e`: both document inline fallbacks for every spawn path
(`confirm` SKILL.md:81, :93; `run-e2e` delegates but its orchestrator half degrades), so they degrade
rather than break.

**§2 — Dispatch as an independence mechanism, not just a context saving.** `/verification:confirm`
already requires the Stage-2 verdict to come from "an agent that did NOT produce the artifact …
withholding your rationale so it audits the artifact and not your story" (SKILL.md:100). Dispatching
the skill satisfies that invariant by construction. This reframes the dispatch decision for every
review/verify-shaped skill: the argument is correctness (producer ≠ critic), not only token cost.

**§3 — Two skills already implement the target posture.** `/testing:run-e2e` isolates its drive loop
in a subagent and consumes only evidence paths (SKILL.md:45-47); `/verification:confirm` persists an
assertion-only manifest to the contract slice while raw captures stay at `<memory_dir>/<slug>/scratch/`
(SKILL.md:102). Both are in-repo precedents for the index-plus-sidecar shape of Decision 4 and can be
cited by the plan step instead of inventing the pattern.

**§4 — Frontmatter.** None of the 17 sets `context: fork`, `agent:`, or `disable-model-invocation: true`.
Twelve declare `disable-model-invocation: false` explicitly; `/toolchain:check`, `/toolchain:lint`, and
`/visualization:visualize` omit the key entirely (the default is `false`). All 17 therefore qualify for
`skills:` preload on a plugin agent — no row is blocked by frontmatter.

**§5 — `/testing:plan` has no durable artifact today.** It only presents the plan in conversation
(SKILL.md:95). Its DISPATCH-DEFAULT verdict is conditional on adding a memory-slice write; the same
gap applies to `/work-items:scan-todos`' inventory.

## Task-tool dependency

**No skill in B11 depends on `TaskCreate` / `TaskUpdate` / `TaskList` / `TaskGet`.** Verified by grep
over the whole of `plugins/work-items/`, `plugins/testing/`, `plugins/toolchain/`,
`plugins/verification/`, `plugins/visualization/`, and `plugins/tdd/` — zero matches in any file
(SKILL.md, context, reference, actions, evals, scripts). The batch's Task-tool risk is nil.

The `work-items` family reaches its tracker entirely through **surfaces that survive the background
filter**:

- **Coordination** — `${CLAUDE_PLUGIN_ROOT}/tools/work-item-tracker/work-item-tracker.sh <verb>`
  (`claim`, `reclaim`, `list-frontier`, `create-item`), a shell script over the bound adapter
  (`work/SKILL.md:76-78, :125-128, :185-188`; `decompose/SKILL.md:122-127`). Bash survives.
- **The one deliberate inlined provider call** — the `#502` telemetry upsert is raw `gh api`
  (`work-loop/SKILL.md:63-84`; `attend-queue/SKILL.md:97-118`). Bash + `gh` survives.
- **Durable state is already files and tracker comments, never harness task state** — the per-lane
  telemetry issue comment carrying the `work-items/loop-state@1` block (`work-loop/SKILL.md:99-107`),
  and `<memory_dir>/<slug>/work-items-checklist.md` (`track/SKILL.md:41-45`; `work/SKILL.md:28-35`).
  This already matches the Brief's rule that a dispatched agent's ledger must be a file on disk.

**The single harness-scheduling dependency in the batch is `/work-items:work-loop`'s `ScheduleWakeup`**
(SKILL.md:47, :190) — dropped by Filter 1 in every subagent, everywhere, not only in background mode.
That is a genuine hard blocker and is the sole reason a `work-items` skill fails dispatch on tool
availability. `Monitor` (`attend-queue/SKILL.md:148`, `work-loop/SKILL.md:128`) and `EnterWorktree`
(referenced in `work`/`work-loop` evals, and explicitly *avoided* by the orchestrator at
`work/SKILL.md:194`) both survive the background filter and block nothing.
