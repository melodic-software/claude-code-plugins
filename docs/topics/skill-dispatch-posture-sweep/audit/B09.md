# B09 — dispatch-posture audit

Batch of 15 skills, audited against the locked decisions in
[`docs/topics/discovery-subagent-dispatch/PLAN.md`](../../discovery-subagent-dispatch/PLAN.md)
and the criteria in
[`LEDGER.md`](../LEDGER.md), **as amended** —
`history-fork` mechanism, live-USER blocker phrasing, own-`Agent`-fan-out blocker, and the
preload-vs-runtime-invocation ruling.

Mechanism is recorded only for dispatch verdicts; non-dispatch rows carry `—`.

| Skill | Verdict | Mechanism | Rationale |
|---|---|---|---|
| `/repo-fleet-hygiene:audit` | DISPATCH-DEFAULT | plugin-agent (runtime invocation) | Read-only by contract ("The bundled script has no mutation mode"), fans a `gh`/`git` sweep across an entire fleet, and its whole output is a confidence-tiered report the parent consumes as findings — the raw per-repository evidence never needs to enter the orchestrator's window. **This is the one row where the checklist's preload carve-out collides with itself:** the skill has no `!`-precompute, which would qualify it for `skills:` preload, but its `allowed-tools` grant (`Bash(bash ${CLAUDE_PLUGIN_ROOT}/skills/audit/scripts/audit-fleet.sh *)`) *is* load-time machinery whose behavior under preload is unverified — so runtime invocation, with `Bash` granted coarsely in the agent's `tools:` and the command-pattern narrowing lost. Progressive disclosure: the five grouped lists (`HIGH`/`MEDIUM`/`LOW`/`UNKNOWN`/`ACKNOWLEDGED`) are already a natural index-plus-sidecar split, one sidecar per repository section, and the skill today persists nothing — it should write the report to disk rather than return it inline. |
| `/repo-hygiene:clean` | INLINE-ONLY | — | **Blocker: the absence of a live USER.** Every mutating path is gated on a human decision the skill cannot manufacture — "show dry-run output → confirm → only then `--apply`" at §1.5 pre-flight, §4.2 branch deletion, §4.3 stash triage, §6/§6.5 tree reset, §7 orphan removal, and §8 batch — and the skill's own autonomous fallback is `abort`, not proceed. The `CLEAN_GUARD_ACK=1` prefix is legitimate only "after the user's explicit confirmation in this session"; with no user in the loop there is no path to an apply, whatever tool the confirmation would have used. |
| `/review:fanout` | INLINE-ONLY | — | **Blocker: its own `Agent` fan-out as a correctness control**, plus an unconditional main-thread requirement stated in the file — the three orchestrator plugins "All run on the MAIN THREAD (they fan out their own agents; a subagent cannot dependably do that)". Recursion recorded: dispatching fanout would strip `Agent` unless `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` is set (Decision 3 keeps that optional), silently collapsing a breadth sweep across many independent surfaces into one agent's inline self-critique — the exact failure the skill exists to prevent. It is itself the dispatcher; the context saving already happens at its leaves. |
| `/review:quality-gate` | INLINE-ONLY | — | **Blocker: its own `Agent` fan-out as a correctness control**, stated as a hard rule — "Self mode never runs the checklist on the producing thread. Dispatch a fresh-context read-only subagent; the thread that wrote the code rubber-stamps its own recap." Dispatching this skill degrades exactly that step to inline self-critique, reintroducing the rubber-stamp it was written to block. Step 2's "verify each finding against the actual diff (a subagent's report is synthesis, not evidence)" is a parent-side obligation by design. Same load-time caveat as the fleet audit: its `allowed-tools` grant (`Bash(gh pr list:*)`) is load-time machinery of unverified behavior under preload. |
| `/session-flow:clean-stop` | INLINE-ONLY | — | **Blockers: the live transcript, and the degrade-to-stop that carrying it would impose.** Step 1's scope — "every repository and worktree **this session touched**" — is the conversation, so `history-fork` is the only mechanism that could carry it. That is not acceptable here: `history-fork` is rollout-gated by `CLAUDE_CODE_FORK_SUBAGENT` and degrades to *stop*, not to *inline*, and this skill is explicitly the supersede path for `handoff` "when the machine itself may go away". The discriminating question is whether degrade-to-stop is safe for a loss-prevention contract; it is not — a skill whose failure mode is "do nothing before the disk disappears" cannot take a posture that can silently decline to run. Reinforcing: that inferred scope drives irreversible outward-facing writes (push, `gh pr create`, issue filing). |
| `/session-flow:continue-in-background` | INLINE-ONLY | — | **Blocker: the live transcript, where the only mechanism that carries it inverts the premise.** The save-point *is* the conversation (position, what was tried and ruled out, remaining work), so `history-fork` is the sole fit — but the skill fires precisely when context is heavy and the user is stepping away, i.e. when transcript-length cost is maximal, while its own work is one file write plus one `claude --bg` launch. There is no bulk content to move off the parent, so dispatch cost exceeds dispatch benefit by construction. |
| `/session-flow:handoff` | INLINE-ONLY | — | **Same blocker, same engine.** Its documented triggers are "Mid-task, context heavy" and "Quality degrading (context rot)" — the exact conditions under which `history-fork`'s cost scales worst — and its output is a handoff file plus a rails prompt, not a bulk read. Dispatching a save-point writer costs more transcript than it saves. |
| `/session-flow:keep-going` | INLINE-ONLY | — | **Blockers independent of the transcript.** It reconciles against task-ledger surfaces (`TaskGet`/`TaskList`) that the background filter drops, and it resumes, restarts, or kills the off-thread work *this session* spawned — harness control that reaches only the session owning it, whatever context a fork inherits. Step 4's "Reconcile the main thread… then continue it" then puts the main task back in motion. |
| `/session-flow:orchestrate` | INLINE-ONLY | — | **Blocker: the output is a mutation of the invoking session's context, not an artifact.** "Do NOT re-emit the imperatives — loading them IS the priming." Any dispatch mechanism, `history-fork` included, would arm the child and return nothing to the parent — the one context that needed arming. Not a transcript-input blocker: it reads no conversation, it writes to one. The Priming addendum confirms the boundary, claiming main-session-only surfaces (agent teams, dynamic workflows) "a pasted target cannot reach". |
| `/session-flow:orient` | DISPATCH-OPTIONAL | history-fork | Read #1 of four is "**The conversation** — the goal, the load-bearing decisions… Synthesize these inline", so fresh-context mechanisms are out and `history-fork` is required. Nothing else blocks — it is read-only ("Writes nothing"), needs no user, spawns nothing, touches no task tools. **The cost curve points the right way here, uniquely in this batch:** orient fires on "where were we" / "catch me up" / session start, when the transcript is *shortest*, while the bulk of its work is the durable-state leg (handoffs, workflow checklist, running-retro ledgers, `gh pr list`, off-thread glance). Optional rather than default because `CLAUDE_CODE_FORK_SUBAGENT` is rollout-gated and degrades to stop — acceptable for a briefing, since inline orientation stays available. |
| `/session-flow:reanchor` | DISPATCH-OPTIONAL | plugin-agent (runtime invocation) | The four checks are file- and network-bound, not conversation-bound — read handoff/plan files, `gh` a PR's state, `git fetch` a base and count against `FETCH_HEAD`, compare installed vs source manifests — and the output is a drift list ("premise → claimed state → actual state") the parent acts on. Fresh context suffices *provided* the parent hands over the premise list, since "Gather the session's inputs" and "Scope to what the session's inputs actually reference" originate in the live session; when the premise set exists only in the transcript, `history-fork` is the fallback. Inline stays the default for that hand-off reason. The skill carries no `!`-precompute, no `allowed-tools`, and no `${user_config.…}`, so it is one of the few genuine `skills:`-preload candidates under the checklist's carve-out — runtime invocation is still the safer default. |
| `/session-flow:reconcile` | INLINE-ONLY | — | **Blockers independent of the transcript.** It closes proven-done tasks through `TaskList`/`TaskGet`/`TaskUpdate`, all dropped by the background filter, and retires or kills off-thread work this session spawned. The file names the containment itself: "harness control reaches only this session's own work". |
| `/session-flow:retro` | DISPATCH-DEFAULT | plugin-agent (runtime invocation) | The bulk work is a parser run over `<session-id>.jsonl` **on disk** plus selective transcript reads — high-volume raw content the parent never re-reads, yielding metrics, five scored dimensions, and a regression check. No transcript *inheritance* is needed: the record is a file, and the sibling `running-retro` already proves the shape by resolving absolute paths and delegating to a fresh subagent. Runtime invocation, not preload — the skill carries `!`-precompute blocks and `shell: bash`, exactly the load-time machinery the checklist flags as unverified under `skills:`. Two parent-owned carve-outs: `codify`'s Phase 4 needs **a live user** ("never persist codifications without explicit user approval"), re-surfaced by the parent per the Brief's acceptance criterion; and mode inference reads live context pressure ("when context is >75% used or compaction has occurred, prefer `quick`"), which no dispatched agent can observe, so the parent passes the mode explicitly. Progressive disclosure: the session-mode output is a natural index-plus-sidecars set. |
| `/session-flow:running-retro` | NO-CHANGE | — | Already dispatches: step 3 spawns a subagent, and "The subagent returns a compact findings block only; the verbose transcript stays in its context" — the posture this effort is establishing, shipped. **Recursion recorded:** it also belongs to the own-`Agent`-fan-out blocker class, because fresh context is the point ("it sees none of this conversation, the skills invoked, or files read") — dispatching running-retro would degrade its mandated fresh-context analysis into self-analysis. Its residual inline steps are correctly inline: the mandatory subjective-state note ("the only signal the analysis subagent cannot get for itself"), the ledger append, and the offer-routing gate. It also reads `${user_config.observer_*}` values, which the file states render only because "A skill runs **in-session**" — a concrete instance of the load-time machinery behind the checklist's preload caution. Refinement candidate, not a verdict change: it spawns a generic `general-purpose` agent, so discipline arrives as prompt text rather than a purpose-built agent body. |
| `/session-flow:workflow` | INLINE-ONLY | — | **Blocker: `TaskCreate`**, dropped by the background filter — §4 tracks progress by creating "a task per applicable stage via TaskCreate". `history-fork` would cover the other half (position detection is explicitly conversational: "Check conversation context for evidence of completed stages") but cannot restore a filtered tool. Its output is a next-stage recommendation to the user — an in-conversation decision rather than a report. |

## Notable

- **Frontmatter negative, checked and absent.** No skill in this batch carries `context: fork`,
  an `agent:` field, or `disable-model-invocation: true` — so none is undispatchable under the
  Brief's pending amendment 2. All eleven `session-flow` skills and both `review` skills declare
  `disable-model-invocation: false` explicitly; `/repo-fleet-hygiene:audit` and
  `/repo-hygiene:clean` omit the field (defaulting to model-invocable). Nothing in this batch is
  pre-wired for dispatch at the frontmatter level.
- **`session-flow` splits on "whose state?", and the amendment sharpens where the line falls.** The
  two skills whose inputs are durable artifacts — `retro` (a JSONL on disk) and `reanchor` (files,
  refs, and API state) — take fresh-context mechanisms. `orient` is the one skill whose transcript
  dependency is both real *and* affordable, so it takes `history-fork`. The remaining eight are
  blocked by something no fork can repair: filtered task tools (`keep-going`, `reconcile`,
  `workflow`), session-scoped harness control (`keep-going`, `reconcile`), a context mutation of
  the invoking session (`orchestrate`), an absent user (`repo-hygiene:clean`), a mandated `Agent`
  fan-out (`review` ×2), or a cost curve that inverts the premise (`handoff`,
  `continue-in-background`, `clean-stop`).
- **`history-fork`'s cost curve is the discriminator, not its availability.** Three skills here fire
  *because* context is heavy — `handoff`, `continue-in-background`, and (at end of session)
  `clean-stop` — so the mechanism that could carry their input is most expensive exactly when they
  run, while their own work is a file write and a command. `orient` is the mirror image: it fires at
  session start or on "catch me up", when the transcript is shortest and the durable-state leg
  dominates. Availability gating (`CLAUDE_CODE_FORK_SUBAGENT`) is the secondary constraint;
  transcript length is the primary one.
- **`repo-hygiene:clean` carries a *skill*-level `hooks:` PreToolUse guard.** The Brief settles that
  *plugin-agent* frontmatter `hooks` are ignored and that `settings.json` hooks still fire inside
  subagent tool calls. What a **skill-frontmatter** hook does when that skill is preloaded via
  `skills:` into a plugin agent is unaddressed. It does not change the verdict (the absent user
  already blocks dispatch), but it is a genuine gap — and it sits in the same unverified family as
  the checklist's `!`-precompute / `allowed-tools` / `${user_config.…}` caution.
- **`/repo-fleet-hygiene:audit` should gain a durable artifact regardless of dispatch.** It returns
  its fleet report inline and persists nothing. Both `review` skills already resolve a findings
  location through the plugin's `topic-docs` binding and write there; the fleet audit has no such
  seam and is the one skill in this batch whose report-shaped output goes nowhere.

## Reference implementation — the `review` plugin's six agents

`plugins/review/agents/` ships `architecture-guardian`, `ci-log-auditor`, `code-reviewer`,
`doc-drift-detector`, `ecosystem-specialist`, and `security-reviewer`. What the existing shape
teaches:

- **No agent declares `skills:`** — corroborating the checklist's amended ruling from the other
  direction. Every review agent carries `Skill` in its `tools:` list, so it *can* invoke a skill,
  but nothing is preloaded; the discipline lives in the agent body as prose. Two consequences worth
  keeping separate: runtime invocation is the marketplace's proven default and should stay so,
  while the "discipline arrives as recall, not content" shape Decision 2 rejected for discovery is
  what a *prose* body produces — an agent body that mandates the Skill call is the reconciliation,
  not `skills:` preload.
- **The frontmatter matches the Brief's acceptance criterion already.** All six declare only
  `name`, `description`, `tools`, `model`, `effort`, `maxTurns`, and `memory` — none declares
  `hooks`, `mcpServers`, or `permissionMode` (the three fields plugin-shipped agents ignore).
  None sets `background:` or `isolation:`, so all six run under the default background posture and
  its narrow tool set.
- **Their `tools:` lists are entirely filter-2 survivors.** `Read, Grep, Glob, Bash, Skill`
  (`ecosystem-specialist` reorders to `Bash, Read, Grep, Glob, Skill`) — every entry survives the
  background filter, so the shape is background-compatible by construction rather than by accident.
  A useful template: a dispatched agent needing only read + shell + skill invocation loses nothing
  to either filter.
- **Model tier is matched to the stage, not inherited.** `opus` for the two judgment-heavy lenses
  (`architecture-guardian`, `security-reviewer`), `sonnet` for the other four; uniform
  `effort: high`, `maxTurns` 25–30, `memory: local`. This is the per-stage tier discipline
  `/session-flow:orchestrate` imperative 7 preaches, applied in a shipped roster.
- **The agent body owns the expensive resolution.** Each agent resolves its own change set inline
  (the `gh pr list --head … --json baseRefName` → `git fetch` → `git merge-base` ladder) rather
  than having the parent resolve and pass it. That keeps raw diff resolution out of the
  orchestrator's window — the same context-economy argument this effort makes — but the ladder is
  duplicated verbatim across four agent files, which is drift-prone.

*Scope note: these findings rest on each agent's frontmatter and opening body section. The agents'
output contracts, severity-vocabulary usage, and report shapes were not audited.*
