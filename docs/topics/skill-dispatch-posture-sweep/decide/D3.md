# D3 — Does a start-of-run user question block dispatch?

**Question.** Many skills open by asking the user something. A subagent cannot ask
(`AskUserQuestion` is filtered out of every non-fork subagent, and inline prose rounds are equally
unreachable). Does that opening question block dispatch, or is it pre-dispatch parent work?

**Recommendation: it is pre-dispatch parent work, and it is not a blocker.** The current criteria
already say the right thing ("needing user input is **not by itself** a blocker … interaction blocks
dispatch ONLY when it is mid-flow load-bearing"), but "mid-flow" is being read as *positional* —
inside the skill's step list — rather than *temporal*. `/discovery:blindspot`'s intake is numbered
step 1, so B03 read it as mid-flow; `/github:audit`'s scope question sits in its step 1 too, and B04
read it as pre-dispatch. Same shape, opposite verdicts, because the criteria never said which
reading is meant. The fix is to replace the positional word with an **information-dependency** test.

## The discriminator

Three cells, decided in order. Only the second and third can block.

### 1. Parameter question — never a blocker

The answer is fully determined by information that exists **before the run starts**: the user's
intent, the invocation arguments, and the conversation so far. Step position is irrelevant; a
question written as "step 1" is still pre-dispatch.

> **Test — could the parent answer this from the user's intent, the invocation arguments, the
> conversation, and at most a cheap bounded pre-flight (a router or config read, a remote lookup) —
> without any of the run's own findings?** If yes, it is a parameter. The parent asks it, fixes the
> answer, and passes it into the dispatch prompt as a stated input.

Scope, target, mode, coverage area, "what do you already know", "which of these areas", and
confirm-before-a-broad-sweep are all parameter questions. So is a confirm gate on an *invocation-time*
flag (`--apply`): the flag is declared before the run, so the gated variant is a different posture,
not a mid-flight branch of the dispatched one.

### 2. Discovered question — blocks only if it steers

The question's **existence or content depends on what the run finds**. The skill cannot know it is
needed, or cannot phrase it, until it has done work, so the parent cannot pre-ask it.

Discovered ≠ blocking. Apply the existing mid-flow test, now unambiguous because it only ever fires
here:

- **Blocks** when deferring stalls the run or lets it continue on an unconfirmed branch — the run
  would pick one of several readings and produce output about the wrong thing.
- **Does not block** when the skill has a documented defer path that *stops and reports* rather than
  guessing: the subagent returns the open question as text, the parent re-surfaces it, no wrong
  branch is taken. A returned question costs one extra round trip, not correctness.

### 3. Elicitation question — blocks when the deliverable is the answer

The user is the **data source**, not the scope-setter: the answers *are* substantive content of the
output, not parameters shaping how it is produced. A skill that transcribes user-held knowledge
(reproduction steps, what they expected, who is blocked) does not stall under dispatch — it
completes and returns a hollow artifact full of placeholders. That is worse than stalling, because
it looks like success.

> **Test — if every user answer were replaced by "unknown", would the deliverable still be the thing
> the skill exists to produce?** If no, and the core fields depend on it, that is a blocker.

Note the placeholder trap: a documented `(unknown — needs confirmation)` fallback reads like the
Brief's degrade path but is not one. The Brief's path defers a *question*; this one ships a *gap*.

### Discharge rules

- Never name the blocker as the absence of `AskUserQuestion` (already in the criteria; B01 and B03
  both violated it). Name the cell above.
- A skill with **no durable artifact** is not thereby INLINE-ONLY. It is a skill change the dispatch
  verdict implies — B04 booked exactly that caveat for `/github:audit` and still said
  DISPATCH-DEFAULT. B03 used the same fact as a second leg for INLINE-ONLY on `/discovery:blindspot`.
  Both cannot be right; the criteria's own signal list makes it a *shape* issue, not a blocker.
- Cell 2 and cell 3 can be **conditional** (only fire on some invocations or some inputs). A gate
  that fires on a subset argues for phase-granularity, already an open item; it does not by itself
  earn INLINE-ONLY when the whole-skill dispatch value is otherwise high.

### Proposed criteria text

Replacing the second half of the "**A live user, mid-flow**" bullet in
[`LEDGER.md`](../LEDGER.md), after the existing
"name the blocker as the absence of a USER" sentence:

> Second — and this is where most over-blocking happens — needing user input is **not by itself** a
> blocker, and **where the question sits in the step list decides nothing**. Classify by information
> dependency:
>
> - **Parameter** — the answer is determined before the run starts (scope, target, mode, the user's
>   starting point, a broad-sweep confirm). Could the parent answer it from intent, arguments, the
>   conversation, and at most a cheap bounded pre-flight — without any of the run's own findings?
>   Then it is pre-dispatch parent work: the parent asks, fixes the answer, and passes it into the
>   dispatch prompt. **Never a blocker**, however early the skill asks it.
> - **Discovered** — the question's existence or wording depends on what the run finds. Blocks only
>   when deferring stalls the run or lets it continue on an unconfirmed branch. A documented
>   stop-and-report path (return the question, parent re-surfaces, nothing guessed) is the Brief's
>   degrade path working as designed — **not** a blocker.
> - **Elicitation** — the answers are substantive content of the deliverable, held only by the user.
>   Blocks when the skill's core output fields depend on them. A `(unknown)` placeholder fallback
>   does **not** discharge this: it ships a gap rather than deferring a question.

### `/github:audit` — DISPATCH-DEFAULT (confirmed), plugin-agent

Every interactive line is a parameter question. "No area given: summarize the router's areas and ask
which to audit" (L18) and "An all-area org sweep requires an explicit user confirm first" (L19–20)
are answerable from `${CLAUDE_PLUGIN_ROOT}/reference/areas.md` plus the user's intent, before any
`gh` call. Step 2's target resolution ("when ambiguous, ask", L27) is the same: the parent can read
the repo remote itself.

Two lines look mid-flight and are not:

- **`--apply`** (L65–76) is "declared at invocation" and "never widens what a bare invocation may do
  mid-flight". Its per-step confirms belong to a different invocation, not to a branch of the
  dispatched bare run.
- **The browser-automation offer** (L92–99) is discovered — the method ladder only lands on a UI-only
  surface by getting there — but the fall-through is report-and-deep-link, and "no browser automation
  fires from this skill on a bare invocation" (L88). Stop-and-report, so cell 2 non-blocking.

Implies a skill change (durable per-area artifact), as B04 already booked.

### `/discovery:blindspot` — INLINE-ONLY → DISPATCH-OPTIONAL, plugin-agent

Step 1 is *"ask the user's starting point first (one question). Blindspot output calibrates to that
disclosure"* (L34–35). Calibration input, asked before the scan and answerable from the user's intent
alone — no pre-flight even needed — so a parameter question, structurally identical to
`/github:audit`'s. B03's stated
blocker was *"an interactive user turn a subagent cannot take (`AskUserQuestion` is filter-1
blocked)"* — the tool-shaped form the criteria already reject on its face.

Nothing else in the workflow steers on findings. The lane choice (L36) follows from the argument and
the intake answer. The escalation (L47–49) is a recommendation, returnable as text. Cards are
"calibrated to their intake disclosure" (L73), and the parent supplies that disclosure verbatim.

B03's second leg — *"there is no artifact to point at"* — is the no-durable-artifact discharge rule
above, and B04 declined to treat the identical fact as a blocker.

**Why OPTIONAL and not DEFAULT.** The gate question decides only that dispatch is *permitted*; the
level is a separate call, and on the criteria's own DISPATCH-DEFAULT signal list blindspot scores one
of five. For it: heavy in, tiny out — the codebase lane reads a whole target area plus git history
and the domain lane fetches docs, while the deliverable is a handful of cards. Against it: the skill
actively refuses a durable artifact (L62–65, L76) because its deliverable is the user's
understanding, and the assembled improved prompt must be relayed verbatim with its
copy-start/copy-end markers — an in-conversation deliverable, which the signal list names as an
argument against DEFAULT. No `-deep` sibling, no context-cost warning of its own, no independence
argument.

The decisive asymmetry against `/github:audit`, whose inputs are `gh` state and fetched docs: what
blindspot works on is *the user's current framing* (L55), and on the common invocation — the user
says what they are about to build, then runs the skill — that framing is resident in the
conversation. Packaging it into a dispatch prompt is lossy in a way scope-passing is not. Inline
therefore stays a legitimate default; `history-fork` is the alternative when the framing is diffuse
and the scan is still worth relocating.

When the parent does dispatch, the prompt must carry: the area/domain argument, the user's intake
disclosure verbatim, and an explicit packaged statement of the framing. Implies a skill change: the
agent persists the card set and returns a path, with the assembled prompt in the final message,
markers intact. Carries the open `!`-precompute-under-preload caveat (branch + project root,
L12–13) — prefer runtime `Skill` invocation.

### `/bug-report:write` — INLINE-ONLY (confirmed), justification replaced

B01's stated blocker was *"Blocker: `AskUserQuestion`"* — rejected form, so the row needs new footing
even though the verdict survives. The real basis is cell 3, reinforced by cell 2:

- **Elicitation.** Three of the five fields — steps to reproduce, expected vs actual, severity — are
  reporter-held knowledge with no other source; the Step 3 table's questions exist to transcribe
  them (L70–76). Replace the answers with "unknown" and the deliverable stops being a bug report:
  the skill's own premise is *"a sharp report captured up front saves the next session from
  re-asking"* (L27). The `(unknown — needs reporter confirmation)` placeholder (L25) is the
  placeholder trap, not a degrade path.
- Step 2's symbol-ambiguity ask (L58) is also discovered, but it is **parent-dischargeable** — the
  survey is a `Glob`/`Grep` plus `git log --oneline -10`, cheap enough to run as pre-flight — so the
  row does not rest on it. The elicitation dependency is what blocks.

Secondary and honest: dispatch value here is near zero — a targeted Glob/Grep plus
`git log --oneline -10`. Nothing to reclaim, so this verdict is low-stakes; **NO-CHANGE** ("short,
conversational") describes it about as well as INLINE-ONLY. Leaving it INLINE-ONLY avoids churn;
either way it is not a dispatch candidate.

### `/planning:draft-goal-condition` — DISPATCH-OPTIONAL (confirmed), plugin-agent

The exemplar for cell 2's non-blocking half. Step 1's doc-fetch-failure branch — *"stop and tell the
user exactly that … Offer the user two ways forward"* (L39) — is discovered (you learn the fetch
failed only by fetching) and reaches the user, but it explicitly forbids continuing on a remembered
limit or shape. That is stop-and-report: the subagent returns the two options, the parent
re-surfaces, nothing is guessed. Not a blocker. Step 0's lever-fit routing (L19–27) is a returnable
recommendation; Step 3's tighten-and-re-run loop (L66) is mechanical.

Inline stays the default on cost, not on interaction: one WebFetch plus a character counter is a
2–3-call run, and the deliverable is a single paste-ready string. B06's reasoning already matches;
recorded here as a confirmation that "asks the user something" and "blocks dispatch" are independent.

## Consequences beyond these four

- Any INLINE-ONLY row whose only stated blocker is a parameter question comes off INLINE-ONLY.
  `/discovery:blindspot` is one; every other row justified as "step 1 asks the user" should be
  re-tested against cell 1 before the criteria are frozen. Note the flip only establishes that
  dispatch is permitted — the DEFAULT/OPTIONAL level is a separate call on the signal list, and
  clearing the gate is not evidence for DEFAULT.
- `/bug-report:write` and the five `re-anchor` rows are a reminder that a *surviving* verdict on
  *rejected* reasoning is still a defect in the ledger — the rationale is what future audits copy.
- Conditional cell-2/cell-3 gates (fire on some invocations only) keep landing in DISPATCH-OPTIONAL
  because the vocabulary has no phase cell. This discriminator sharpens the diagnosis; it does not
  fix that gap.
