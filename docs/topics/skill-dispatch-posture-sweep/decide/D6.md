# D6 — Should `research-deep` and `explore-deep` be retired?

Decided independently. Inputs read: `docs/MIGRATION-PLAYBOOK.md` (126-136), all four discovery
SKILL.md files, `docs/PLUGIN-PHILOSOPHY.md`, `plugins/re-anchor/{README.md,CHANGELOG.md}`, PLAN.md
Brief / Constraints / Decisions / Acceptance criteria, and a scripted reference count.
Excluded by instruction and not read: `verify/reconciliation.md`, `verify/C.md`, and PLAN.md's
"Amendments pending confirmation" / "Deferred questions" sections.

## Recommendation

**Split the verdict. Retire `explore-deep` — conditionally. Keep `research-deep`.**

Retire `explore-deep` **once `discovery:explorer` demonstrably reproduces its project-memory loading
and its sidecar-on-collision behavior.** The condition is not padding: `plugins/discovery/agents/`
does not exist yet (verified — the directory is absent), so the skill being retired is currently a
duplicate of something unbuilt. Deleting it before the replacement covers those two behaviors loses
them silently. See criteria 5 and 6 below.

The two skills are not symmetric, and the single-verdict framing ("retire both / keep both") is what
makes the contested reading of the playbook look necessary. It is not necessary.

## What the convention actually says, and what it protects

`docs/MIGRATION-PLAYBOOK.md:129-136` has three separable parts:

- **R1 (operative rule).** "A structural variant earns a new sibling name; a depth/intensity variant
  takes an argument, never a sibling."
- **R2 (classification).** "Execution tier counts as structural" — topology is not depth.
- **J (mechanism observation).** "...is fixed in frontmatter and cannot be a runtime argument, so it
  earns a sibling."

The retirement-by-reinterpretation argument treats **J as the whole justification**: dispatch becomes
a runtime `Agent()` call, J is falsified, R2 collapses, both siblings are unearned. **That reading is
motivated, on four independent grounds:**

1. **J is subordinate, not the ratio.** The passage's own closing sentence states the operative test:
   "the `-deep` suffix names that isolation tier, not a depth knob on the same execution path — a
   true effort knob on one execution path still takes an argument." The discriminator is
   **same execution path vs. a second execution path**, not **frontmatter vs. runtime**. Runtime
   `Agent()` changes *which mechanism* creates the second path; it does not collapse the two paths
   into one.
2. **J is still literally true for `research-deep`.** Its Tier 1 needs `Workflow`; its multi-topic
   fan-out needs `Agent`. **Note the seam and do not lean on the filter alone:** PLAN.md's own
   Constraints state `Workflow` is unavailable in every non-fork subagent *and* immediately add that
   "the filter argument alone does not cover a fork" — so Filter 1 establishes this for non-fork
   subagents, not for the `fork` subagent type (`/subtask`). The claim carries on two independent
   grounds that do not depend on the filter: the skill asserts the main-context requirement in its
   own voice (`plugins/discovery/skills/research-deep/SKILL.md:18` — "It must run in main context to
   reach the Workflow tool"), and `Agent` errors even inside a true fork, which closes the multi-topic
   path in every dispatched context without exception. So the heaviest tier is *not* runtime-selectable
   from a dispatched context, and the premise that voids the convention is factually false for one of
   the convention's two named examples.
3. **PLAN.md already locked the opposite.** Acceptance criteria: "`research-deep` still dispatches
   Tier 1 from main context (`Workflow` is subagent-unavailable)." Retiring it reverses a settled
   decision on a reinterpretation, not on new evidence.
4. **The reading is load-bearing only for the conclusion it reaches.** The narrower reading below
   retires `explore-deep` and touches zero other plugins. The J-voiding reading retires both and
   requires edits in three other plugins plus two unfixable CHANGELOG citations. When the broader
   premise is required only to reach the broader conclusion, that is the signature.

**What the convention is protecting against** — two failure modes, not one:

- (a) Name inflation: siblings minted for what is really an intensity knob.
- (b) A genuinely different execution topology hidden behind an argument or behind model inference,
  where the user cannot see or reliably select which one they get.

Mechanism-fixedness was the *evidence* offered for (b) at authoring time. The *concern* is selection
legibility. Runtime dispatch changes the mechanism but not the concern: a topology chosen by a model
evaluating a prose rubric is strictly less legible and less reliable than one chosen by the user
typing a different command.

**The correct ground for retiring `explore-deep` is not that the convention is void — it is that the
convention is satisfied by a single skill once the parent absorbs the variant's topology.** A variant
that no longer varies is a duplicate, not a structural variant. That applies R1; it does not override
it. This distinction is the whole decision, because the J-voiding rationale generalizes to every
`-deep` sibling in the marketplace, and the absorption rationale does not.

## Why the two skills are not symmetric

### `explore-deep` — absorbed; retire it

Post-change `/explore` dispatches `discovery:explorer` (plugin agent, `skills:` preload) which runs
the 6 dimensions, writes the `EXPLORE.md` index-plus-sidecars, and returns a pointer plus summary.
`explore-deep` today is `context: fork` + `agent: general-purpose` running the same 6 dimensions,
loading project memory, writing `EXPLORE.md`, returning summary + artifact path + blocking questions.
**There is no user-visible delta left.** Both are "an isolated non-fork subagent runs the explore
workflow; the artifact lands on disk; a summary returns."

Two further facts make keeping it actively harmful, not merely redundant:

- **Its stated precondition is stale.** The description requires `CLAUDE_CODE_FORK_SUBAGENT=1`. Per
  PLAN.md's verified constraints, `context: fork` **is a regular agent type, not a conversation
  fork**; that env var gates the `fork` *subagent type* (`/subtask`). So the skill ships a false
  precondition and, contrary to `SKILL.md:22`'s tool-inheritance implication, has been silently
  taking the narrow background tool set. (Sourced from PLAN.md's this-session verification against
  <https://code.claude.com/docs/en/sub-agents>; I did not independently re-fetch.)
- **Decision 2 already rejected its mechanism** — `context: fork` was rejected for this effort ("no
  per-invocation prompt beyond `$ARGUMENTS`, silent narrow-tool-set trap"). Keeping `explore-deep`
  ships the exact mechanism the effort rejected, beside the replacement for it.

Relocation target already exists in the plan: `explore-deep`'s non-duplicative content (Step 1
project-rule loading, Step 3 sidecar-on-collision, Step 4 return contract) belongs in the
`discovery:explorer` agent definition PLAN.md already requires.

### `research-deep` — not absorbed; keep it

`research-deep` is not a fork. It runs inline in main context and is a **tier selector plus an N-way
multi-topic fan-out**, not a single heavier execution:

| | Needs | Available to a dispatched subagent? |
|---|---|---|
| Tier 1 — workflow engine | `Workflow` | No — Filter 1 for non-fork subagents; the skill states the main-context requirement in its own voice (`SKILL.md:18`). Not established by the filter alone for the `fork` subagent type. |
| Multi-topic fan-out (N ≥ 2) | `Agent` | No — Filter 1, **and** `Agent` errors even in a true fork. No carve-out. |
| Tier 2 — forked subagent | `Agent` from main | Yes, and this is exactly what `/research` now does by default |
| Tier 3 — inline | — | The escape hatch `/research` documents |

Post-change `/research`-by-default is **exactly Tier 2, always** — one point in `research-deep`'s
tier space, not the space. `research-deep` is therefore not absorbed; it retains capability the new
default cannot have and, by the tool filters, cannot acquire.

**Could the tier table be folded into `/research` instead?** Mechanically yes — `/research`'s body
runs in main context and can reach `Workflow`. But it costs more than it saves:

- It makes `/research`'s default **engine-biased** ("prefer the heaviest available tier UNLESS
  clearly small"). PLAN.md's captured assumption authorizes dispatch-by-default with no cost ceiling;
  it does not authorize always-prefer-a-workflow-engine. That is a cost-profile change the user has
  not been asked about.
- It loads the multi-topic decomposition check and the 3-tier table into main context on **every**
  `/research` invocation, to serve the uncommon case. That directly opposes the effort's stated
  primary goal — preserving the main agent's context.
- It replaces an explicit user escalation verb with model inference from a prose rubric on every
  call. Less legible, less reliable — precisely failure mode (b) above.

## Strongest argument against this recommendation

**The suffix becomes incoherent within one plugin.** `discovery` would ship `research`/`research-deep`
but only `explore`. A user who learns from `/research` that `-deep` means "the isolated tier" reaches
for `/explore-deep`, does not find it, and concludes `/explore` is the shallow one — which is exactly
the discoverability harm the convention exists to prevent. The playbook and philosophy both present
the pair as a matched set; halving it leaves the convention with one live exemplar and one dead one.
Clean answers are both-or-neither, and "both" is defensible on symmetry grounds even where it is not
strictly necessary.

**Response.** The objection is real but it is a documentation problem, and the cheaper one. Under the
absorption reading the suffix's meaning is stable and statable in one sentence: *`-deep` names a
second execution topology the parent does not already provide.* `/explore` now provides it;
`/research` does not provide Tier 1 or the multi-topic fan-out. Fixing the docs costs three edits
(below) and touches no other plugin. Retiring both costs edits in three other plugins, two permanently
dangling CHANGELOG citations, loss of the `Workflow` tier and the multi-topic fan-out, and voids a
convention on a premise that is false for one of its two named examples.

**Second-strongest.** `explore-deep`'s `context: fork` may differ from the planned plugin agent in
memory inheritance — its Step 1 asserts a fork auto-loads `CLAUDE.md` while path-scoped rules do not.
A plugin agent has a `memory` frontmatter field (in PLAN.md's verified field list), so the behavior
is reproducible, but this is an assumption, not a verified equivalence. **Make it an explicit
acceptance criterion on the retirement, not a footnote** — see below.

## Does this bind other plugins?

**No. It binds `discovery` only.** The trigger is per-pair and testable:

> A `-deep` sibling retires when the parent skill's new default execution topology is **identical**
> to the sibling's — the variant no longer varies.

True for `explore`/`explore-deep`. False for `research`/`research-deep`. Also false for re-anchor's
`do-your-research`/`do-your-research-deep` and `recheck-against-upstream`/`recheck-against-upstream-deep`,
whose parents gain no dispatch in this effort — their siblings still carry a topology the parent lacks.
The forthcoming marketplace sweep must evaluate this condition **pair by pair**; a blanket "`-deep` is
retired now that dispatch is a runtime call" is the over-reach this decision rejects.
