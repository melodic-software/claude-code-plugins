# D2 — Does dispatching a producer≠critic skill satisfy its own fresh-context requirement?

**Decided independently.** Sources read: `plugins/verification/skills/confirm/SKILL.md`,
`plugins/review/skills/quality-gate/SKILL.md` + all eight `context/*.md`, all six
`plugins/review/agents/*.md` frontmatter, `plugins/review/skills/fanout/SKILL.md`,
`plugins/planning/skills/devils-advocate/SKILL.md`,
`plugins/session-flow/skills/running-retro/SKILL.md`,
`plugins/session-flow/skills/orchestrate/{SKILL.md,context/sources.md}`,
`plugins/docs-hygiene/skills/compress/context/fan-out-orchestration.md`.

## Recommendation

**Yes — dispatch satisfies producer≠critic by construction, for both skills. Overturn the
`quality-gate` NO.** The user's instinct is correct, but "inherently" is the wrong word and one
limit is real and hard. The precise claim that survives:

> Dispatch satisfies the requirement **by construction under a criteria-only envelope**, and the
> dispatched agent should then run the skill's checklist **inline** rather than re-dispatching —
> because it *is* the fresh pair of eyes the inner dispatch existed to obtain.

Call this **hoisting, not nesting**: the parent resolves the mode, picks the specialist agent, and
makes ONE dispatch hop. The inner dispatch the skill mandates is not skipped — it is *satisfied* at
the outer boundary and therefore dissolves.

## Two questions that are not the same question

The prompt asks whether the requirement demands one uncontaminated context or several distinct
lenses. **They are different guarantees, and only the first is what either skill buys.**

| Guarantee | Defeats | Property of | Bought by |
|---|---|---|---|
| **Independence** (producer ≠ critic) | motivated reasoning; approving your own recap | *who* renders the verdict | a fresh context — dispatch delivers this |
| **Decorrelation** (distinct lenses) | correlated blind spots shared across judges | *how many / which priors* examine it | breadth + a different model |

`quality-gate` explicitly buys only the first: *"Depth, not breadth. This skill picks ONE lens per
invocation"* (`SKILL.md:21`), routing breadth to `fanout`. So dispatching it forfeits no lens — it
never had more than one. `confirm` renders one verdict; same shape.

Dispatch also adds **no new correlation**: main(Opus) → sub(Opus) → reviewer(Opus) is exactly as
correlated as main(Opus) → reviewer(Opus). The chain was already same-vendor. Both skills already
name the correct decorrelation remedy and it is orthogonal to dispatch: a cross-vendor reviewer,
presence-gated (`confirm:100`, `quality-gate/context/self.md:5`), with the reason stated plainly in
`fanout:90` — *"its blind spots are uncorrelated with the same-vendor leaf agents."*

**So the "distinct lenses" objection does not survive contact with `quality-gate`.** It survives
against `fanout`, which is a different skill — see "Where the NO belongs" below.

## The in-repo precedent that already decides this

`devils-advocate` states the by-construction principle verbatim (`SKILL.md:31`):

> *"When you were invoked on an artifact this context did not author (a file, a plan from another
> session, a diff), you are already the fresh pair of eyes — proceed directly."*

That is the same rule, already ratified in this marketplace, for a structurally identical
requirement. A dispatched agent is by definition invoked on an artifact it did not author.

Both target skills' own wording binds on **producer identity, not thread depth**:

- `quality-gate/SKILL.md:57` — *"Self mode never runs the checklist on **the producing thread**."*
- `quality-gate/context/self.md:5` — *"**the producing main thread** MUST NOT run the checklist inline."*
- `confirm:100` — *"render `CONFIRMED`/`NEEDS WORK` from **an agent that did NOT produce the artifact**."*

A dispatched fresh agent is not the producing thread and did not produce the artifact. By the
skills' own text, it may run the checklist inline. No amendment to their intent is needed — only
to their assumed *runtime position* (both were written assuming they run on main).

## The limit, and the evidence that forces it

Four limits. Two are hard and cited; two are procedural.

### L1 (HARD) — Freshness is a property of the dispatch *envelope*, not the process boundary

This is the limit the word "inherently" gets wrong. Cited, `devils-advocate:34`:

> *"the dispatch prompt carries only WHAT to investigate ... never your conclusions about it: 'here
> is the target; go look yourself,' not 'here is what I found; confirm it.' **A sub-agent handed the
> parent's verdict inherits the parent's blind spot.**"*

A new context window is necessary but not sufficient. A parent that narrates its rationale into the
dispatch prompt reconstructs the contamination inside the fresh window and buys nothing. `confirm`
already encodes the correct envelope: *"dispatch a fresh-context verifier **with the acceptance
criteria and the diff, withholding your rationale**."*

**Envelope contract (both skills):** mode/criterion (pre-resolved) + diff base + acceptance criteria
or plan path + findings-artifact location. **Never** the parent's reasoning, its expectation of the
outcome, or a summary of what it built and why. Criteria are the spec; rationale is contamination.

### L2 (HARD) — The dispatch target must be able to do what the skill asks of it

Verbatim-verified against <https://code.claude.com/docs/en/sub-agents> and recorded at
`orchestrate/context/sources.md:70-84`:

- *"As of Claude Code v2.1.172, a subagent can spawn its own subagents."*
- Gating: *"listing `Agent` in `tools` lets that subagent spawn nested subagents"*; **"If `Agent` is
  omitted … the agent cannot spawn any subagents."**
- Background depth: *"a background subagent at depth five does not receive the Agent tool and cannot
  spawn further. The limit is fixed and not configurable."*

**Empirically verified in this repo — all six review agents' frontmatter grants
`Read, Grep, Glob, Bash, Skill`. None grants `Agent`.** (`plugins/review/agents/*.md`.)

Consequence, and it is decisive: **dispatching `/review:quality-gate` into any of the six review
agents makes the skill's mandated inner dispatch structurally impossible** — the agent has no
`Agent` tool. A naive "dispatch the skill into `code-reviewer`" therefore *fails* the skill as
written. This is almost certainly what the `quality-gate` audit detected, and it is a real finding.

But the correct fix is not "stay inline." All six agents **do** grant `Skill` — they can invoke the
skill, they just cannot re-dispatch from inside it. So the fix is to hoist: the dispatched
specialist runs the checklist itself, which is exactly what L-precedent (`devils-advocate:31`)
licenses. The tool-grant limit then never binds.

Where a mode genuinely needs a second spawn — `self.md:17` (two parallel axis workers on large
diffs), `restatement.md:20` (per-batch fan-out on large markdown diffs), `confirm:83` (multi-
ecosystem Stage 1) — the dispatch target **must** be `general-purpose` (tools `*`, includes `Agent`)
rather than a review agent, or the parent keeps that fan-out at the outer boundary. Do not author a
tree that depends on a specific depth (`orchestrate` Imperative 5: *"reliability degrades with depth
and platforms cap it, so never author a tree that needs a specific or deep nesting level"*).

### L3 (HARD) — Wholesale dispatch requires every input to be materializable

The general rule, and the one that produces a genuine NO elsewhere:

> A skill may be dispatched wholesale **iff every input its procedure requires is materializable** —
> on disk, in the diff, or statable as criteria. If any required input is a *live property of the
> main agent*, that step cannot be dispatched.

`running-retro` is the counterexample and the proof (`SKILL.md:51-55`, gotcha at `:220`):

> *"The transcript on disk holds what happened; it does not hold the acting agent's present read of
> it. **This note is the only signal the analysis subagent cannot get for itself.**"*
> *"The subjective-state note is mandatory — skipping it discards the one input the subagent cannot
> reconstruct from disk."*

Dispatch `running-retro` wholesale and Step 1 becomes impossible — a fresh subagent has no in-flight
state to introspect. It is already correctly split (main-thread note + dispatched analysis) and
needs no change.

`confirm` and `quality-gate` have no such input **provided intent is materialized**. Both need "what
was the goal?" (`quality-gate` Step 1.2; `confirm` Stage 2.2) and both already specify durable
fallbacks — `self.md:9` reads the plan from `<contract_dir>/<slug>/PLAN.md`; `confirm` passes
acceptance criteria explicitly. Stating criteria is *not* contamination (L1); stating rationale is.
When the goal exists only as unwritten conversation and cannot be reduced to criteria without
narrating rationale, that is the one case to keep on main — rare, and detectable up front.

### L4 (procedural) — A subagent cannot ask the user

`quality-gate` Step 0: *"Ambiguous → present the modes and ask."* `confirm` Stage 2.2: *"If none is
clear, ask the user what the goal was."* Neither is available to a subagent.

Mitigation: the **parent resolves the mode/criterion before dispatching** (it is a one-line decision
from conversation context and costs nothing), and the dispatched agent returns
`BLOCKED: <question>` rather than guessing. Step 4 Handoff and the escalation suggestions stay with
the parent, which receives the findings table and verdict.

### L5 (procedural) — The verify-against-diff hop

`quality-gate` Step 2 rule 2 and `self.md:4`: *"verify each finding against the actual diff (a
subagent's report is synthesis, not evidence) before presenting."* Under hoisting, findings-producer
and findings-presenter collapse into one agent, and the parent cannot re-verify without loading the
diff — which is precisely the context flood we are avoiding.

This is a real but small loss, with two mitigations and an in-repo precedent:

1. **Make findings self-verifying.** Require every finding to carry `file:line` **plus a quoted
   evidence snippet**. The parent then verifies at the moment it acts on a finding — it must open
   that file to fix it anyway — so verification cost is paid only for findings that matter.
2. **Precedent for trading the hop for a conservative action rule:** `compress`'s Phase C accepts
   *"Phase B returns are unverified synthesis — the main session reverts per finding rather than
   verifying each by hand"* (`fan-out-orchestration.md:70`). The hop is not sacred; it is a
   false-positive filter, and a cheap conservative rule can stand in for it.
3. The hop's original rationale was that the orchestrator *had not read the diff*. A hoisted
   reviewer reads the diff first-hand with Read/Grep, so its findings are already primary
   observation rather than synthesis-of-synthesis. The premise weakens as the hop collapses.

## Where the NO belongs — `fanout`, not `quality-gate`

`fanout:86` states, first-party: *"All run on the MAIN THREAD (they fan out their own agents; **a
subagent cannot dependably do that**)."* Read against L2, this claim is now stale in its blanket
form (nested spawning shipped in v2.1.172) but **correct in effect** for the roster it governs: the
orchestrator plugins each spawn their own trees, and `fanout` is the skill whose whole value *is*
several distinct lenses. That is where "must stay inline" is genuinely load-bearing — and it should
be restated as a tool-grant condition rather than a flat impossibility.

The `quality-gate` audit appears to have imported `fanout`'s constraint onto a single-lens skill.
The two audits diverged because `confirm`'s natural worker is a general-purpose agent (which has
`Agent`) while `quality-gate`'s named workers are the six review agents (which do not) — a
tool-grant accident, not a difference in what independence demands.

| **`verification:confirm`** | **YES — dispatchable** (audit confirmed) | One hop into a Bash-capable agent (`general-purpose`, or `review:ecosystem-specialist` when Stage 1 needs no sub-fan-out). Envelope = criteria + diff + mode, rationale withheld. Dispatched agent runs Stage 1 and Stage 2 inline and returns the verdict + evidence-manifest path. Stage 1's build/test output — the single largest context cost in either skill — never reaches main. |
| **`review:quality-gate`** | **YES — dispatchable; overturn the NO** | Parent resolves the mode, then ONE hop into the mode's specialist (`code-reviewer` / `architecture-guardian` / `security-reviewer` / `general-purpose` for `slice`/`restatement`), instructing it to invoke `/review:quality-gate <mode>` via its `Skill` tool. It is the fresh context, so it runs the checklist inline. Returns findings table + verdict + artifact path. |
| **`planning:devils-advocate`** | **YES** — already says so at `:31`; it is the precedent, not an open question. `incumbent` mode's "always dispatch" is satisfied trivially (a fresh agent holds no digest to be biased by). | |
| **`session-flow:running-retro`** | **NO wholesale** — Step 1's subjective-state note is non-materializable (L3). Already correctly split; leave it. Its `arm` mode is the strongest form of the user's priority anyway: an out-of-band observer at *zero* context cost. | |

## Two operating rules that fall out

1. **Dispatch the skill by name; never transcribe it.** Tell the subagent to invoke
   `/review:quality-gate self` via its `Skill` tool rather than pasting the skill's content into the
   prompt. Pasting breaks `${CLAUDE_PLUGIN_ROOT}` expansion (`running-retro:61` — *"a
   `${CLAUDE_PLUGIN_ROOT}` token will NOT expand there"*), drops the `!`-injected pre-computed git
   context, and freezes a copy that drifts from the skill. This is why L2's `Skill`-grant matters as
   much as the `Agent`-grant.
2. **Everything durable already lands on disk.** `self.md:5` requires a findings artifact *even on a
   clean pass*; `restatement.md:39` likewise; `confirm:102` persists an evidence manifest. So the
   return payload to main is a path plus a verdict — dispatch is not just context-neutral here, the
   skills were already built for it.

## Flagged unverified

- **Cross-vendor hop under dispatch.** Both skills prefer a cross-vendor reviewer for high-stakes
  verdicts, and `fanout:86` places the Codex plugin on the main thread. Whether a Bash-capable
  subagent can drive the Codex CLI is **not verified** — the `codex` plugin ships a `codex-rescue`
  agent whose only tool is `Bash` and a `codex-cli-runtime` helper contract, which suggests it can.
  Until someone tests it, route the cross-vendor escalation main-thread. This is the one leg of
  either skill where dispatch may not be free, and it is worth an empirical test rather than a
  standing caveat.
- **`fanout:86`'s blanket claim** ("a subagent cannot dependably do that") predates or ignores
  v2.1.172 nested spawning. Correct in effect for its roster, imprecise as written. Flagging as
  adjacent drift, not fixing (out of D2's scope).
