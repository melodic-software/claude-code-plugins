# D1 — Is nested spawning a prerequisite for dispatching a fresh-context-mandating skill?

Decided in isolation from the reconciliation pass and PLAN's pending-amendments section.

## Recommendation

**Neither rule governs as written; the conflict is an artifact of conflating two different things
nesting buys.** Keep Rule A intact for *throughput* nesting. Reject Rule B's remedy (env var as a
hard dispatch prerequisite) while accepting its diagnosis (silent degradation is real and
unacceptable), and replace it with an **orchestrator-mediated verification hand-off**: when a
dispatched skill mandates a fresh-context step it cannot spawn, it does not run that step at all —
it emits a verification request and the orchestrator dispatches the verifier as a **sibling** agent.

The crux: **independence is a property of context provenance, not of spawn parentage.** A verifier
that reads the artifact off disk has never seen the producing context, regardless of who spawned it.
Nesting is one way to obtain a fresh context; it is not the only way, and it is not what the
correctness control actually requires.

This is not a new construction. `compress` already documents exactly this shape in
`context/fan-out-orchestration.md`, quoted in its own Gotchas: *"the main session dispatches separate
compress + audit subagents, reconciling per finding"* — chosen precisely because *"subagents cannot
reliably spawn the verifier themselves."* The recommendation generalizes existing marketplace
practice rather than inventing a mechanism.

### The distinction that resolves the contradiction

Classify every nested spawn by **what the nesting buys**:

| Class | The child exists to… | Absent nesting | Governing rule |
|---|---|---|---|
| **Throughput nesting** | do N independent units faster, each with identical epistemic standing to the parent | parent does them sequentially — **slower, same coverage** | **Rule A** — optional detected capability |
| **Independence nesting** | be a context that has *not* seen what the parent produced or read (producer ≠ critic) | parent self-critiques — **not slower, weaker; a different and worse control** | **neither** — see below |

Rule A's degradation clause ("slower, same coverage") is factually true for throughput nesting and
factually false for independence nesting. Sequential execution in the producing context is not a
slower version of a fresh-context control; it is the *absence* of that control. That is the real
defect Rule B detected — and it must be fixed regardless of which remedy wins.

### The degradation ladder a correctness-control step follows

1. **Nesting available with sufficient remaining depth** → the dispatched agent spawns its own
   verifier. One round-trip; main sees nothing. Strictly best; keep recommending the env var.
2. **Nesting unavailable** → the dispatched agent **does not self-critique**. It completes the
   producing phase, writes the artifact, and returns `verification: pending` plus a verification
   request (prompt template + artifact path + what to refute). The orchestrator dispatches the
   verifier as a sibling of the producer and merges the verdict. Main's context cost is verdict
   tokens and paths, never the corpus.
3. **Sibling split genuinely impossible** (the control needs mid-run state that never lands on disk)
   → *then* the skill declares nesting a hard prerequisite, and on its absence either runs inline in
   main (paying the context cost knowingly) or aborts with the remediation. It **never** runs
   dispatched-with-self-critique.

Neither row under decision here reaches rung 3. Both artifacts are (or become) files on disk, which
is exactly what makes the sibling split available — a direct consequence of Decision 5's
"the ledger must be a file."

### Detection belongs to the dispatcher, not the dispatchee

Neither rule states this, and it is load-bearing. Reading
`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` yields the session **ceiling**, not an agent's **remaining
budget** — a dispatched agent cannot compute its remaining depth because it does not know how deep it
already sits. Only the orchestrator knows.

So: the parent resolves the capability and passes it down as an explicit fact in the dispatch prompt
("you may spawn subagents" / "you may not spawn subagents — return verification requests instead").
The child never detects, never guesses, and never silently discovers the `Agent` tool missing.

Corollary: **depth is a budget, not a boolean.** "Is the var set?" is the wrong predicate; the
predicate is "is the remaining budget ≥ what this dispatch needs." A design that branches on presence
is wrong even on its own terms.

## Evidence

**Official docs** — <https://code.claude.com/docs/en/sub-agents>, "Let subagents spawn their own
subagents", fetched this session:

> By default, a subagent can't spawn subagents of its own… While nesting is off, Claude Code
> withholds the `Agent` tool from every subagent except a fork, which inherits the parent's full tool
> list. `Agent` stays in that list, but returns an error instead of spawning.

> To allow nesting, set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` to the number of subagent layers you
> want below your main conversation.

> From Claude Code v2.1.172 through v2.1.216, subagents could nest by default, up to five layers
> deep, and the limit couldn't be changed.

Installed version is **2.1.219** (verified: `claude --version`) — past that window, so nesting is
**off by default** here. The version history is itself an argument against a hard prerequisite: a
verdict pinned to this capability was silently true across a four-dozen-release window and became
false without any skill changing.

**Environment, this machine** — `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` is `"5"` in
`~/.claude/settings.json` and reads back as `5` from a Bash call. *Caveat on the evidence:* that read
was performed from an **agent-team teammate**, not from an Agent-tool-spawned subagent. Env is
process-level so visibility is near-certain in both, but the empirical confirmation is one step
removed — flagged rather than asserted.

**Inference, not a stated rule:** the docs give one worked example ("this entry… allows two layers:
`2`") and no explicit counting rule. From it I infer a dispatched agent at layer 1 needs a ceiling of
**≥ 2** to spawn its own verifier, and `audit-derivability`'s `sweep` (dispatched agent → per-doc
agent → spot-test) would need **≥ 3**. Treat both as inference; the recommendation does not depend on
them, because under sibling mediation the required depth is **0**.

**Repo evidence** — every skill in scope states its control in correctness terms, not speed terms:

- `compress/SKILL.md:97` — *"Self-audit drifts toward EXPANSION… self-audit re-adds words just
  removed."* Observed rate: **4/4 reverse-direction edits in one batch compression wave.** Same line
  already concedes *"subagents cannot reliably spawn the verifier themselves"* and routes to the
  main-session sibling recipe.
- `audit-derivability/SKILL.md:56,119` — the spot-test must be a *"fresh-context, non-fork subagent…
  that has NOT seen the document"*; named failure mode is **"the self-grade trap."**
- `plan/SKILL.md:128` — *"The producing main thread MUST NOT self-attack the plan inline… the model
  that just wrote the plan rubber-stamps it."*
- `audit-answers/SKILL.md:49` — *"A fork inherits this session's reasoning and would carry its bias
  forward… this is the self-grade fresh-eyes rule the marketplace mandates for any step that judges
  its own context's work."*
- `audit-instructions/SKILL.md:112` — *"this is a self-grade of the audit's own proposals, so a fork
  that inherits the producing context would not be independent."*

Every one of them names **contamination of the producing context** as the failure. None names spawn
parentage. That is the textual basis for the provenance-not-parentage rule.

## Alternatives rejected

**A. Rule B as written — env var is a hard prerequisite; without it the skill stays INLINE-ONLY.**
Rejected on four independent grounds.

1. It inverts the user's stated primary design constraint (preserve MAIN context; dispatch unless
   there is a real reason it cannot) to solve a problem that has another solution. `audit-instructions`
   sweeping every instruction surface in main context is precisely the flood the effort exists to stop.
2. **A verdict that flips on an operator env var is not a verdict — it is a runtime branch.** The
   marketplace ships one contract to many machines; under Rule B `audit-instructions` is
   DISPATCH-DEFAULT on a machine with the var and INLINE-ONLY on one without. Ship the branch in the
   design, not two verdicts in the ledger.
3. Depth is a budget, so "set" is the wrong predicate (above).
4. Env vars are read at session start, so a skill that discovers the prerequisite unmet cannot
   remediate within the run — the "prerequisite" is unactionable at the moment it binds.

**B. Rule A applied unchanged to correctness fan-out.** Rejected as factually false: "slower, same
coverage" does not describe the loss. This is the silent degradation the question names, and it is a
real defect in Decision 3's current wording regardless of which remedy is adopted.

**C. Relax the skills' controls to "prefer fresh, allow self-critique when unavailable."** Rejected:
it trades an empirically measured failure rate (compress's 4/4) for token savings without surfacing
the trade, and it deletes the one property that makes a dispatched verify-shaped skill *better* than
its inline form — the checklist's own DISPATCH-DEFAULT signal, *"a verify/review-shaped skill that
requires producer ≠ critic satisfies that invariant by construction when dispatched."*

**D. Use a `fork` to get around the filter.** Doubly wrong: the docs say `Agent` in a fork *"returns
an error instead of spawning"*, so it does not restore the capability; and a fork is a contaminated
context by construction — the exact opposite of what a fresh verifier must be.

**E. Have `discovery:setup` (or any skill) set the env var.** Out of bounds — that is the operator's
settings file, chezmoi-tracked here — and inert until the next session anyway. Recommending it stays
correct; requiring it does not.

## What changes for the two rows

Both rows **stay `DISPATCH-DEFAULT` / `plugin-agent`.** What changes is the *blocker reasoning* and
the per-row condition: from "needs nested spawning" to "needs a verification hand-off contract."

### `claude-config:audit-instructions`

Two fan-outs of different classes, and the row must stop treating them alike:

- **Phase B, per-surface lanes** (`SKILL.md:92`) — *throughput* nesting. Each lane audits an
  independent surface; nothing there judges the dispatched agent's own output. **Rule A applies
  unchanged**: absent nesting the agent walks surfaces sequentially — slower, same coverage. Not a
  condition on the verdict.
- **Phase C, verify pass** (`SKILL.md:112`) — *independence* nesting, self-declared. Under the
  hand-off contract the dispatched agent does **not** run it. It writes its proposals to the report it
  **already persists** (`${CLAUDE_PLUGIN_DATA}/audit-instructions/last-audit.md`, `SKILL.md:126`) and
  returns `verification: pending`. The orchestrator dispatches one sibling verifier **per surface**
  (the skill's own batching, `SKILL.md:120`) against that path with the refute prompt; each returns a
  defended/dropped verdict list. Main sees ~5–8 verdict blocks, never the instruction corpus.

This row needs **no nesting at all** under the recommendation — the disk hand-off it requires already
exists today.

Unchanged and still owed (B01 caught it): the *"before the total dispatch count… would exceed ~20,
confirm with the user first"* gate (`SKILL.md:107–108`) cannot ask from inside a subagent. The parent
pre-authorizes a dispatch budget in the dispatch prompt, and the same budget now also covers the
sibling verifiers it will fire itself.

### `docs-hygiene:audit-derivability`

The existing condition stands unchanged: the row is DISPATCH-DEFAULT **conditional on the skill
gaining a durable ledger artifact**, since today the verdict ledger *is* the returned deliverable and
pointer-plus-summary is incoherent without a file. The nesting caveat, however, is retired.

Its spot-test independence is *stronger and differently shaped* than the others: the verifier must not
have seen **the document**, not merely the producer's reasoning. Sibling mediation satisfies this more
cleanly than nesting does, because the orchestrator hands the spot-tester a derivation question and
never the doc path. Three-phase choreography, since the comparison needs both conclusion sets and the
producer may have exited:

1. **Producer** (dispatched sweep agent) writes each document's load-bearing conclusion list into that
   document's sidecar, then emits a spot-test queue — one entry per gated document, each carrying the
   derivation question and the sidecar path, with the document path withheld from the tester.
2. **Spot-tester** (sibling `Explore`, dispatched by the orchestrator per queue entry) explores
   natively and writes its independently derived conclusions to a second file. It returns a path.
3. **Comparator** (one cheap sibling, or the orchestrator when the pair is short) reads both files and
   emits `converged` / `diverged` plus the count. Main sees the token, never either list.

**Queue bound** — the discriminating cost question, made to hold by contract two ways: every verifier
returns a verdict token plus a path, never prose; and the spot-test is already **stakes-gated by the
skill itself** (`SKILL.md:58`: *"skip it for an obviously trivial derivable file… run it whenever
being wrong about the deletion costs a reader something real"*). The queue is therefore the
load-bearing subset of a `sweep`, not one entry per document.

Required depth drops from an inferred **3** to **0**.

## How a skill expresses the requirement so it degrades honestly

A uniform block in any SKILL.md whose contract mandates a fresh-context step. The capability's absence
changes **who dispatches the verifier — never whether the control runs.**

```markdown
## Dispatch contract

- **Independence-critical step:** <step name> — fresh-context, non-fork; producer ≠ critic.
- **Dispatched, may spawn:** run the step in-agent as today.
- **Dispatched, may not spawn:** do NOT run the step. Write the artifact, set
  `verification: pending` in the index header, and return a verification request —
  refute-prompt, artifact path, and the unit to batch by. The orchestrator dispatches
  the verifier as a sibling and merges the verdict.
- **Never** run this step inside the producing context. An artifact whose `verification`
  field is not `passed` is not shippable, and a consumer MUST treat it as unverified.
- Spawn capability is stated by the dispatcher in the dispatch prompt. Do not detect it:
  the env ceiling is not this agent's remaining budget.
```

Three properties make this honest rather than merely graceful:

- **The absence is announced, never absorbed.** The capability gap surfaces as a structured
  return value the orchestrator must act on — it cannot be quietly satisfied by self-critique.
- **The artifact carries its own status.** `verification: pending | passed | failed` rides in the
  Decision-4 index header (index only — the sidecars do not restate it), so a downstream consumer
  physically cannot mistake an unverified ledger for a verified one, including across sessions.
- **The control's cost is paid, not skipped.** Rung 2 is slower in wall-clock than rung 1 by one
  orchestrator round-trip. That is the honest price of the missing capability — and it is a
  *latency* cost, which is what Rule A always promised, rather than the *correctness* cost Rule B
  correctly refused to accept.

## Consequent edit to Decision 3

Decision 3's resolution is right about throughput and over-general about correctness. It should read
(shape, not final wording): `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` is an optional detected capability
for **throughput** fan-out — absent it, the dispatched agent goes sequential: slower, same coverage.
For an **independence** fan-out it is an optimization only: absent it, the dispatched agent does not
self-critique but returns a verification request the orchestrator dispatches as a sibling.
The capability is resolved by the dispatcher and stated in the dispatch prompt, because the env
ceiling is not the child's remaining budget.

Also worth propagating: the audit checklist's hard-blocker bullet *"Its own `Agent` fan-out, when the
skill mandates fresh-context subagents as a correctness control"* is no longer a blocker on its own.
It becomes a **dispatch condition** — the row needs a hand-off contract and a durable artifact. Rows
where the recursion note was the *only* recorded blocker should be re-examined against that.
