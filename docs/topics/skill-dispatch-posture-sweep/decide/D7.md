# D7 — Dispatch granularity: whole-skill or phase-level

Decided in isolation. Inputs read: `discovery/skills/research`, `discovery/skills/explore`,
`event-storming/skills/simulation`, `kindle-dedrm/skills/manage`, `code-tidying/skills/tidy`,
`plugin-quality/skills/audit`, `plugin-quality/agents/auditor.md`, PLAN.md Brief §Constraints +
§Decisions (1–6), and the sweep ledger `LEDGER.md`.
Deliberately not read: `verify/reconciliation.md`, PLAN.md §Amendments pending confirmation.

## Recommendation (short form)

**Go phase-level.** The dispatch unit is a phase; the whole-skill verdict becomes a *roll-up* of its
phases, so the 138-row ledger survives as an index rather than being rewritten. No new frontmatter,
no harness dependency: two shipped declaration shapes already exist in this marketplace and both are
sufficient — an **Execution-site column on the action-router table** for argument-selected splits
(`kindle-dedrm:manage`, `code-tidying:tidy`, `event-storming:simulation` all already carry the
table), and a **per-step execution-site annotation plus a handoff contract** for sequential splits
(`plugin-quality:audit` steps 2–3 → `plugin-quality:auditor`, shipped and working).

For `/discovery:research`: **one dispatched work span covering Phase 0 through Phase 4 and the six
mechanical outcome-gate criteria**, with the parent keeping topic resolution at the front and
presentation / user-surfacing at the back. The gate's two judgment criteria leave the producer:
**project fit goes to the parent** (it holds the conventions and the live task) and **the
confidence criterion goes to a parent-dispatched sibling verifier** that reads only the artifact set,
because self-grading the bar you just satisficed is worth close to nothing.

---

## 1. Why whole-skill granularity is not merely imprecise — it inverts the stated priority

The design constraint is explicit: preserving MAIN agent context is the primary goal; anything that
would flood main context should dispatch unless there is a real reason it cannot.

Whole-skill granularity resolves a mixed skill by taking the **most restrictive** phase and applying
it to the whole file. Every hard blocker in the audit criteria is a *phase property* — a live user
mid-flow, a terminal that moves the invoker's session, `Workflow`, a Task-tool write, an irreversible
action. A single such phase stamps the skill INLINE-ONLY, and the skill's genuinely context-heavy
phases keep flooding main context forever. That is not a loss of precision at the margin; it is the
vocabulary systematically producing the answer the primary constraint forbids.

The sweep already measured the exposure:

- **57 INLINE-ONLY rows (41%)**, at least 4 of which the normalization pass itself flagged as
  containing a "clearly dispatchable sub-action" — `event-storming:methodology --<format>`,
  `event-storming:simulation --discover-bcs`, `firecrawl:update --check`, `kindle-dedrm:manage
  update`. Those four are not edge cases; they are the shape.
- **29 DISPATCH-OPTIONAL rows (21%)**, which the ledger's own open-items section says are being
  "stretched to carry *dispatch this phase, keep that one*."

So the question is not "does phase-level add enough precision to justify complexity." It is: the
whole-skill model cannot express the answer for roughly a third of the corpus, and the errors it
makes all fall on the wrong side of the primary constraint. Phase-level is the minimum expressive
power the locked goal requires.

Weighing the counter-argument honestly: phase-level does cost more per skill to author, review, and
keep honest, and it creates a new failure mode (a run that crosses the boundary and loses state at
the handoff). Section 3's crossing budget is the control for that, and section 2's roll-up is what
keeps the existing ledger from being invalidated. The complexity is bounded and paid only by mixed
skills; the whole-skill model's cost is unbounded and paid by main context on every invocation.

## 2. Vocabulary

### 2a. Two distinct splits — do not conflate them

The four example skills demonstrate two structurally different things, and they need different
declaration and different verdict semantics:

| | **Action split** | **Phase split** |
|---|---|---|
| Shape | Disjoint entry points; the router selects one, only one runs | Sequential steps; a single run passes through both sites |
| Examples | `manage update` vs `cleanup`; `tidy dry-run` vs full run; `simulation --discover-bcs` vs `--simulate` | `plugin-quality:audit` steps 1→6 |
| Verdict attaches to | the action | the step |
| Boundary cost | **zero** — no handoff; the posture is chosen at invocation | one handoff (prompt out, return in) per crossing |
| Declaration | Execution-site column on the existing router table | Execution-site annotation on the step heading + handoff contract |

Action splits are close to free and should be applied liberally. Phase splits carry real cost and
need a budget. Collapsing both into one word is what makes phase-level *look* expensive.

### 2b. Phase-level verdicts

Per phase (or per action), one of:

- `dispatch` — this phase runs in a subagent. Names the mechanism (the existing four-mechanism
  vocabulary is unchanged: `plugin-agent` / `context-fork` / `inline-dispatcher` / `history-fork`).
- `inline` — this phase stays in the invoker's context. **Must name the blocker**, from the existing
  hard-blocker list plus one addition (below). An `inline` phase with no named blocker is a defect.
- `either` — genuinely runtime-conditional (context zone, task size, whether the user is present).
  Reserved; see 2d.

### 2c. One blocker category to add

The existing hard-blocker list has "a terminal that must move the invoker's own session (worktree
entry, plan-mode transition, session handoff)." That is the *mutation* form of a more general
category. The *observation* form is missing and is load-bearing for `/discovery:explore`:

> **The invoker's own session is the subject of the phase.** A subagent's probe reports the
> subagent's environment, not the parent's. `/discovery:explore` dimension 6 says "MCP server
> status — test with a read-only call before depending on it": run from a background subagent, that
> tests a tool pool the background filter has already narrowed, and answers a question about the
> wrong session. Same for the parent's own permission mode and available tool set.

Stated as a rule: **a phase whose observable or whose mutation is the invoker's own session state is
`inline`.** Both directions of the same blocker; state it once and stop writing the mutation form
alone.

### 2d. Skill-level roll-up — derived, not authored

The four existing skill verdicts are kept as an index over the phase verdicts. Only one cell is new:

| Roll-up | Definition |
|---|---|
| `DISPATCH-DEFAULT` | every phase is `dispatch` |
| **`DISPATCH-SPLIT`** *(new)* | some phases `dispatch`, some `inline` — the missing cell |
| `DISPATCH-OPTIONAL` | at least one phase is `either`, and it is a **runtime** condition (context zone, task size, user presence), not a phase distinction. This narrowing is the point: it stops being a shrug bucket |
| `INLINE-ONLY` | every phase is `inline`. Now a genuinely strong claim, since one blocked phase no longer earns it |
| `NO-CHANGE` | short, conversational, or already dispatching |

The ledger's Verdict column keeps its shape and gains one value, and only rows whose phases actually
differ need a phase table. The 29 `DISPATCH-OPTIONAL` rows re-sort into `DISPATCH-SPLIT` (most, on
the evidence) and a much smaller, honest `DISPATCH-OPTIONAL`. The 4 named INLINE-ONLY rows become
`DISPATCH-SPLIT` by action split.

**Do not under-price this.** `INLINE-ONLY` is *redefined* here — from "has a blocker" to "**every**
phase is inline." All 57 existing `INLINE-ONLY` rows were justified at whole-skill granularity
against the old definition, and none has been tested against the new one. The renorm pass is the
warning: of 15 rows re-tested there, 8 kept their verdict while their stated justification was
replaced, narrowed, or voided. The same is likely here, except the definitional change is sharper
and the exposure is 57 rows, not 15. Two honest options for the plan step — pick one explicitly:

- **Re-test all 57** against "every phase," accepting the cost. Cheaper than it sounds per row
  (the question is only "does this skill have a context-heavy phase the named blocker doesn't
  touch?"), but it is 57 rows, not 4.
- **Grandfather** the existing `INLINE-ONLY` verdicts under the old definition, with an explicit
  re-test trigger recorded on the ledger (next time the skill is edited, or before any work is
  planned against that row). Cheap now, but every grandfathered row is a known-unaudited claim and
  must be labeled as one.

What is genuinely a re-derivation over existing rationale is the 29 + 4 rows in §7 item 4. The 57 is
a separate, larger decision that adopting §2d forces.

## 3. Declaration mechanism

**No frontmatter field.** The harness has no per-phase dispatch field; inventing one produces an
inert key that silently misleads — exactly the failure the Brief's version-floor section is written
against. Declaration is prose contract in the SKILL.md body, which is where the shipped precedent
lives.

### 3a. Action splits — one column

Add an **Execution site** column to the action-router table the skill already has:

| Action | Execution site | What it does |
|---|---|---|
| `update` | `dispatch` (plugin-agent) | drift check, no mutations |
| `cleanup` | `inline` — per-item irreversible confirmation | reverses every mutation |

Cost: one column in a table that already exists in every multi-action skill examined.

### 3b. Phase splits — annotate the heading, contract the boundary

Copy `plugin-quality:audit` verbatim in shape. It already does all four things a phase split needs,
and it is the only shipped example, which is itself the argument for copying rather than inventing:

1. **Every step heading names its site** — `### Step 1 — Evidence capture (main thread, always)`,
   `### Step 2 — Map + ground (fresh auditor subagent — never a forked context)`. The site is
   declared where the reader already is; no separate registry to drift.
2. **The dispatch prompt is specified as paths, not pasted content** — packet path, target, lens
   file paths. This is what makes the crossing cheap and is the reason the auditor can work at all
   without inheriting history.
3. **The return is contracted to a summary form** — "finding count by severity, top findings one
   line each, and the packet path." Bounded return size is the whole point of dispatching.
4. **The durable artifact is the handoff, not the return** — `findings.md` is written into the
   packet by the agent; the parent reads it on demand, or not at all in the degraded zone.

One flaw in the precedent to fix while copying it: the input contract is stated **twice** — in
`skills/audit/SKILL.md` step 2 (packet path, target, lens files) and again in `agents/auditor.md`
("everything you need arrives in your dispatch prompt: the evidence-packet path, the audit target,
and the component-type lens file path(s)"). Two copies of one contract is a drift surface. **The
agent file owns the input contract**; the dispatching step points at it and names only what varies
per invocation.

Add one thing the precedent leaves implicit: **a named fallback per dispatch step** for when the
mechanism is unavailable (env var unset, `disable-model-invocation: true`, no nesting depth). The
sweep already found that "graceful degradation" is false for fresh-context verification disciplines —
running sequentially is not a substitute for running uncontaminated — so the fallback must sometimes
be *stop and say so*, not *inline*. Each dispatch step declares which.

For skills with more than two steps, a compact **Execution sites** table near the top of the skill,
generated from the headings, gives the reader the split at a glance without hunting.

### 3c. Crossing budget — the control on complexity

**A run gets at most one work span plus at most one verification span.** Contiguous dispatchable
phases group into a single dispatched span; a skill needing two or more *work* spans is a signal it
is two skills sharing a file, and should be said so rather than paying the handoffs.
`plugin-quality:audit` has exactly one work span (steps 2–3) and no verification span.

The verification span is carved out on principle, not as an exception: its input is the **artifact**
the work span produced, never the corpus, so its cost is bounded by construction and does not scale
with the research. That property is also what makes it independent — a verifier that had to re-read
the corpus would be re-doing the work, not checking it. A span that cannot state its input as "the
prior span's artifact" is a work span and counts against the budget.

This rule is what keeps phase-level from becoming per-step micro-dispatch, and it does most of the
work of answering "is the complexity justified" — the declaration is one column or a heading suffix,
and the run shape is capped at one out-and-back.

### 3d. Enforceability

The heading annotation and the router column are regex-checkable, so `skill-quality:check` can gate
them: every step heading in a skill with a phase split carries a site; every `inline` phase names a
blocker; every dispatch step names a mechanism and a fallback. Without that, phase annotations rot
into decoration.

## 4. `/discovery:research` — phase-by-phase

`/research`'s roll-up becomes **`DISPATCH-SPLIT`**, not `DISPATCH-DEFAULT`. Under the crossing
budget it is one dispatched span, plus one sibling verifier dispatch, plus two thin parent ends.

| # | Phase | Site | Reasoning |
|---|---|---|---|
| A | Topic resolution + dispatch-prompt composition | **parent (inline)** | The skill says "if no specific topic was provided, infer the research topic from the current conversation context." That input *is* the conversation; a fresh-context agent cannot see it, and `history-fork` — the only mechanism that could — costs in proportion to transcript length and would import the flood we are trying to prevent. The parent resolves the topic, then composes a **self-contained** prompt (topic, version pins, the consuming project's convention-file paths, the memory-slice path, the corpus definition if the user named one). Cost: tens of tokens. This phase is small precisely because it hands over *paths, not pasted content*. |
| B | Phase 0 — corpus enumeration + `research-checklist.md` | **dispatch** (span start) | Enumeration is `llms.txt` / sitemap / registry / release-index reads — fetch-heavy, mechanical, and its output is a ledger file, not a decision. Decision 6 already requires it to be written before any query, which makes it the natural head of the span: the agent's first act is to write its own durable state, which is also its compensation for having no Task tools. |
| C | Phase 1 — broad (≥3 queries, ≥3 tool types) | **dispatch** | The single largest context flood in the skill: SERP results plus full page bodies the parent never re-reads. This is the phase the primary constraint exists for. |
| D | Phase 1 output — written analysis block (hypothesis, numbered gaps/conflicts, tool-diversity audit, recency status, falsification candidate) | **dispatch — stays in the span** | Tempting to surface, because it is small and readable. Do not: it is *input to Phase 2*, and discipline 9 makes the chaining mechanical ("each Phase 2 query maps to a named entry in it"). Handing it to the parent and back would cost a crossing to buy a preview of a list that the final artifact carries anyway. Write it to the artifact set; the parent reads it on demand. |
| E | Phase 2 — targeted + mandatory falsification | **dispatch** | Same flood profile as Phase 1, and it consumes D's list directly. Splitting here would force re-serializing per-claim tier/diversity state across the boundary — pure cost. |
| F | Phase 3 — preferred sources / tool-ecosystem fallback | **dispatch** | Same. Note discipline 4 (4+ distinct tool types *across* the topic, phases cannot share the same 3 end-to-end): cross-phase tool diversity is state that only exists inside one continuous run. This is an independent reason the three research phases must be **one agent, not three**. |
| G | Phase 4 — conditional follow-up | **dispatch** | It is the remedy branch of the gate below. It has to be inside the loop, because "iterate until HIGH confidence" means *run more queries*, which only the agent is positioned to do. |
| H | Outcome gate, criteria 1–6 (mechanical) | **dispatch — loop-exit condition, emits a receipt** | See §5. |
| I | Artifact write — index + sidecars + `research-checklist.md` + gate receipt | **dispatch (span end)** | Decision 4's index-plus-sidecars shape. The agent returns a pointer and a one-paragraph summary; the bulk lands on disk. |
| J | Outcome gate, criterion 7 (every claim HIGH confidence) | **verification span — fresh agent, parent-dispatched sibling** | See §5. Needs the sidecars read against the claims, which is why it cannot be the parent's. |
| K | Outcome gate, criterion 8 (project fit) | **parent (inline)** | Needs the consuming project's convention files and the live task — both of which the parent already has, and neither of which the researcher was pointed at. Parent-held regardless of whether the verifier in J exists. |
| L | Presentation, Gaps + open questions to the user, decision hand-off | **parent (inline)** | `AskUserQuestion` is filter-1 blocked in every non-fork subagent, and the Brief's degrade path is exactly this: return questions as text, parent re-surfaces. The skill's own boundary ("does not make decisions") means the terminal step was always the parent's. |

Roll-up: `DISPATCH-SPLIT`, mechanism `plugin-agent` (`discovery:researcher`) for the work span B–I,
plus a second `plugin-agent` (`discovery:research-verifier`) for the verification span J.

### 4a. Consequence for the skill's own Tier rule

Line 148 currently reads "Subagent returns are Tier 3 (synthesis), not corroborators, until their
cited primaries are fetched this turn." Under dispatch-by-default that makes the parent's entire view
Tier 3 by the skill's own rule — the ledger flags this as an open item, and this split resolves it
rather than inheriting it:

> **Tier is a property of the source a claim cites, not of the transport that carried it.** A claim
> whose primary was fetched *inside the dispatched run*, with URL and fetch timestamp recorded in the
> artifact, is Tier 0/1 — the fetch happened this turn, in this task, by this skill. What is Tier 3
> is a subagent's **prose summary read in place of the artifact**. The artifact is the evidence; the
> return message is a pointer to it.

That distinction is what makes dispatch-by-default coherent with the tier discipline, and it is why
§5's receipt check is about *artifact locators* rather than about trusting a summary.

## 5. The outcome gate — the substantive question

Asked directly: is a self-check run by the same agent that did the work worth anything, or must the
parent hold it?

**Answer to the binary as posed, before I complicate it:** mostly the agent, partly the parent, and
neither of them for one criterion. Criteria 1–6 are worth real money run by the producer, because
they are artifact-readable and the producer is the only party who can act on a FAIL. Criterion 8 is
the parent's outright. Criterion 7 self-graded is worth close to nothing — that is the one that
needs a third party, and §5's closing paragraph says what to do if the plan step declines to add one.

**So the gate is two different things wearing one heading.** The
skill's own text half-concedes this — "The same model that satisficed the bars runs this check, so a
self-congratulatory recap rubber-stamps shallow work. Only artifact-grounded binary criteria bite."
That sentence is the skill trying to buy independence with binariness. It partly works, and where it
works is exactly separable from where it does not.

**Criteria 1–6 are mechanical.** "Every claim row has ≥1 Tier 0/1 source whose URL/command was
captured THIS turn." "Every Phase 2/3 query traces to a numbered gap in a written block." "The
falsification query ran and is recorded." "Latest changelog fetched this turn." These are read off
artifacts — the evidence table, the gap lists, the fetch log — and the FAIL remedy for every one of
them is *run another query*. Only the agent can do that. Moving these to the parent would mean the
parent fails the run and then has no way to fix it except re-dispatching a whole research pass over a
single missing fetch. **Keep them in the agent, as the loop-exit condition** — that is the correct
home, and it is not producer-grading-itself in the vicious sense, because these criteria are
checkable against an artifact by anyone, and the agent is merely the party positioned to act.

Make them auditable rather than assertable: the gate emits a **receipt table**, one row per
criterion, each citing the concrete locator that satisfies it (file+anchor, URL+fetch timestamp,
command). A bare "PASS" is not a receipt. Several criteria are additionally scriptable (row counts,
presence of a timestamped URL per claim row, query-to-gap-number mapping); script what can be
scripted, per the deterministic-work discipline, so those rows are computed rather than judged.

**Criteria 7 and 8 are both judgment, but they fail differently and go to different places.**

**Criterion 8 — "project fit against the consuming project's conventions and stated direction" — is
the parent's, unconditionally.** It needs two things the researcher never had: the consuming
project's convention files, and the live task. The parent has both already, at no marginal context
cost. This assignment does not depend on the verifier existing and should be made regardless.

**Criterion 7 — "every accepted claim is HIGH confidence" — is the hard one.** It is precisely the
bar the producer satisficed while producing; asking the producer whether it was confident enough
re-asks the question it already answered by acting. But it is also not the parent's: judging it means
reading the sidecars against the claims, and pushing that into main context destroys the primary
constraint — while nodding at a summary instead is the same rubber stamp with a different signatory.
Criterion 7 is the one criterion whose correct holder is a **third party that is neither producer nor
context-flooded**:

- **J — `discovery:research-verifier`, a fresh plugin agent dispatched by the parent as a *sibling*
  after the researcher returns.** It reads only the artifact set (index + sidecars + checklist + gate
  receipt) — never the corpus — and returns a short verdict: confidence assessments it disputes,
  claims whose cited support does not carry the weight put on it, and gaps laundered into findings.
  Bounded input, bounded output, zero corpus in main context. This satisfies producer ≠ critic by
  construction, which the sweep already recognizes as a *correctness* argument for dispatch, not
  merely a token-cost one.
- **Sibling, not nested — deliberately.** A verifier spawned *by* the researcher needs
  `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`, which Decision 3 keeps optional, and the sweep's own
  finding is that graceful degradation is false for fresh-context verification: running the check
  inside the producer sequentially is not a slower substitute, it is a *different and worse* check.
  Dispatching the verifier from the parent removes the env-var dependency entirely. This is the
  single most important structural point in this section.
- **The parent's own share is a receipt check, not a re-judgment.** The parent reads the index and
  the gate receipt — a few hundred tokens — and checks falsifiable properties: the receipt exists;
  every criterion row cites a locator rather than an adjective; the claim count in the index matches
  the evidence-table row count; Gaps are either populated or explicitly asserted empty; the
  verifier's verdict is present and its disputes are either resolved or surfaced. The threat model
  here is not a lying agent, it is a **satisficing** one that writes PASS without the artifact — and
  a locator-presence check catches exactly that at negligible cost.

So the gate splits three ways by *who can act on a FAIL*: the agent owns what only more queries can
fix (1–6); a fresh sibling owns what only independence can fix (7); the parent owns what only the
live task can fix (8), plus the receipt check over the whole. That is the same producer ≠ critic ≠
tester separation the engineering standards demand, and here it happens to also be the cheapest
arrangement in main-context tokens.

**If the plan step declines the third agent:** criterion 8 still moves to the parent — that part is
free and correct either way. Criterion 7 stays with the producer and **is labeled unverified in the
artifact and in the returned summary**, so a downstream consumer knows the confidence column was
self-assessed. What it must never do is pass silently, and the parent must not substitute a nod at
the summary for the check — that buys nothing and disguises the gap.

## 6. `/discovery:explore` — the same treatment, briefly

Also `DISPATCH-SPLIT`, and it demonstrates the added blocker category rather than the gate question:

- **parent** — scope inference from conversation (same reason as research phase A); the `!`-precompute
  block, whose behavior under `skills:` preload the sweep records as unverified (an independent
  reason to prefer runtime `Skill` invocation here); **dimension 6's session-state probes** (MCP
  server reachability, worktree state, permission posture) where the *invoker's* session is the
  subject; and the terminal surfacing of open questions to the user, which the skill's outcome gate
  makes mandatory and `AskUserQuestion`'s absence makes undelegatable.
- **dispatch** — dimensions 1–5 (codebase reading, git history, project structure, test discovery,
  build/config), the numbered gap-list, the fan-out, the synthesis, and the `EXPLORE.md` write.
- Note dimension 6 is *not* wholly inline: "installed versions" of an ecosystem toolchain is a
  property of the machine and dispatches fine. The split is within the dimension, which is itself
  further evidence that the unit is a phase and not a file.

## 7. What I would put to the plan step

1. Adopt phase-level with the roll-up in §2d; add `DISPATCH-SPLIT`; narrow `DISPATCH-OPTIONAL` to
   runtime-conditional only.
2. Adopt the §2c blocker in both its observation and mutation forms.
3. Adopt the two declaration shapes in §3, copied from shipped precedent, with the crossing budget
   (§3c) and the `skill-quality:check` gate (§3d).
4. Re-derive the ledger's 29 `DISPATCH-OPTIONAL` rows and the 4 named INLINE-ONLY sub-action rows
   against the new vocabulary — a re-derivation over existing rationale, not a re-audit.
5. **Separately decide the 57 `INLINE-ONLY` rows** per §2d: re-test against the new definition, or
   grandfather with a recorded re-test trigger. This is the real cost of adopting §2d and should be
   priced before the vocabulary is locked, not after.
6. For `/research`: §4's table, the §4a tier amendment, and the three-way gate split in §5 — which
   adds one new agent (`discovery:research-verifier`) to Decision 2's two.

  closing paragraph is the fallback — criterion 8 moves to the parent regardless, criterion 7 stays
  with the producer and is labeled unverified, never silently passed.
- I have assumed the crossing budget (§3c) is a guideline the plan step can relax for a specific
  skill, not an invariant.
- Applying §2d to the ledger will interact with the three unratified flips and the
