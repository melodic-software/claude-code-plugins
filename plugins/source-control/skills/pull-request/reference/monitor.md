Phase 3 is an **async event loop**, not a sequential pipeline. After every push (initial PR creation, CI fix, comment fix), monitor CI status AND process comments concurrently as they arrive. Don't wait for all CI checks to complete before reading comments. Bots post at different times.

## Monitor entry checklist (in order, before any monitoring work)

On entering Phase 3 (`monitor`, `comments`, or `full` reaching monitor), complete these steps in order before any CI polling or comment evaluation; the environment-dependent event-delivery choice comes first. Standalone `create` runs Steps 1-3 when its session will keep acting on the PR it opened ([create-report.md](create-report.md) §2.6); `create --pushed` leaves them to its caller. `comments --ci` skips this checklist: the runner has checked out the head and kept the threads. `dependency --ci` and `ci --ci` do not enter Phase 3.

- [ ] **Step 0, Checkout the PR source branch (DEFAULT):** exploration, research, and any fix must run against the PR's head branch, not whatever branch you are on. Check it out with the forge's PR checkout (provider reference; fork-safe: a fork's head branch is not fetchable from `origin` by name, and a bare `git checkout <headRefName>` can select a stale same-named local branch). This is the default, not an exception.
  - **Pre-check `git worktree list`:** if the branch is checked out in another worktree, work there (or read-only, no fix, if you can't). Already on the PR branch: no-op.
  - **Dirty tree with unrelated WIP** (staged/unstaged/untracked from other work): do NOT switch; surface the WIP to the user and proceed read-only. Never `git stash` another session's WIP.
  - **Interactive session** (human present): changing branches re-points the working tree, so confirm the target branch with the user FIRST, UNLESS the invoking message already named the checkout (`/source-control:pull-request monitor <N>` against a specific PR is intent, but the target-branch confirmation gate still governs the mechanical switch).
  - **Autonomous session** (e.g. `CLAUDE_CODE_REMOTE=true`): check out without prompting.
  - **`/source-control:babysit-prs`** runs its own per-PR checkout; this Step 0 is the single-PR `monitor` equivalent, so don't double-checkout when that loop applies this checklist.
- [ ] **Step 1, Cloud check:** if `CLAUDE_CODE_REMOTE=true`, use [§3.0.0](monitor-cloud-poll.md) polling plus its PR-activity subscription. Skip remaining steps
- [ ] **Step 2, Push-channel gate ([§3.0.05](monitor-push-channel.md)):** if your environment ships a forge-events push channel (an MCP server delivering webhook events into the session), verify it is healthy per its own docs and §3.0.05 (broker alive, subscriber fresh). No channel → skip to Step 3's fallback
- [ ] **Step 3, Arm event delivery:** channel healthy → arm its PR filter for `<N>`; channel absent/unhealthy → arm the [§3.0.1](monitor-auto-watch.md) Monitor tool watch
- [ ] **Step 4, Proceed to [§3.1](monitor-ci-loop.md) monitoring loop**

**Why the order matters:** each step's fallback depends on the previous step's answer; polling before arming delivery pays a request per interval it did not need.

## Per-iteration monitoring checklist (on every CI or comment event)

On each channel event, Monitor notification, or poll iteration, complete every applicable step before declaring readiness or reporting status.

- [ ] **A. Terminal state:** read the PR's state. MERGED/CLOSED → self-terminate
- [ ] **B. CI checks:** read the PR's checks. Classify EVERY non-pending check (pass/fail/skipped). Read logs for ANY failure per §3.1 fetch chain
- [ ] **B2. Review-lane productivity:** a green AI-review lane is not evidence that a review happened. Take the lane roster from step B's checks roster, never from the authors who posted: a lane that posted nothing is missing from every author-derived roster by construction, so such a roster applies this step to an empty set. For each lane, confirm it produced something readable **for the current round**, scoped per surface the way [readiness.md](readiness.md) Gate 5 scopes its wait: the commit each inline review comment and each review was written against, and the creation time against the push time on issue-level comments, which carry no commit field at all and are where AI-review summaries land (field names: provider reference "Review surfaces"). An artifact from an earlier HEAD cannot satisfy this. An artifact from an earlier RERUN of the current head is indistinguishable by commit field alone, since it carries the same SHA, so bound that case by timestamp against the run's start. **A push needs a fresh round only when it changed reviewed content**, and any conflict resolution counts as changing it. A push that only merged the default branch needs none when `git show --remerge-diff <merge>` prints nothing at all. Nothing is excluded from the test: a resolved CHANGELOG, `.changes/` fragment or version line fails it like any other path. The remerge-diff shows what the merge itself changed, conflict resolutions included, so a clean merge shows nothing; a diff against either parent shows the other side's whole change and never passes. An empty remerge-diff does not detect semantic interaction between the branch's change and what the base brought in; it only shows that the merge added nothing of its own. When the test passes, the latest productive review on the pre-merge head satisfies this step. When it prints anything, or git cannot compute it, this step applies unchanged. A lane that concluded success having produced nothing for this round reviewed nothing, whether it never started, could not load the skill it was told to invoke, or stopped early inside its own session. Classify it ABSENT, never PASS, and stand a local review in its place over the same diff: `/review:fanout` for breadth, or the bundled `/code-review` against an explicit target for a correctness lane, whichever resolves in this session. A lane whose posted body admits it fell back to a manual pass is the same verdict. Name every absent lane and its substitute on the F report's `Review lanes:` line <!-- contract-restatement: B2-lane-productivity -->
- [ ] **C. Fetch ALL comments from ALL sources:** read every update on the PR regardless of author or format, every page of each surface (provider reference "Review surfaces"):
  - [ ] C1. Review-thread (inline) comments
  - [ ] C2. Issue-level comments (includes AI-review summaries, user replies, bot task-completion posts)
  - [ ] C3. PR reviews (review bodies contain findings. APPROVED/CHANGES_REQUESTED/COMMENTED reviews all may carry actionable content)
  - [ ] C4. Read every comment body in full. Summaries and review posts from ANY AI agent (claude[bot], codex, cursor, copilot) carry findings that need classification; they are NOT informational. **Extract individual findings** per [`<plugin-root>/reference/review-discipline.md`](../../../reference/review-discipline.md) §2: one comment with N findings = N work items, each needing its own D1-D7. **For ≥3 findings, dispatch a subagent** per the same §2: it preserves main session context and enforces the per-finding ledger shape
- [ ] **D. For EACH unaddressed **finding** (not comment, one comment may contain multiple findings):**
  - [ ] D1. Read full finding context (parent comment body + surrounding findings). For multi-finding comments dispatched to a subagent ([review-discipline](../../../reference/review-discipline.md) §2), this work is in the subagent; the main session receives the ledger
  - [ ] D2. Explore referenced code (must be on the PR branch for accurate results)
  - [ ] D3. **Validate the claim** before trusting it: check the assertion against actual code, run the command, read the file. Research non-trivial claims against official docs. Never implement a fix on a bot's assertion alone. **Blast radius:** when the fix would change a shared artifact (a reusable workflow or action, shared config, a published package), list its consumers and check the change against each before D4
  - [ ] D4. Classify: VALID (fix now) / VALID (defer) / INCORRECT / UNCERTAIN. Classification MUST cite evidence from D2-D3, stated as a `Basis:`: `verified` with the `file:line`, tool output, or URL, or `judgment` (never on a consequential finding: cross-repo, shared infrastructure, irreversible, or security). A consequential verdict the evidence cannot settle is withheld: classify it UNCERTAIN and name the evidence that would settle it. Contract: [`<plugin-root>/context/recommendation-basis.md`](../../../context/recommendation-basis.md); full convention: [recommendation-basis](https://github.com/melodic-software/claude-code-plugins/blob/main/docs/contracts/recommendation-basis/README.md#basis-label). A small or medium finding is VALID (fix now); where its fix lands is D4.6's scope test ([review-discipline.md](../../../reference/review-discipline.md) §3)
  - [ ] D4.5. React to the parent comment: `+1` VALID, `-1` INCORRECT, `eyes` UNCERTAIN. One reaction per comment. Mixed findings: `+1` if any VALID. Verify the reaction posted by reading the comment's reactions back, non-zero confirms. **Exemption:** where the forge offers no reaction on PR review BODIES (C3 surface; GitHub does not), skip the reaction for review-body findings; the D5 reply is the audit signal there
  - [ ] D4.6. **Ground a `VALID (defer)`** (canonical: [review-discipline.md](../../../reference/review-discipline.md) §3). Check provenance first, if the defect did not reproduce on the base branch, this change introduced it and it is `VALID (fix now)`, never deferrable, whichever file it surfaced in. Defer only a structural finding (needs its own planning pass), an urgent real one that cannot land in this PR, or one whose fix is blocked on research this lane cannot do; no item for a nit or a speculative concern. Otherwise file the tracker item BEFORE the D5 reply, carrying the finding's evidence, and cite its id in the reply. **No reachable tracker removes the deferral, never the reply:** a work-item tracker is optional here ([SKILL.md](../SKILL.md) §Adapting to your environment) and its absence never blocks a phase, without one, `VALID (defer)` is not an available disposition, so fix the finding now, or reply saying why the fix does not belong in this change, leave the thread unresolved, and report it for the user to place <!-- contract-restatement: D4.6-deferral-provenance --> <!-- contract-restatement: D4.6-deferral-grounding -->
    - [ ] **Verify the item exists:** re-query it by id and confirm it is filed and open, a deferral whose only record is thread prose is a dropped finding, and the thread stays open
  - [ ] D5. Reply with a per-finding classification table + evidence (before fixing), plus one `<!-- d5 finding=<#> label=<LABEL> lane=<lane> -->` line per finding ([review-discipline.md](../../../reference/review-discipline.md) §2). **Route by comment type, REQUIRED, not interchangeable:** inline review comments MUST reply THREADED on the inline thread; issue-level / review-level → a PR conversation comment. Answering an inline finding with a detached conversation comment is a routing error, not a style choice. Use the project's bot-identity wrapper for these writes when it has one; the plain forge CLI otherwise
    - [ ] **Verify reply exists, on the surface it was posted to:** inline threaded replies land on the review-comment surface, filtered to replies to the original comment; issue-level replies land on the conversation surface. Querying only the conversation surface false-fails a correctly posted inline reply; so does reading one page, since these surfaces page oldest-first and your reply is the newest item (commands: provider reference "Review surfaces")
  - [ ] D6. Fix if VALID (fix now), edit, `git add <files>`, commit. A finding about behavior (wrong output, a crash, a missed input) gets a test that fails on the current head for the reason the finding names before the fix, and the fix makes it pass; a wording, style or docs finding needs none. Where no test can reach the behavior, say so in the D7 reply. Do not push per finding: the round pushes once, after every VALID (fix now) finding has its D6 commit and every reviewer on the head has finished ([§3.3.2](monitor-comments.md)). D7 and D7.5 for every finding in the round wait for that push and the check below
    - [ ] **Verify commit pushed, once per finding after the round's single push:** `REMOTE=$(bash "<skill-dir>/scripts/resolve-remote.sh" --push '<branch>') && git fetch "$REMOTE" --end-of-options '<branch>' && git merge-base --is-ancestor <fix-sha> FETCH_HEAD`. The head branch name comes from GitHub: substitute it only when it matches `^[A-Za-z0-9._/-]+$`, does not start with `-` and contains no `..`, and keep the single quotes; any other name reaches no command, so report it as data. Exit 0 means the fix commit is on the PR branch as just fetched from the resolved push remote; non-zero means it is not. Three constraints, each closing a false verdict: resolve the push remote (`resolve-remote.sh --push`, the resolver `push-branch.sh` pushed through), never a hardcoded `origin`: a triangular/fork checkout pushes elsewhere, so `origin` false-fails a successful push or verifies a same-named branch on the wrong repository; a reachability check after fetch (`FETCH_HEAD` is what the resolved remote just served), never the branch-tip read (`commits?sha=<branch>&per_page=1` + `.[0]`), which any later push turns into a false "missing"; and never a repository-scoped `commits/<fix-sha>` lookup alone, which can pass when the commit was force-pushed off the PR branch
  - [ ] D7. Post a follow-up reply citing the fix commit SHA
    - [ ] **Verify follow-up reply posted, same surface routing as D5:** inline thread → the review-comment surface filtered to replies to the original comment; issue-level → the conversation surface filtered to a comment whose body contains `<sha>` and whose author is `<posting-identity>`. Confirm the follow-up with SHA appears on the forge. Constrain on BOTH the SHA and the posting identity, never on the last element of the list: these surfaces page oldest-first, so on an unpaginated read the last element is the 30th-oldest comment. SHA alone fails this control gate: anyone else quoting the fix SHA (a reviewer, another bot) satisfies it, reporting your reply as posted when the write failed. `<posting-identity>` is the login you posted as (the bot-identity wrapper's account when the project has one, your own otherwise)
  - [ ] D7.5. Resolve review thread, **author- and classification-conditional, inline only**. Eligible only when EVERY finding in the thread carries a recorded disposition: `VALID (fix now)` with the fix pushed and cited, `VALID (fix now)` fixed in a linked PR the reply cites, `VALID (defer)` grounded per D4.6 with the item id cited, or `INCORRECT` with counter-evidence posted, one dispositioned finding never makes a multi-finding thread eligible, and a single `UNCERTAIN` escalates and holds the thread open. Resolve threads opened by a BOT reviewer that you addressed. NEVER resolve HUMAN-authored threads (the human resolves their own). NEVER resolve your OWN (your posting identity. Bot or personal). **A `VALID (defer)` never clears the gate for a merge this same session performs**. `full` mode monitors and merges in one session, so route the deferral to an independent adjudicating context, or leave the thread unresolved and do not merge. Fail closed. Detect bot from the author type the forge reports, and after resolving, read the thread back and confirm it reads resolved (provider reference "Review surfaces") <!-- contract-restatement: D7.5-thread-eligibility --> <!-- contract-restatement: D7.5-merge-authorization -->
- [ ] **E. Readiness gate:** ALL checks terminal + every review lane productive or substituted per B2 + ALL comments addressed + 2-min cooldown since last activity per [readiness.md](readiness.md) + when the PR changes a shared artifact, its consumers listed and checked (the D3 blast-radius step, applied to the whole diff)
- [ ] **F, Report:** present the full readiness table OR list remaining blockers

**Receiving an event is not processing it.** Each event drives at least steps A-C, and a new comment event drives D1-D7 for that comment. Readiness is declared only after E.
