## Project Overview

Harbormaster is a TypeScript monorepo that manages container-ship berth scheduling for mid-size
ports. It exposes a REST API for booking agents, a background scheduler that assigns berths, and a
notification service that emails terminal operators when a berth assignment changes. The project
uses pnpm workspaces to manage its packages, TypeScript for static typing, Express for the HTTP
layer, and Vitest for testing. Data is persisted in PostgreSQL through Drizzle ORM, and messages
between services travel over RabbitMQ.

## Package Details

### packages/core

This package contains the domain model. The `Berth` entity in `src/berth.ts` models a physical
berth with a length, depth, and crane count. The `Vessel` entity in `src/vessel.ts` models an
arriving ship with its dimensions and cargo manifest summary. The `Booking` aggregate in
`src/booking.ts` connects a vessel to a berth over a time window and enforces that windows never
overlap for the same berth. Scheduling logic lives in `src/schedule.ts` as pure functions so the
scheduler service can call them without any I/O. Errors are typed classes in `src/errors.ts`, and
everything public is re-exported from `src/index.ts`.

### packages/db

This package owns persistence. Table definitions live in `src/schema.ts` using Drizzle's
`pgTable` helpers. Migrations are generated with drizzle-kit into `src/migrations/` and applied
by the API service at startup. Each aggregate has a repository class under `src/repositories/`
that maps between Drizzle rows and the domain entities from `packages/core`.

### packages/config

This package loads and validates environment variables. The Zod schema in `src/env.ts` declares
every variable with its type and default, and the loader throws at startup when a required
variable is missing, so services fail fast instead of misbehaving at runtime.

### services/api

The Express application. `src/app.ts` builds the app, registering JSON body parsing, the auth
middleware, the routers, and the error handler in that order. Routes live under `src/routes/`,
one file per resource. The service listens on the port from `packages/config`.

### services/scheduler

A background worker. `src/main.ts` connects to RabbitMQ, consumes booking-created events, and
runs the assignment pass in `src/assign.ts`, which calls the pure scheduling functions from
`packages/core` and writes results through `packages/db`.

### services/notifier

A background worker that consumes assignment-changed events and sends emails to terminal
operators using the MJML templates in `src/templates/`.

## Development Commands

- `pnpm install` — install all workspace dependencies
- `pnpm build` — build every package and service with TypeScript project references
- `pnpm test` — run the Vitest suite across the workspace
- `pnpm lint` — run ESLint over every package
- `pnpm format` — run Prettier over the repository
- `pnpm typecheck` — run `tsc --noEmit` across the workspace
- `pnpm --filter @harbormaster/api dev` — start the API in watch mode
- `pnpm --filter @harbormaster/scheduler dev` — start the scheduler in watch mode
- `bash scripts/reset-db.sh` — reset the local development database

After cloning, run `pnpm build:proto` once before the first `pnpm test`: the generated RabbitMQ
message stubs are gitignored, and Vitest fails with a misleading module-resolution error — not a
missing-dependency error — until they exist.

## Code Style Guidelines

- Use TypeScript strict mode everywhere; `tsconfig.base.json` already enables it
- Use `camelCase` for variables and functions, `PascalCase` for types and classes
- Prefer `const` over `let`; never use `var`
- Prefer arrow functions for callbacks and standalone function declarations for exports
- Use template literals instead of string concatenation
- Use async/await instead of raw promise chains
- Keep functions small and single-purpose
- Write descriptive variable names; avoid single-letter names outside loop indices
- Use ES module `import`/`export` syntax, never CommonJS `require`
- Prefer named exports over default exports
- Format code with Prettier before committing; the configuration uses Prettier's defaults
- Follow the ESLint rules configured in `.eslintrc.cjs`; do not disable rules inline
- Order imports: Node built-ins first, then external packages, then workspace packages, then
  relative imports
- Avoid `any`; when a type is genuinely unknown, use `unknown` and narrow it

## Testing Conventions

- Tests live next to the code they cover, named `<module>.test.ts`
- Use Vitest's `describe`/`it` blocks with behavior-style descriptions
- Mock external services with `vi.mock`; never call real infrastructure from unit tests
- Aim for meaningful coverage of branching logic rather than a numeric coverage target
- Integration tests live under each service's `test/` directory and run against Dockerized
  PostgreSQL and RabbitMQ started by `docker compose up -d`
- Run `pnpm test` before pushing to make sure the suite passes

## Express Middleware Reference

Express middleware functions are functions that have access to the request object, the response
object, and the next middleware function in the application's request-response cycle. Middleware
can execute any code, make changes to the request and response objects, end the request-response
cycle, or call the next middleware in the stack. If the current middleware function does not end
the request-response cycle, it must call `next()` to pass control to the next middleware
function; otherwise the request is left hanging. Application-level middleware is bound to the
app object with `app.use()`, while router-level middleware works the same way but is bound to an
instance of `express.Router()`. Error-handling middleware is defined with four arguments instead
of three (`err`, `req`, `res`, `next`), and Express recognizes it by arity. This is why
`src/middleware/error-handler.ts` must keep all four parameters even though `next` is unused.

## API Endpoints

The API service exposes the following routes, all defined under `services/api/src/routes/`:

- `GET /health/live` — liveness probe, returns 200 when the process is up
- `GET /health/ready` — readiness probe, returns 200 when the database is reachable
- `GET /berths` — list berths with their dimensions and crane counts
- `GET /berths/:id/availability` — availability windows for one berth
- `GET /bookings` — list bookings, filterable by status and date range
- `POST /bookings` — create a booking request for a vessel
- `GET /bookings/:id` — fetch one booking with its assignment state
- `PATCH /bookings/:id` — amend a pending booking's window or vessel details
- `DELETE /bookings/:id` — cancel a booking that has not yet been assigned

All routes except the health probes require a JWT bearer token issued by the port authority's
identity provider. Request and response bodies are JSON. Validation errors return HTTP 422 with
a body listing each failed field, and domain rule violations return HTTP 409.

## TypeScript Configuration

The base configuration in `tsconfig.base.json` sets the following options:

- `strict: true` — enables all strict type-checking options
- `target: ES2022` — modern output, matching the pinned Node.js version
- `module: NodeNext` — native ES modules with Node.js resolution
- `esModuleInterop: true` — smooths CommonJS interop for the few remaining CJS dependencies
- `skipLibCheck: true` — skips type-checking declaration files for faster builds
- `composite: true` — enables TypeScript project references between packages

Each package extends this base file and adds only its `outDir` and `references` entries.

## Database Notes

- The development database runs in Docker via `docker compose up -d postgres`
- Connection settings come from the environment variables validated in `packages/config`
- Drizzle migrations are applied automatically when the API service starts
- To create a new migration, edit `src/schema.ts` and run `pnpm --filter @harbormaster/db
  generate`
- The `bookings` table has a partial unique index preventing overlapping windows per berth;
  Postgres enforces it, so application-level checks are a fast path, not the source of truth

## Git Workflow

- Create a feature branch from `main` for every change
- Write commit messages in the imperative mood with a short summary line
- Keep commits focused; avoid mixing refactoring with behavior changes
- Open a pull request and wait for CI to pass before requesting review
- Squash-merge pull requests so `main` stays linear
- Never force-push to `main`
- Rebase feature branches onto `main` instead of merging `main` into them
- Delete feature branches after merging

## Environment Variables

The full list is defined and validated in `packages/config/src/env.ts`. The most commonly needed
ones during development are:

- `DATABASE_URL` — PostgreSQL connection string
- `RABBITMQ_URL` — RabbitMQ connection string
- `JWT_SECRET` — secret for signing API tokens
- `SMTP_HOST` — mail server for the notifier
- `LOG_LEVEL` — pino log level, defaults to `info`
