# `/bug-report` template and worked examples

Loaded on demand by the `bug-report` skill. Contains: the full Markdown template (5 fields), one worked example, the `--file` frontmatter, and the "No bug confirmed" form.

## Full template

Default emission (stdout) — no frontmatter:

```markdown
# Bug: <title in present tense, one line>

**Severity**: <low | medium | high | critical>
**Suggested fix location**: `<file path>` `<function or class name>` (no patch)
**Reported by**: <reporter identity, or session ID>
**Reported at**: <ISO-8601 timestamp>

## Steps to reproduce

1. <step>
2. <step>
3. <step>

## Expected behavior

<what should happen>

## Actual behavior

<what does happen>

## Severity justification

<one sentence: why this severity. Cite blast radius / blocking factor / data-integrity impact>

## Notes

<optional: anything the reporter said that doesn't fit above; flag any (unknown — needs reporter confirmation) entries here for traceability>

---

*Generated by `/bug-report`. To file it as a work item, hand off in a GitHub repo with*
*`gh issue create --body-file <this report>` (let `gh` prompt for the title), or use an available tracker MCP tool.*
```

## `--file` mode frontmatter

When writing to a file, prepend:

```markdown
---
type: bug-report
date: <ISO-8601 UTC, e.g. 2026-05-02T14:30:00Z>
slug: <slug>
severity: <low | medium | high | critical>
fix-location: <file path>
---
```

ISO basic timestamp in the filename (Windows-safe, no colons): `20260502T143000Z`. Example filename: `20260502T143000Z-bug-pricefor-discount-math.md`.

## Worked example

**User input**:

> there is a bug in `priceFor` in `product-service.js` — when `discountPercent` is non-zero, the total comes out off by what looks like a per-unit-vs-total ordering issue

**Survey** (fast breadth pass):

- `Glob` `**/product-service.js` → one match: `apps/storefront/src/product-service.js`
- `Grep` `priceFor` in that file → exported function at line 12
- `git log --oneline -5 -- apps/storefront/src/product-service.js` → last change 3 weeks ago, "feat: add quantity discount support"

Symbol unambiguous, file located, recent change identified. Skip to Q&A.

**Q&A** (one question at a time):

> Which input triggers it? Give me the smallest case where the total is wrong.

User: `priceFor("widget-1", 3, 10)` returns `2700` for a `1000`-cent product, expected `2700` (3 × 900). Wait — that matches. Try `priceFor("widget-1", 3, 50)` → returns `1500`, expected `1500`.

The reporter realises the math may be correct and asks: "actually run it through and tell me if the bug is real."

**Resolution**: the agent runs the math, reports back. Two outcomes:

1. **Math correct** → recommend the user closes the loop without filing. Emit a "No bug confirmed" note instead of a report.
2. **Math wrong** → emit the structured report below.

Assume the math is wrong (the comment claims the discount is per-unit-before-multiply but the formula multiplies after, leaving a comment/code mismatch which is its own defect).

**Emitted report**:

```markdown
# Bug: `priceFor` comment misrepresents discount-application order in `product-service.js`

**Severity**: low
**Suggested fix location**: `apps/storefront/src/product-service.js` `priceFor` (lines 12-18)
**Reported by**: dev@example.com
**Reported at**: 2026-05-02T14:30:00Z

## Steps to reproduce

1. Open `apps/storefront/src/product-service.js`
2. Read the comment on line 16: `// discount applied per unit before multiplying out.`
3. Compare to the actual formula on line 17: `const unit = product.priceCents - product.priceCents * (discountPercent / 100); return unit * quantity;`

## Expected behavior

Comment matches code. Either:

- The comment describes what the code does (per-unit discount, then multiply by quantity) — current behaviour
- OR the comment describes a pending fix that has not landed

## Actual behavior

Comment claims a bug that the code does not currently exhibit (the math is correct as written). The comment is stale, or the code was fixed without updating the comment.

## Severity justification

Cosmetic / documentation drift. No incorrect output, no data corruption, no user-visible defect. Worth fixing for code clarity but no production impact.

## Notes

- (unknown — needs reporter confirmation): is the intent to remove the comment, or was a stricter "per-unit-discount-then-tax" rule planned that the code does not implement?
- The function has no unit test in `apps/storefront/test/`. Consider adding one alongside the comment fix to lock in the math.

---

*Generated by `/bug-report`. To file it as a work item, hand off in a GitHub repo with*
*`gh issue create --body-file <this report>` (let `gh` prompt for the title), or use an available tracker MCP tool.*
```

## Negative-constraint reminders

When emitting, the skill MUST NOT:

- Patch the code or open a PR — only emit the report
- Invent reproduction steps that the user did not give and the source does not back
- Skip the severity-justification field (one sentence is enough; "obvious" is not a justification)
- Drop the `(unknown — needs reporter confirmation)` placeholders into prose — surface them under Notes
- Auto-correct typos in the user's description — `flusH()` may be intentional; ask one question

## When the report is "no bug confirmed"

When the survey + Q&A reveals no defect, do NOT emit a bug report. Emit a 3-line summary instead:

```markdown
*No bug confirmed.*

**Description claimed**: <what the user said>
**Verified state**: <what the source/test/run actually shows>
**Recommendation**: <close the loop / capture it as a feature request / open a question elsewhere>
```

This preserves the read-only contract while saving the user from filing a phantom issue.
