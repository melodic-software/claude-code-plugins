## Purpose

Rework often comes from acting on assumptions the user never made and the agent never surfaced, an **underspecified** task, one missing the constraints needed to act safely. `/planning:interview` is the pipeline's underspecification resolver: a structured pass driving every unknown the task depends on to a decision or capturing it as a named, explicit assumption, before exploration, planning, or execution start.

The **pre-clarity** stage. Upstream of exploration, research, and `/planning:plan`. `/planning:plan` presupposes a coherent task; `/planning:interview` produces one out of fuzzy intent. The contract it writes is the target every later stage aims at.

**Level this skill decides: behavior**, what the work does and how to tell it is done; interfaces and contracts are `/planning:design`'s, and files and symbols are `/planning:plan`'s.

**Supportive, not adversarial.** `/planning:devils-advocate` attacks an existing artifact after the fact. `/planning:interview` walks alongside the user to extract a clear contract from the start. The `product` action is the one exception: the user asked for the idea itself to be tested ([`context/product.md`](context/product.md)).

**Domain-routed.** The interview loop is universal. Any task, proposal, or choice can be its subject. What the session *produces* depends on context: an engineering task in a code repo locks a PLAN.md Brief and can hand off to `/planning:plan`; a general decision drives to a shared understanding and ends there. The domain is inferred from the task's build surface. The problem itself decides, with repo and working directory as context that never suffices alone. Never asked, and it is orthogonal to the `me`/`auto`/`lock` action. Engineering machinery, codebase grounding, the Brief, ADR/glossary outputs, pipeline handoff, engages only when the context is engineering; the universal loop runs either way. A user can override the inference in prose ("this isn't a code task", "interview me on this decision"). An engineering session also reads the consumer's standards before any bundled default, asks the variation-intent question, and prompts quality requirements (NFRs), each scaled by the quality bar: read [`context/loop.md`](context/loop.md) "Engineering defaults" after the Step 1 survey.

**Two invocation modes, one schema.** When intent is fuzzy, `/planning:interview` runs the depth-first Q&A loop. When intent is already clear from conversation, `/planning:interview` synthesizes directly without asking (front-loaded brief). Both write the same output for the session's domain. A PLAN.md Brief for an engineering task, a shared-understanding summary otherwise. The default action **auto-detects** which mode fits and routes accordingly. **Cost framing**: every clarification round-trip skipped is time and tokens saved. Auto-detect removes redundant Q&A; explicit `lock` asks only its one problem question when the user has already given the answer.

## Gates

Five gates halt this skill. They are stated here, near the top of the file, so they stay in view; the full rule is in the step each line names, and the two never differ in what they forbid.

- **The user's decisions are never synthesized.** Synthesize-directly and the Mixed path's synthesized rest resolve only codebase-resolvable facts and unambiguous conventional defaults. A decision that is genuinely the user's is asked, never folded into the Brief or captured as an assumption. Unattended, and only when the caller declares it, that decision is recorded `blocked` with arbiter `USER-RESERVED` and named as a blocker. Full rule: Step 1.5, the auto-guard and its unattended path.
- **A gap during `lock` synthesis halts the run.** Stop and surface the gap to the user; never fudge it with a guess. `lock` confirms the problem with one question and takes its invocation as confirmation of the rest; neither exempts it from this halt. Full rule: the Action Router `lock` row and Step 1.5. Unattended, a stop at the instance question or the Finish line exits as [`context/loop.md`](context/loop.md) "Unattended path" says, not by this halt.
- **The register gate runs before the contract locks.** Before persisting the contract or handing off, run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-open-questions.sh" --ledger <memory_dir>/<topic-slug>/interview-checklist.md`; exit 1 and exit 2 both halt. Only a run that asked no question skips it; the acceptance-criteria coverage prompt is not a question for this purpose, and any other question is ([`context/coverage-prompt.md`](context/coverage-prompt.md)). Full rule: Step 3, "Register gate".
- **The confirmation gate holds the contract until the user confirms.** In `me` and `auto`, the interview ends only on the user's explicit confirmation: before persisting the contract or handing off, restate the shared understanding, opening with the one-line problem, and wait for that confirmation. `lock` confirms the problem with one registered question and its invocation confirms the rest; its STOP-on-gap rule still applies. Full rule: Step 3, "Confirmation gate".
- **The Brief is cross-checked once it exists.** Immediately after writing the Brief, run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-open-questions.sh" --ledger <memory_dir>/<topic-slug>/interview-checklist.md --procedure --brief <memory_dir>/<topic-slug>/PLAN.md`, plus any flag the resolved lane's spoke adds to it (re-read that spoke if it is no longer in context); a non-zero exit halts. Fix a missing deferred question or heading in the Brief, never by retiring a row; exit 1 with `brief=unconfirmed` clears only after the user confirms a fresh `restate` and the Brief is exported again. A run that writes no Brief (a general session, `scope`) skips it. Full rule: Step 4, "Cross-check the Brief once it exists". An unattended run that exits without the lock, as [`context/loop.md`](context/loop.md) "Unattended path" says, skips this cross-check too.

## Stance: supportive, depth-first, opinionated

The Q&A path of this skill is one engine wrapped in a stop condition and an output contract. Four working principles drive it:

1. **Frontier-rounds loop**. A question is ready once every decision it rests on has an answer, and the set of ready questions is the **frontier**. On a webhook-retry task, the retry budget is ready on day one, while the alert threshold rests on that budget and so sits out until the budget is answered. Each round numbers every ready question, orders them as [`context/loop.md`](context/loop.md) "Frontier rounds" item 2 says (new questions by how much later work each answer would reshape, largest first), sends them together (one per message under `single` pacing, "Question pacing" below), and waits; the replies decide what is ready next time. One ready question still makes a round
2. **Survey-then-deep**. Before asking blind, do a fast breadth pass (repo files, recent commits, existing skills, relevant project rules) so questions land in real context
3. **Climb-to-anchor**. Find the nearest `CLAUDE.md`, `AGENTS.md`, domain-vocabulary file, or module README by walking UP from the relevant directory toward repo root; let those shape questions instead of asking what is already documented
4. **The project's terms from the start**. Once the interview starts, past the quick-change skip
   in [`context/routing.md`](context/routing.md), invoke `/domain-driven-design:ubiquitous-language lookup` (if enabled)
   via the Skill tool, with one line saying why ("Reading the project glossary so these questions
   use its terms."); when that skill is not listed, read the glossary file as loop.md "Step 1.
   Survey before you ask" says, and the opening lines offer its plugin's install once ("Question lanes").
   Agree each term in the question where it first appears and write it only after the user
   confirms its restatement ("Agree a term where it first appears"). Route decisions, gotchas, and
   conventions to their proper homes (ADR, project rules, side note) in the same response. A
   general session writes no repo docs. It drives to a shared-understanding summary only

**Intake the starting point.** Early in the loop (or before it), establish where the user is. One discovery question in the intake round ([`context/lookups.md`](context/lookups.md) "The intake round") that discloses their starting point; questions and recommendations calibrate to that disclosure. Route by what it shows; recommend, never auto-switch, in the one-line shape [`context/lookups.md`](context/lookups.md) "The intake round" gives a routing suggestion:

- **Idea stage** (a half-formed idea, "I just had this thought", the user does not yet know what they want): recommend `/planning:brainstorm`, which explores approaches and returns here with a handoff. If the user stays, follow [`problem-framing.md`](../../context/problem-framing.md) "Idea-stage requests".
- **User-facing product work** whose users or success measures are unsettled: recommend `/planning:prd` first.
- **Unfamiliar territory**: when the domain or codebase area is new to the USER, they can't yet evaluate options. Route to a blindspot-surfacing exploration FIRST (invoke `/discovery:blindspot <area>` (if enabled) via the Skill tool, otherwise a guided walkthrough of the area); an interview over unknown territory locks a contract the user can't assess.
- **"Document my repo"**: a request to write down the project's domain language or its terms is not an interview. Route it to `/domain-driven-design:ubiquitous-language` (if enabled) (its `seed` action when no glossary exists); when the `domain-driven-design` plugin is not enabled, say that skill owns it and offer to interview a concrete task instead.
- **A brainstorm handoff exists**: when `<memory_dir>/<topic-slug>/brainstorm.md` has a `## Handoff` block, read it as a settled upstream artifact and seed the Brief from it: Problem into `### Problem`, the Intent and Vision fields into the Goal's lines of the same names, Chosen direction into the Goal, Rejected options (with reasons) into `### Out-of-scope`, Criteria surfaced as acceptance-criteria candidates. The restatement still confirms each.

Every other skill the interview hands to or detours through: [`context/composition.md`](context/composition.md).

**Ask the quality bar in round 1.** When the request does not already state it, round 1 asks which bar the work is for: a throwaway prototype, an internal tool, or production. The Step 1 survey decides the question's form. When the survey read evidence for one bar in a source it cites (who runs the result, what data it touches, whether it ships to users, such as a published plugin manifest or a release workflow), round 1 asks it as a decision question: `My recommendation:` names that bar with the evidence as its basis, the other two bars are its alternatives, and a `Flips if:` line names the fact that would change it. The request's wording alone is not that evidence. With no such evidence, round 1 asks it as a discovery question, its title listing no bars and its Context naming the three bars and what each changes. Either form is registered `open` and stays open until the user answers. When the request states it, never re-ask it; treat it as settled. Interview depth scales with the bar. A prototype gets the scoping questions only, with production concerns (accounts, scaling, monitoring, CI, coverage targets) named as deferred rather than asked. Production gets the full depth, including failure handling, data correctness, security, monitoring, and rollback; an internal tool sits between the two. When the user cannot judge the discovery question ("I don't know", "you tell me"), recommend one from evidence in the next round: who runs the result, what data it touches, and whether it ships to users. Ask them to confirm it like any recommendation. Never fall back to the prototype bar unasked.

**Open with the problem when the request has none.** A request phrased as a solution with no stated problem follows [`problem-framing.md`](../../context/problem-framing.md) "Prescribed solution": read that section before round 1, and make round 1's first question its rethink-or-accept question; any why question comes after it. In a round that asks only discovery questions, the quality bar's decision form aside, it is asked open, in the shape [`context/lookups.md`](context/lookups.md) "The intake round" gives; in any other round, state the problem worked back out with its evidence rating first, never an open question asking what problem the solution solves. When the request names neither a problem nor a solution (an idea), round 1's first question asks what problem it solves and why the user wants it solved; keep that answer in the user's words for the Goal's Intent line.

**Check a problem only someone reported.** A stated problem whose evidence is only `reported` gets one instance question, and a Problem field that would read `unknown` gets candidate values to confirm, per [`problem-framing.md`](../../context/problem-framing.md) "Reported-only evidence" and "Candidates for an unknown field".

**Every goal carries a "because".** When the user states a goal with no reason, ask why, as a registered question, before the goal locks, and keep the answer in their words on the Goal's Intent line. The Intent line reads `none stated` only where no one could be asked: an upstream artifact that quotes no reason, `lock`, or an unattended run.

A new effort starts here, however big. When the interview shows the effort will outrun a single session AND is still too foggy to phrase as sharp questions, the user can't yet list the decisions, let alone lock them. Name `/planning:wayfind` to the user (it charts the fog as a map of decision items and works the frontier down decision by decision, graduating to a Brief once it clears); recommend, never auto-switch. The user can run it in this same session: its chart step reads this topic's ledger, so settled answers become decisions so far and open questions become decision items.

**Question budget scales with what's already settled.** Upstream artifacts, research findings, exploration output, a PRD, a design resolution, count as settled prerequisites: an interview invoked after them starts with a smaller tree and fewer rounds; never re-ask what an artifact already answers. There is no numeric question cap (the shared lane's round cap, [`context/lane-shared.md`](context/lane-shared.md) "Round cap", limits a round, not the interview), but a frontier that keeps *ballooning* (each round opens more branches than it closes) is the wayfind signal above, not a license for a marathon session. Surface the routing recommendation instead of grinding on.

**Bulk application work is not a decision set. The interview settles it once, it never executes it.** When the task applies a settled shape across a corpus (every document in a set, every file matching a pattern, every page of a spec), the interview's output is TWO things and no more: the small set of genuinely contested decisions, driven to decisions the normal way, plus an **execution contract**. One line in the session's output artifact, routed by domain like every other output: the Brief's `### Acceptance criteria` in an engineering session, the shared-understanding summary in a general one. Naming the per-unit close-out loop (one source unit at a time: apply, verify, close) and what *closed* means for a unit. NEVER enumerate the per-unit applications as decision rows: an interview that becomes the execution container turns every application step into a decision needing its own adoption ceremony, and the corpus's size becomes the session's length. **Tripwire. Count the candidates against the corpus:** when the candidate question count scales with the number of source units rather than with the number of genuine forks, that is execution masquerading as decisions. Collapse the per-unit rows into the loop, keep only the forks, and say what you collapsed. Distinct from the ballooning frontier above and remedied differently: ballooning routes to `/planning:wayfind`, unit-scaling collapses into the execution contract and hands off to execution.

Tone is collaborative but opinionated. You are not interrogating; you are helping the user think out loud by PROPOSING answers grounded in codebase evidence. When the user gives a definitive answer, lock it. When they hesitate, slow down and offer two or three concrete shapes the answer could take. Every option set names exactly ONE recommended option marked **(RECOMMENDED)** with its basis (each fact with its source, then the one-line inference), except a withheld or discovery question (see "Recommended answers"), each asked open with no recommended option. The surface follows the resolution in "Question lanes" above: rounds go where its handle sends them, and `AskUserQuestion` only where `handle.rules` allows cards, when the user opted in and the round qualifies.

**Do not nod along.** Agreement is not the job. When an answer conflicts with the code, a constraint row, or an earlier answer, name the conflict and its source once, before recording it, and ask whether they hold the answer or change it, registered like any question; the row stays `open` until they say. Never praise an answer or call it a good idea.

### Relentless mode (`me`)

Read [`context/relentless-mode.md`](context/relentless-mode.md) before the first round when the action resolves to `me`. It holds what relentless mode means and its canonical framing. The round mechanics below apply to every mode that asks questions.

**Ask each round inline as one numbered set.** Per-question shape within the round, as the saved round file holds it (the full block; "Keep the layout whole" says what each detail level prints):

```text
Q<N>: **<one-line question>**

Context:
- <the problem this decision solves, in one or two sentences> (<link or file:line>)
- <what the source says or ships, paraphrased; label each part of an absorbed idea source or ours> (<link to its exact section>)
- <what exists today, and the gap> (<file:line>)
- <each term the question relies on, defined inline> (<its source, or its agreed terminology row>)

[Source: <the exact text the decision rests on, as a > quote>, <link to its exact section>, <one line on why that text makes this a question>. ONLY when the question rests on text the user has not read]

My recommendation: **<answer>**. <2-3 sentences: why it beats the alternatives, including why those facts together lead to this answer for this user>. It gains <what it gains>, at the cost of <what it costs>.
Origin: <the user, round <N> | <named source> (<link>) | new (ours)>
[Checked against: <each constraint named in words>. ONLY when a constraint shaped the answer]
Basis: verified, <the Context sources this recommendation rests on>
[Flips if: <the condition that would change it, a fact the user can confirm>. ONLY when such a condition exists]
[Withheld: <the evidence that would settle it>. ONLY in place of the recommendation and the lines after it up to Alternatives, for a question research could not settle]

[Commits you to: <ONLY when the recommendation fixes more than one decision; each part of it, numbered>
- Q<N+1>: <sub-decision>: <recommended value>, one bullet per part, numbered on from Q<N+1>]

Alternatives:
- (a) <option>. <what it gains>, but <what it costs> (<source, or judgment>; origin: <the user | named source | new (ours)>)
- (b) <option>. <what it gains>, but <what it costs> (<source, or judgment>; origin: <the user | named source | new (ours)>)

---

Q<N+1>: ...
```

**Every proposal names its origin.** The `Origin:` line under the recommendation, and the `origin:` note in each alternative, say whose idea it is: the user (with the round they said it in), a named source (with a link to its exact section), or new (ours), meaning this session proposed it. A proposal that merges two gets both labels, each on the part it covers. The user can then weigh an idea by where it came from without asking "is this theirs or yours?". The label is the proposal's provenance, not its evidence: `Basis:` still names the sources the recommendation rests on. Both lines bind the full block in the saved round file; the `standard` and `minimal` prints hide them, so the recommendation's reason itself ends with its evidence label, its source and the specific fact it rests on ("(verified, user, round 1: receivers deduplicate on `event_id`)"), never a label and source alone, at every level.

**Group the round by topic.** When a round's questions span more than one topic, put them under short topic headers (`#### Retry budget`), ordered inside and across groups as [`context/loop.md`](context/loop.md) "Frontier rounds" item 2 says. `Q<N>` numbering stays continuous across groups. The round ends with no summary table. The user may answer by exception ("all as recommended except Q7 = b") or by topic ("on retries, ..."). A reply addressed to a topic resolves each question under that header it decides, under the same read-back, free-text and hedged rules as any answer, and leaves the rest `open` under the drift check.

**Open the round header with its scope check.** Every round header, the intake round's included, carries one `Scope check:` line under the round's title line, as `round.sh` prints it ([`context/routing.md`](context/routing.md) "The scope-check line"), then the `Later:`, `Held:` and `Settled by evidence:` lines that apply.

**Name the held questions in the round header.** When a question is held for a running lookup ([`context/lookups.md`](context/lookups.md) "Held questions"), the round header carries one `Held:` line naming each held question by id and plain name, and what it waits on: `Held: Q6 (alert threshold), waiting on the principle map`. Its id, its `waits on:` row and when it is asked: [`context/lookups.md`](context/lookups.md) "Held questions". A held row the reply does not address is restated by the `Held:` line, not by a separate drift line.

**Name later rounds in the round header.** When this round's answers will open questions that are not ready yet, the round header carries one `Later:` line naming those topics in plain words: `Later: interface shape, test plan, migration order`. It lists topics, not questions: nothing on it takes a `Q<N>` or a register row, and a topic leaves the line once its questions are asked or an answer removes the need for them. Omit the line when no later round is known.

**Name the evidence-settled decisions in the round header.** A decision whose evidence leaves only one viable answer gets no question. The round header lists each on one `Settled by evidence:` line, by id and plain name, with the answer and its Basis: `Settled by evidence: Q7 (log format), JSON lines, Basis: verified, src/log.ts:12`. Each takes its `Q<N>` and an `answered` register row with the resolution `answered-from-evidence: <answer>. Basis: <source>`. The user can reopen one by id: its row goes back to `open` and it is asked in full in the next round. Any decision with a live alternative is still asked. The quality bar is never settled by evidence: one the user has not stated is asked, and a recommended one is a decision question whose row stays `open` until the user answers, never a line here ("Ask the quality bar in round 1").

**Question pacing (`question_pacing`).** Pacing: resolve `question_pacing` once, before the first round or the page start, per [`${CLAUDE_PLUGIN_ROOT}/reference/config.md`](../../reference/config.md) "Convention-home keys", with `${user_config.question_pacing}` as its user layer (unexpanded or empty means unset; the default is `round`), and report the value and its layer in one line shaped `Pacing: <value> (<layer>)`. `auto` settles to `round` or `single` after the Step 1 survey and before the first round or the page start, and everything after reads that choice: `single` when the topic is broad and open-ended (many independent directions, little settled upstream, no spec or earlier answer to anchor on), `round` otherwise. State the choice and how to switch in one line ("Asking one at a time: this topic is wide open. Say 'give me the whole round' to switch."). `round` asks the frontier as one set. `single` computes the frontier the same way, then asks one question per message in blast-radius order: each message carries one question in the whole question layout, the `Held:` line when one applies, and the closing probe, with no topic header. Its round header keeps the `Scope check:` line `round.sh` printed, never one written by hand, and its `Later:` line names only topics outside this round's frontier: the frontier questions still to come in later messages are never named, previewed, listed or given as the reason this one goes first, in the header, in text above the round or in an alternative (the round check's `--pacing single` run: "Check the draft round for bare codes before it is shown"). One frontier is still one round: one round number and one `round-<N>.md` file, sent over several messages. A round fired from inside another workflow's phase ignores `single` ("Rounds fire at phase boundaries"). Register each question `open` in the message that asks it, and recompute the frontier after each answer, since an answer can prune or add questions. The user's request in the session ("one at a time", "give me the whole round") overrides it for that session. The page honors `single` too: the session posts the round with its first question and adds each later one after the one before it is answered ([`context/lane-page.md`](context/lane-page.md)).

`Q<N>` numbering is one counter per topic ([`context/question-shape.md`](context/question-shape.md), the `id` row). Take every new id from `bash "${CLAUDE_PLUGIN_ROOT}/surface/round.sh" next-id --ledger <memory_dir>/<topic-slug>/interview-checklist.md --count <n>`, `<n>` being the round's new rows (held, settled-by-evidence and commitment rows included; on the page lane add `--dir '<data_dir>'`); for a round, the same call with `--round`, `--limit` and `--rounds-dir` also prints its `Scope check:` line ([`context/routing.md`](context/routing.md) "The scope-check line"). Assign them in the order the round shows them; never pick an id by hand, fill a gap or renumber a row. With no Bash, take the highest number among the register's rows and the high ends of its `- gap |` lines, and count up from it. Close the round with one probe inviting a constraint that breaks the recommendations, worded "something else", never "anything else": "Is there something else that would change these recommendations?" (eval case `interview-closing-probe-something-else`). Put the note that the user may answer in any order before the probe. In the terminal lane an inline round is the last message of the turn that sends it and the probe its last line, because the user answers what the turn ends on: write its round file, run its checks and register its rows before it is sent (under `single`, each row in the message that asks it), and call no tool after it. A correction that changes a question already shown resends the whole round with the note in its header (under `single`, only that question, the note above it); any other note waits for the top of the next round. Wait for the answers before computing the next round. The recommendation+basis discipline holds per question. Inline prose carries the recommendation, its reasoning, AND the probe in one readable block; a card cannot.

**One verdict marker.** The `My recommendation:` line is the *single* verdict marker for the question. Never stack a second one: no standalone `**(RECOMMENDED)**` badge line above it, and no `(recommended)` tag repeated in the Alternatives list; the recommended answer is named once, on that line. The alternatives exclude the recommendation: none restates it.

**Context first, as much as the decision needs and no more.** Every question carries its own `Context:` block (its place: "Keep the layout whole"), so the user can decide from that question alone without scrolling back or asking what something means; the round-header restate never stands in for it. The block holds what drives the decision and nothing else; its items, which terms it defines inline and the one-claim-per-line sourcing rule are in [`context/question-shape.md`](context/question-shape.md) "Context", for every lane, and a claim the user stated cites `user, round <N>`. `Basis:` keeps its job as the label in the saved block: it names which of the Context sources the recommendation rests on, so the user sees at once whether it is grounded. Eval case: `interview-context-unfamiliar-term-upstream`.

**Alternatives carry their tradeoffs.** One option per bullet, never a run-on sentence or a table: what it would gain, what it would cost, and the source behind that, so it can be weighed against the recommendation. The recommendation names its own gain and cost the same way, in one sentence of its reason, so every option on the table shows both. A decision with only one viable answer is not asked: it goes on the round header's `Settled by evidence:` line (below).

**Keep the layout whole.** Every question opens with its title line, then its `Context:` block, before `My recommendation:` (or `Withheld:` or `Discovery:`), then `Alternatives:`, with a blank line after the title, after the recommendation block and after `Alternatives:`, and a `---` line between one question and the next. With emoji markers on, the title is `❓ Q<N>: **<title>**` and the recommendation `➡️ My recommendation:`; off, the same without the two markers. Keep a question's information in its own block: no terms table at the top of the round, no per-question alternatives table, and no closing summary table. A structural question's compact visual goes first inside its Context ("Visual-first for structural questions"). The `product` action states its own shape as a declared exception ([`context/product.md`](context/product.md) "Question shape").

**Save the full block; print it at the detail level.** The round file `round-<N>.md` ("Check the draft round for bare codes before it is shown") always holds the full block above, `Origin:`, `Basis:`, `Checked against:` and the `Source:` quote included. Resolve `question_detail` once, before the first round, per [`${CLAUDE_PLUGIN_ROOT}/reference/config.md`](../../reference/config.md) "Convention-home keys", with `${user_config.question_detail}` as its user layer (unexpanded or empty means unset; the default is `standard`); a request in the session ("show me the full detail") overrides it. In the terminal lane, the round you send is the output of `bash "${CLAUDE_PLUGIN_ROOT}/surface/round.sh" show --level <question_detail> <memory_dir>/<topic-slug>/round-<N>.md`, pasted verbatim: `full` prints the file as saved; `standard` drops `Origin:`, `Basis:`, `Checked against:` and the `Source:` quote's body (its link stays) and puts each alternative on one line; `minimal` also drops `Context:` and `Source:` and prints an alternatives count with `say "more Q<N>"`. Under `single` pacing, each message carries the round header and only that one question's block from the `show` output, never the other questions. "The whole question layout", wherever this skill asks for it, means a question's block printed this way at the resolved level, not the `full` level. No level hides the recommendation and its reason, a reused literal, `Withheld:`, `Discovery:`, `Second view:`, `Departs from:`, `Flips if:` or a `Commits you to:` part. A reply "more Q<N>" prints that question's full block from the file; "full round" prints the round with `--level full`. With no Bash, print the `standard` block yourself by the same rules.

**No undecided name, scope or design shown as settled.** A name, scope or design the user has not agreed to appears only as a recommendation inside a question, never as a working assumption in prose, a restate, or another question's Context.

**Source first, when the user has not read it.** When a question rests on text the user has not read (a doc, a post, a repo file), add the `Source:` block after the Context block and before `My recommendation:`: that exact text as a `>` quote, a link to its exact section, and one line on why that text makes this a question. The Brief carries the link, not the quote.

**A recommendation that fixes more than one decision lists every part.** When the recommended answer also settles other decisions (a design that picks a platform, a runtime, a credential, an identity), list each under `Commits you to:` with its own `Q<N>`. They are parts of the one recommendation, not a second verdict, and each is registered `open` at ask-time like any question. An explicit acceptance of the headline ("Q5 yes", "accept all recommendations") resolves each listed part to its recommended value (on the page, only the parts the user ticks); the user can overturn one by its number. When an accept-shorthand resolves commitment rows, name their `Q<N>` ids in one line. Choosing an alternative or rejecting the headline withdraws the parts, and any sub-decision the chosen alternative implies is asked in the next round. A sub-decision the recommendation assumes but does not list is not decided by any answer to the headline: list it, or keep it out of the recommendation. A question with a `Commits you to:` block is never asked through an `AskUserQuestion` card; on the page, its parts are the question's `commits` entries. How many ids the parts take differs by lane: [`context/loop.md`](context/loop.md) "Commitment rows" and "Commitment parts on the page".

**Emoji anchors (default on, still configurable).** Emoji markers: `${user_config.use_emoji_question_markers}` (unexpanded or empty means the default, on). With the emoji-markers setting on (the default), prefix the `Q<N>:` line with `❓` and the `My recommendation:` line with `➡️`; with it off, keep the undecorated shape above. Decoration of the existing single verdict marker, never a second one. Conversational rendering only: the ledger, register, and Brief stay plain, and `Q<N>` remains the answer handle. **Agree a term where it first appears.** Nothing is asked about terms before round 1. The question that first relies on a sourced term defines it in its Context with its source (`file:line`, URL, or `user, round <N>`), and registering that question adds the term's `proposed` row to the ledger's `## Terminology matrix`. Once the answers settle a term, restate it with its definition in one line at the top of the next message ("Term: billing account, the household that pays for several members (user, round 2). Confirm or correct it."). That restatement is a question, registered like any other at ask-time (`- Q<N> | open | round <N> | Agree the term billing account? |`); mark the matrix row `agreed` and resolve the register row only when the user confirms it, so the register gate holds an unagreed term. A row still `proposed` at Step 3 is confirmed in the closing summary's "Project glossary changes" group. A qualified name that cites its clash is a sourced term ([`context/term-clash.md`](context/term-clash.md)). A definition this session coins has nothing to cite, so it gets no row and no `Basis:` claim: record it in the shorthand glossary ("Name every code; define every term where it is used") and ask the user to agree it in a withheld question ("A withheld question carries no recommendation marker") in the round that first needs it. Its `Withheld:` line says the definitions are the session's own and only the user can confirm them, each Context line is labeled `judgment`, and it asks the user to confirm or correct them. Write a term only once it is agreed: in an engineering session through the inline vocabulary update ("Domain-aware behaviors"); without the glossary skill, or in a general session, the matrix keeps it and the session's durable output carries it (the Brief's `### Constraints` in an engineering session, the shared-understanding summary in a general one). **Name every code; define every term where it is used.** In every line the user reads (rounds, restatements, recaps, the page, labels, reports), show the human-readable name, never a bare code. When the name is short enough to stand alone, show only the name (`scoped change`, not `C3`); pair code and name (`C3: scoped change`, `question Q14, retry budget`) only where the code itself must be quoted, such as a question id the user answers by. `Checked against:` names constraints in words; the ledger may keep bare ids. When a round leans on session-local shorthand, a coined label, an abbreviation, or cross-repo jargon the user may not share, record it in the ledger's shorthand glossary and define it inline in each question that uses it (`head SHA (the commit the PR points at)`), so a reader with none of the session's knowledge can answer from that question alone. Self-contained is not simplified: keep the precise technical terms and register, and expand a code to its real name, never a metaphor or lay substitute (`pr-merge lane`, not `merge robot`); simplify only when the user asks (`/education:explain` (if enabled)). This session shorthand is one of the three glossaries "Domain-aware behaviors" names. Ledger shape: [`context/loop.md`](context/loop.md) "Session-shorthand glossary". Eval case: `interview-coded-terms-round-answerable`.

**Check the draft round for bare codes before it is shown.** In the terminal lane, write the drafted round to `<memory_dir>/<topic-slug>/round-<N>.md` (one file per round, kept: `/planning:audit-answers` reads each question's Context from it). **Partial-round resolution.** The user may answer any subset, in any order, in one reply. Unanswered questions stay OPEN on the frontier. NEVER silently resolve an unanswered question to its recommendation; the auto-guard applies inside rounds too. Honor accept-shorthands: "accept all recommendations" resolves the whole round to the recommended answers; "yes to Q5" / "Q5–Q7 yes" resolves that subset. **Offer an answer audit after accept-all rounds.** Resolve `answer_audit_rounds` per [`${CLAUDE_PLUGIN_ROOT}/reference/config.md`](../../reference/config.md) "Convention-home keys" (no `userConfig` layer; the default is `2`). **A restated open question keeps the whole contract.** Whenever an open question is shown again for an answer (unanswered from last round, a list after async input, a resume), it uses the identical layout, printed from its saved full block at the resolved detail level: its Context, its recommendation with its reason and evidence, and its alternatives. Never a condensed form, such as a table that keeps the recommendations and drops the basis and alternatives, unless the user asks for one or the summary covers answered items only. A one-line drift reminder that names open questions by id and plain name (below) is a pointer, not a restatement; asking any of them again uses the whole question layout.

**A hedged reply resolves only the headline.** A reply given with doubt ("yes?", "I think so", "probably") resolves at most the headline of the one question it can be tied to, never that question's `Commits you to:` rows and never the rest of the round. A hedged accept-shorthand ("accept all?") is not an accept-shorthand. Record the headline with a `hedged:` resolution, keep its commitment rows `open`, and echo back in one line what the headline commits to and which rows are still open. A hedged reply that cannot be tied to one question resolves nothing: restate the open rows.

**Register at ask-time; a reply that does not answer is not an answer.** The moment a round is asked, before any reply, write one `open` row per question into the ledger's open-question register. Then, after EVERY user reply and before doing anything else, check the reply against the register's `open` and `discussing` rows and restate any it did not address, in one line, even when the reply changed the subject entirely. The one exception is the acceptance-criteria coverage prompt, which gets no row even inside a round while every real question beside it does ([`context/coverage-prompt.md`](context/coverage-prompt.md)). **Visual-first for structural questions (default, not on-request).** When a question concerns structure, file/folder layout, before/after states, naming shapes, schema or flow alternatives, and a compact visual (fenced tree, diff, small table; roughly ≤30 lines) can carry it, LEAD with the visual and hang the question off it. A paragraph describing a tree is much harder to verify against the user's mental model than the tree itself; the visual IS the question. Before/after pairs beat single-state snapshots when the question is a migration. Skip only when no compact visual exists (genuinely abstract trade-offs) or when it would blow past ~30 lines. **Dialogue: the user drives too.** They may push back or reframe a decision (e.g. "what's hardest to roll back from?"). When they introduce a new axis, **reversibility** is the most common for V1, re-rank the options on it and REVISE your recommendation out loud, stated as old → new → why, where new may be a withheld open question ([re-emitting a changed recommendation](../../context/recommendation-basis.md)). **Talking a question through.** When the user asks to discuss a question rather than answer it ("let's discuss Q3"), set its register row to `discussing` before the discussion starts. Discuss it, then ask it again in the whole question layout with the recommendation revised as old → new → why (when the discussion leaves it unchanged, say so and why). The row leaves `discussing` only on an answer to the question asked again; the register gate holds a `discussing` row exactly as it holds an `open` one. `discussing` applies to the terminal lane; on the page the row stays `open` ([`context/loop.md`](context/loop.md) "Discussing"). The same holds when a recommendation changes after the user asks for context: re-ask the question in the whole question layout, its Context now carrying what they asked for, with the old and new recommendation and the reason. Default V1 lens: prefer the most *reversible* start; defer the irreversible/expensive as an explicit out-of-scope decision, never a silent assumption.

**Facts are yours; decisions are the user's.** A *fact*, a path, a current value, an existing pattern, what a file already does, is resolved from the environment (Grep/Read/Glob) and STATED, never asked; spending a question on what the code already answers is friction, not interview. Every candidate question first passes the self-answer step, [`${CLAUDE_PLUGIN_ROOT}/context/self-answer.md`](../../context/self-answer.md): prior owner decisions, then codebase, ADRs, docs and history, then connected tools including MCP servers, then research for external facts. A fact it finds is stated with its `Basis:` and source tag and gets no register row (a contact address or identity still gets one: "Recommended answers"); a fact only an unconnected system holds gets one offer to connect it. Register mechanics: [`context/loop.md`](context/loop.md) "Self-answer gate". The environment is not only the working tree: when a task NAMES an external repo or resource, a sibling checkout under a known repo root / workspace layout, or an `owner/repo` reachable through its host, that is a resolvable fact too, so check the filesystem layout and query the repo host directly (e.g. `gh` for a named `owner/repo`) before defaulting to a user question. Cue, not mandate, except where a recommendation is consequential (next paragraph): there grounding is mandatory. Otherwise resolve what's cheaply resolvable, and don't turn every named mention into a research project; a recommendation of any kind still cites a fact, so a question the cheap read leaves with none waits for a lookup or is asked withheld, as [`context/lookups.md`](context/lookups.md) "Held questions" says. A *decision* with a live alternative and no environment answer ALWAYS goes to the user; never resolve one on their behalf. One whose evidence leaves only one viable answer is settled by evidence ("Name the evidence-settled decisions in the round header"); one the owner already ruled on is answered by the quoted ruling (the self-answer step). **Gap triage and lookups.** Before round 1, sort every unknown into a lookup, a discovery question or a decision question; that triage, the intake round, when a lookup and every other pass around the interview runs, what a lookup's brief carries, which questions it holds (the rest are asked now) and how a fact that contradicts an answered row reopens it under its own number: [`context/lookups.md`](context/lookups.md).

**Check a fact the user states.** When the user states a fact about the code or the system ("only the importer calls this", "we never delete rows"), check it with Grep, Read or Glob before a recommendation rests on it. A constraint stated this way is still written `confirmed` at once (Step 2, "Keep a running constraint ledger"). When the code disagrees, show the evidence (`file:line`) and ask which holds, registered like any question, then revise the row on the answer; never let the stated version stand over the code silently.

**Run it to settle it.** When a question turns on what the system does and a cheap, read-only run would show it (an existing status or query command, a `--help`, a dry run), run it and state the result as a fact with the command as its source instead of asking. A run that needs the user's environment is offered as a registered question. A run that writes, deploys or costs money is never made: it stays a question.

**Ground before recommending.** Lightweight codebase gate per question (Grep/Read/Glob). If a recommendation needs more, external best-practice, a library API, deeper exploration, dispatch or do the lookup (research/exploration capability, or inline), then recommend grounded. No recommendation rests on training recall or convention alone ("Recommended answers"), and a **consequential** one (cross-repo, shared infrastructure, irreversible, or security) clears the higher bar: ground it in the affected code plus its consumers, and in external research that reads official docs first for a tool or API and the canonical source for a design pattern, never a pattern's popularity alone, and notes recency and dissent. That lookup runs and holds as [`context/lookups.md`](context/lookups.md) says. The contract this plugin ships, the bar and its three outcomes, is [`${CLAUDE_PLUGIN_ROOT}/context/recommendation-basis.md`](../../context/recommendation-basis.md).

**Before presenting an option that adds a mechanism** (a branch, workflow, ruleset, app, service, dependency or check), name the existing control that already covers the same risk, saying whether you read its enforcing source or only a document (one read only in a document is labeled `documented, unverified`, never `verified`: [basis contract](../../context/recommendation-basis.md) "Three outcomes", and every other Context line or recommendation that states or relies on that control carries the same `documented, unverified` label), and recommend dropping the mechanism if one does; a security control (the protected classes of `/overengineering:justify` (if enabled)) is never dropped without the user's decision, and an abstraction for a stated, known repetition stays when it passes the `reference-dont-duplicate` tests of the standards index (resolved per [`${CLAUDE_PLUGIN_ROOT}/reference/standards-contract.md`](../../reference/standards-contract.md) "Resolution ladder"). For a non-trivial new mechanism, run `/overengineering:justify` (if enabled) on the proposal.

### Recommended answers

For EVERY question but a withheld or discovery one (below), propose an answer grounded in observed evidence. User confirms (fast) or corrects (faster than explaining from scratch). **Every recommendation shows its evidence, never bare judgment.** Each fact the answer rests on sits in the question's Context block with its source (a `file:line`, a URL fetched this session, a session-transcript finding, or tool output); the `My recommendation:` line's reason says why those facts together lead to this answer for this user and ends with its evidence label and source, which every detail level prints, and the saved block's `Basis: verified` line names which of those sources the answer rests on. A `judgment` label alone is not a valid basis in this skill, for a consequential question or any other: the interview holds a stricter bar than the shared [basis contract](../../context/recommendation-basis.md), which still allows that label elsewhere. When only judgment is available, research first (the self-answer step, and "Ground before recommending" for a consequential question); when research leaves no fact to cite, ask the question withheld (below). The same holds for each Context fact the recommendation rests on: one labeled `judgment` alone is researched to a source or the question is asked withheld. The printed label covers every fact the reason relies on, not only the first: when the reason states a fact no Context line sources, or its deciding step rests only on a `judgment` line, that fact is researched to a source or the question is asked withheld, whatever its other facts cite. When drafting, gloss each coined term and each `P<n>` or `Q<N>` id the question names in its own words where it appears ("Name every code; define every term where it is used"). Like `Checked against:`, the basis is part of the recommendation, not a second verdict marker and not part of the Context block; on a card the facts, the reason and any `Flips if:` line ride inside the option's basis text, and on the page the facts go in the question's `context` while the basis text names their sources and carries the reason and any `Flips if:` line, and the `Flips if:` line counts toward the basis prose's 3-sentence budget ([`context/surface.md`](context/surface.md) R12). Mark each recommendation once. In an inline round that marker IS the `My recommendation:` line (one verdict marker, never a second stacked badge); in an `AskUserQuestion` card it is the option tagged **(RECOMMENDED)**. Detail in [`context/loop.md`](context/loop.md) "Frontier rounds".

**State a reused value literally, with where it was read.** When a recommendation reuses an existing value (an email address, account, subscription, region, secret name, repository), the question states the literal value and its source (a `file:line`, tool output, or the connected system that holds it), for example "alerts go to `ops@example.com`, the `budgetContactEmail` in `Pulumi.production.yaml:12`". "The existing X" or "the same address as Y" alone is not allowed: an accepted round would then confirm a value the user never saw.

**Contact addresses and identities are owner-reserved facts.** An email address or other notification target, a login, or a user or service identity that anything will be created with or sent to is the user's to confirm, even when the environment holds a candidate; it is the exception to "Facts are yours" above. Propose the candidate you found as the recommendation, with its literal value and source, and register the question like any other. The row stays `open` until the user confirms that literal, so the register gate holds the contract and nothing is created with the value before then; an accept-shorthand confirms it only when the question showed the literal. In `lock` such a value is a gap: STOP and surface it; in `auto` direct synthesis it makes the path Mixed. Unattended, it is `blocked` with **arbiter: USER-RESERVED**, per [`context/loop.md`](context/loop.md) "Unattended path".

**Word each question so yes accepts the recommendation.** When the recommendation is negative, ask "Should X stay out of this change?", never "Should we do X?" answered "No", because "Q<N> yes" and "accept all" must both mean the recommended answer.

**A withheld question carries no recommendation marker.** A question research cannot settle is an exception to "every question carries a recommendation", and its recommendation is **withheld**: a recommendation with no fact to cite would be bare judgment, consequential or not. It is asked open, never on a card, with a `Withheld:` line naming the evidence that would settle it in place of the `My recommendation:` line, its `Origin:` line, any `Checked against:` line, its `Basis:` evidence list and any `Flips if:` line; no option is tagged **(RECOMMENDED)**, and on the page its `recommendation` field carries the `Withheld:` text. It is registered like any question.

**A discovery question carries no recommendation.** A question the gap triage before round 1, or the drafting of any later round, sorts as discovery ([`context/lookups.md`](context/lookups.md)) asks what only the user knows (the problem and why, who it is for, the scope, where they start, where it heads), so a proposed answer would put words in their mouth. It is asked open: its Context block, then one `Discovery: <what the answer settles>` line in place of `My recommendation:` and every line after it, with no alternatives, never on a card. It is registered `open` with `kind:: discovery`, and no accept-shorthand resolves it. A choice its answer leaves open (the user cannot judge the quality bar) is a decision question in the next round. The quality bar is a discovery question only when the survey holds no evidence for one ("Ask the quality bar in round 1").

### Domain-aware behaviors

When the task touches domain concepts, these behaviors activate during Q&A. The probing behaviors run in any session; the two that write repo artifacts, **inline vocabulary update** and **ADR**, are engineering-only (per the Step 1 domain classification), so a general session, gated to a shared-understanding summary, never mutates a project glossary or proposes an ADR.

**Three glossaries, and who writes each.** The *session shorthand* is the ledger's list of this session's own codes and coinages ("Name every code; define every term where it is used"); the interview writes it and it is discarded with the ledger. The *project glossary* is the project's ubiquitous language, owned by `/domain-driven-design:ubiquitous-language` (if enabled); the interview writes an agreed term to it only through the inline vocabulary update below, after the user confirms the term's restatement ("Agree a term where it first appears"), never in batch at the end. The closing summary's *Project glossary changes* group (Step 3) lists what this session added to, renamed in or removed from the project glossary, and a rename lands as its own reviewed change.

**Whether the interview writes them (`domain_docs`).** Resolve `domain_docs` once, before the first write, per [`${CLAUDE_PLUGIN_ROOT}/reference/config.md`](../../reference/config.md) "Convention-home keys" (no `userConfig` layer; the default is `auto`), and report the value and its layer in one line. `auto` writes the glossary entry and hands decisions to the ADR skill as below; `ask` asks once per resolved term or ADR-worthy decision, as a registered question, before invoking the writer; `off` writes neither and records the term or decision in the resolution field of the register row that resolved it. A request in the session ("don't touch the glossary") overrides it for that session.

- **glossary challenge**. Two triggers share one response, a probe: any domain term the user uses two ways, and any term that collides with an existing definition
- **domain scenario exploration**. Test where one concept ends and the next begins with a concrete case of your own making ("a member returns one volume of a two-volume loan: is the loan open or closed?")
- **scenario comparison**. When two or more candidate terms or models compete for one question, or the user asks for one, put a scenario comparison in the question's Context: scenarios as rows, candidates as columns, the sentence each candidate forces, then where each helps, where the choice makes no difference, and what each costs. Shape and rules: [`context/scenario-comparison.md`](context/scenario-comparison.md)
- **scenario walk**. When the user calls something unclear, or a question rests on a term the glossary lacks or uses two ways, offer (never force) numbered concrete scenarios inside one question's Context, each ending with its own recommendation and the term or rule it forces, answered per scenario. Their ids (`S<M>`, written `Q<N>.S<M>` once the ledger holds sweep rows), triggers, shape and recording: [`context/scenario-comparison.md`](context/scenario-comparison.md) "Scenario walk"
- **inline vocabulary update** *(engineering sessions only, per `domain_docs`)*. When the user
  confirms a term's restatement ("Agree a term where it first appears"), invoke
  `/domain-driven-design:ubiquitous-language curate` (if enabled); otherwise the ledger's
  `## Terminology matrix` keeps the agreed term. That skill owns discovery-first
  placement, the consumer's
  file shape, purity, canonical terms, rejected synonyms, and known-context routing; the interview
  resumes after the update
- **ADR** *(engineering sessions only, per `domain_docs`)*. Each round's numbered **Decision record** step ([`context/loop.md`](context/loop.md) "Frontier rounds", item 8) hands every resolved decision about the system that weighed a real alternative to `/architecture:adr` (if enabled) via the Skill tool. That skill owns the admission test, convention discovery, the no-convention offer and the write; the interview carries no copy of the test and never prescribes a location or format. Without the `architecture` plugin, the decision is recorded as an ADR candidate in its register row

## The interview loop

Five steps. Step 1 (Survey) runs every action. Step 1.5 (Auto-detect) runs on `auto` only. Step 2 (Q&A loop) runs on `me` or `auto`-routed-to-Q&A. Detail in [`context/loop.md`](context/loop.md).

### Step 1. Survey before you ask

Spend the first turn grounding yourself. Read the project's `CLAUDE.md` / `AGENTS.md` if not already in context, Glob/Grep keywords, scan `git log --oneline -20`, climb to the nearest domain-vocabulary file, list relevant project rules, check the topic's memory slice `<memory_dir>/<topic-slug>/` (default `.work/`) for a prior PLAN.md / PRD / design artifacts and for exploration / research artifacts. Read the team's probe topics, the `## Probe topics` section of `<home>/planning.md` ([`${CLAUDE_PLUGIN_ROOT}/reference/config.md`](../../reference/config.md) "Probe topics"): each topic the task touches gets a question in the rounds unless the survey already answers it; at the prototype bar, a topic outside the scoping questions is named as deferred instead.

Survey output: one paragraph "Here is what I see in the repo."

**Classify the domain** from what the survey shows. *engineering* (a build or behavior-change task, or a technical subject that yields a build artifact) or *general* (a decision or idea with no build surface). The deciding signal is the **task/build surface itself**, not the working directory: a general decision raised from inside a code repo is still general, and the engineering machinery must never engage on cwd alone. Repo/cwd is context that breaks the tie only when the task surface is genuinely indeterminate. Then lean engineering inside a code repo, else general. This is inferred, never asked; honor any explicit user override. The domain governs which machinery engages and what the session produces (see Purpose "Domain-routed"); it is orthogonal to the `me`/`auto`/`lock` action.

**Engineering sessions only**. If a prior PLAN.md Brief exists, ask whether to **resume**, **revise**, or **start fresh** (the latter appends a dated scope-change note to the top of the Brief capturing why before rewriting. The Brief is never committed, so that note is its only history; the copy published to the pull request body or the linked issue carries it). On **resume**, before the first resumed round, resolve the surface through `${CLAUDE_PLUGIN_ROOT}` again (never an absolute path copied from a handoff) and run `round.sh --dir '<memory_dir>/<topic-slug>/interview-surface' doctor --ledger <ledger>`; it names each element the running version needs and the ledger lacks. A general session, the `scope` action or the `restate` action never creates or edits a PLAN.md Brief, so it skips this prompt.

Then route per action.

### Step 1.5. Auto-detect (default action only)

For `auto`: classify intent against `context/loop.md` "Step 1.5. Auto-detect" criteria. Three outcomes:

- **Synthesize directly** (clear) → skip Step 2; proceed to Step 3 (confirmation gate), then Step 4 (Persist)
- **Q&A loop** (fuzzy) → continue to Step 2
- **Mixed** → ask the residue (one round. The few open questions together), then synthesize; proceed to Step 3, then Step 4

**Auto-guard. Never decide an interactive choice for the user.** Synthesize-directly (and the Mixed path's "synthesize the rest") applies ONLY to decisions with a verifiable answer (codebase-resolvable) or an unambiguous conventional default. When a remaining decision is genuinely the user's, a design choice with real tradeoffs and no codebase answer, do NOT fold it into the Brief. STOP and either ask it inline (a residue round) or offer to switch: *"This is a real design decision, not mine to pick. Answer it, or want me to run `/planning:interview me` and drive every open branch to a decision?"* Silently capturing such a choice as an assumption is the failure mode this guard prevents.

**Unattended path: the guard holds, the run does not idle.** `/planning:interview` can be reached with no human to answer (a loop, a spawned worker, another skill's chain). The condition is **declared by the caller, never sniffed**: the caller knows whether a person is there to answer, and the skill would only be guessing. Unattended, codebase-resolvable and unambiguous-conventional decisions resolve as usual and are recorded `auto-resolved (unattended)`; a decision genuinely the user's is recorded `blocked` in the register, written to the Brief's `### Deferred questions` with **arbiter: USER-RESERVED**, and named as a blocker in the output. That extends the auto-guard rather than excepting it. The guard forbids the choice *disappearing*, and a named blocker is the choice made maximally visible. Stop on blockers; never wait indefinitely, and never read absence of objection as confirmation. Full ladder: [`context/loop.md`](context/loop.md) "Unattended path".

For `me` / `me <topic>`: skip Step 1.5 except loop.md's "Problem first" paragraph, force Q&A.
For `scope` / `scope <topic>`: skip Step 1.5 except loop.md's "Problem first" paragraph; with no topic, scope the current task. Run Step 2–3, then the **`scope` persist path** below instead of the engineering Brief in Step 4. Do not offer `/planning:plan` handoff; stop after returning decisions.
For `lock`: skip Step 1.5 AND Step 2, synthesize directly. If a gap surfaces mid-synthesis, STOP and surface; do not fudge.

### Step 2. Drive the frontier-rounds loop

Run rounds: restate working understanding → compute the frontier (every open question whose prerequisites are settled) → ask the whole frontier as one numbered set → capture the answers → recompute. Categorize each open item as resolvable / blocked / defer-with-assumption / defer-fully. The restate is also the **session-hop anchor**: after a handoff, resume, or long gap it re-establishes the decided set and this round's stakes before any question, so a returning reader is grounded without re-reading the whole ledger.

Full surfacing-question taxonomy + categorization heuristics in [`context/loop.md`](context/loop.md).

**One blind recommender drafts each round's recommendations.** Once a round's decision questions are drafted (Context, options, your own answer), dispatch the plugin's `interview-recommender` agent once for the round ([`${CLAUDE_PLUGIN_ROOT}/agents/interview-recommender.md`](../../agents/interview-recommender.md)), handing it each decision question with its options unranked and its Context facts, the constraint ledger, the settled decisions with their answers and the self-answered facts; withhold the conversation and your own answers. Its answer is the question's recommendation: its basis feeds the reason and `Basis:`, and any fact that basis cites the Context lacks is added to the Context with its source; its `flips if` feeds the `Flips if:` line, and a fact any `Second view:` line names that would change a question's recommendation also goes on that question's `Flips if:` line; and a question it withholds is asked withheld, with no `Second view:` line, since a withheld question shows no answer. When your answer differs, show it on one `Second view: <your answer and why, in one sentence>` line under the recommendation; when the recommendation departs from a settled decision, show one `Departs from: Q<N> (<plain name>): <its sentence>` line. No detail level hides either line. A round with no decision question runs no recommender. With no Agent tool, draft the recommendation yourself and show no `Second view:` line.

When the resolved lane's spoke shows Step 3's confirmation gate outside this conversation, follow that spoke for where it is shown; the gate and its halts are unchanged.

**`me` mode** maintains a **decision-tree ledger**. One live checkbox per branch, ticked on resolve, remaining-open surfaced periodically (not every turn. Keeps the flow clean like the inline format). Persist each answer the moment it locks in (Step 4), loop until zero open consequential branches. Ask via the inline format (Stance "Relentless mode"). Ledger shape + per-round mechanics + reversibility-lens question shape in [`context/loop.md`](context/loop.md) "Decision-tree ledger".

**Keep a running constraint ledger.** The ledger's `## Constraint ledger` section holds one row per constraint. Every constraint the user states is written at once as `confirmed`, the moment it is stated, never batched to Step 4; a constraint taken from an upstream artifact is `inherited` (a prior Brief, a PRD, a design resolution). Every recommendation names the constraints it was checked against on one line under `My recommendation:`, in words, `Checked against: V1 ships without SSO; no new runtime dependencies` or `Checked against: none`; the ledger's `C<N>` ids stay in the ledger. That line is part of the recommendation, not a second verdict marker and not part of the Context block; a lane spoke may say where it sits on that lane. A card has no recommendation line, so a question goes on an `AskUserQuestion` card only when its line would read `Checked against: none`; one that cites a constraint is asked in prose. An `inherited` constraint the Brief relies on is asked as a register row at ask-time: the answer flips its tag to `confirmed`, and unattended it takes the ladder (`blocked`, USER-RESERVED, when it is the user's call). In `lock` a relied-on inherited constraint is a gap: STOP and surface it (Step 1.5); in `auto` direct synthesis it makes the path Mixed and is asked in the residue round. Row shape: [`context/loop.md`](context/loop.md) "Constraint ledger".

**Re-ground open recommendations before they are shown.** On resume, and before a queued round is shown, check each open recommendation: its `Basis:` cites a source read this session or a constraint row, and it does not rest on an artifact the constraint ledger now excludes. A consequential one that fails is held for a lookup before the user sees it ([`context/lookups.md`](context/lookups.md) "Held questions"). When the user adds a constraint mid-interview, write the `confirmed` row at once and re-check every open recommendation's `Checked against:` line against it; revise the ones it changes and say which.

**Composed artifacts are candidates.** A design from explore or research output, or read from an existing implementation, is a candidate, never a recommendation, until re-derived against the constraint ledger: check it against every row, recommend only what survives, and name the rows on its `Checked against:` line. A research or exploration brief dispatched mid-interview carries the constraint ledger verbatim.

**Label evidence by when it was true.** When a recommendation rests on historical evidence (past metrics, merged PRs, an existing implementation) and the survey finds a recent process change or cannot tell, label each finding `past`, `current`, or `intended` before a recommendation rests on it. A process change is one the survey finds (a changelog, commit, ticket, or user statement dated after the evidence window) or cannot rule out. State or ask any currency you cannot establish; past-only evidence never alone grounds a recommendation.

**What, not how: the mechanism tripwire.** "Does not plan implementation" has a trigger. When a question or its recommendation names a mechanism (a tool, an API, a credential or token scope, a runtime, a platform per step), ask once whether the user wants mechanism-level decisions settled now or at planning. Ask it in the same round as the first mechanism-naming question and register it like any other question. Its Context names the question that named the mechanism, and its `Basis:` cites the fact behind that mechanism in any form "Recommended answers" allows (`Basis: verified, user, round 1: deploys already run through one CI pipeline`); neither cites this rule or this skill, which the user cannot check. With no such fact, ask it withheld. Until it is answered, recommendations carry no mechanism part. When the answer is "at planning", no later recommendation fixes a mechanism, and every still-`open` mechanism row, commitment rows included, becomes `deferred`: carried to the Brief's `### Deferred questions` under the arbiter rule in an engineering session, listed as deferred in the shared-understanding summary in a general one. When the answer is "now", write `C<N> | confirmed | mechanism decisions settled in this interview | user, round <N>` at once, and the Brief's Constraints records that this topic overrides "does not plan implementation".

**Sweep for assumptions before Step 3.** In `me` and `auto` with a register, including the `auto` Mixed path after its residue round, the loop ends with a fresh-context assumption sweep. Once no open question remains on the frontier, and before the Step 3 register gate and confirmation gate, dispatch a non-fork sub-agent to inventory undecided details, hidden defaults, contradictions, and hedged or free-text rows across the ledger, the recommendations, and any composed artifacts. It reports every finding, with no severity, confidence or blocking cut; the disposition pass is the filter, and records each item's outcome: you turn each item into a register row at the next id from `round.sh next-id`, a stated fact, or, for hedged rows, a line in the confirmation restate. Any `open` row it adds returns the run to Step 2, and the next sweep covers only what the new answers changed; Step 3 is reached when a sweep adds no `open` row. A run that asked no question skips it, and so does `lock`; unattended, an item that is the user's decision is `blocked`. The acceptance-criteria coverage prompt is never a sweep item ([`context/coverage-prompt.md`](context/coverage-prompt.md)). Scope, item shape, disposition and the sweep-round label: [`context/assumption-sweep.md`](context/assumption-sweep.md).

### Step 3. Recognize the stop condition

Stop when no question is left to ask. Every unknown the task depends on resolved OR captured as named assumption. The user can describe the goal in one paragraph without contradicting the constraints, and acceptance criteria are testable. The coverage prompt has been asked once and answered ("neither applies" counts), or skipped and reported unexamined per [`context/coverage-prompt.md`](context/coverage-prompt.md). Don't stop early on impatience; don't keep asking past the stop condition.

**Register gate.** Before persisting the Brief or summary, or handing off, run the register through its mechanical check. That no question is left to ask is a judgment, and this is the part of it a script can decide. **Ledger only here**: the Brief does not exist yet (Step 4 writes it), and `--brief` names a file it requires to be present.

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-open-questions.sh" \
  --ledger <memory_dir>/<topic-slug>/interview-checklist.md
```

Exit 1 (a row is `open`, `discussing` or `superseded-by-plan`, or the verdict carries `stale=<n>`) and exit 2 (ungradeable) both HALT. Resolve or explicitly retire an `open` row and re-run; a `stale=<n>` row, of any status, was not checked against the constraints its resolution's `stale::` tail names, so revise or reconfirm it against them, export the ledger again and re-run; a `superseded-by-plan` row leaves only on the user's reply to it ([`context/loop.md`](context/loop.md) "Superseded by plan"). Never lock a Brief or summary over a non-zero exit; that is the reported failure restated. **A run that asked no question wrote no register, has nothing to gate, and skips this**: `auto` routing to synthesize-directly with no open decision. `lock` always writes its problem row, so its register gates. The carve-out is about the absence of questions, never about which action produced it: the moment ANY question exists. Asked, surfaced mid-synthesis, or blocked unattended. A register exists and the gate applies. The `--brief` cross-check runs in Step 4, once there is a Brief to cross-check against; it also exits 1 with `brief=unconfirmed` while the Brief is stamped `Restatement: UNCONFIRMED`. The gate reads only that stamp, so it cannot see a Brief edited after a Confirm: after such an edit, post a new `restate`, get a fresh Confirm and export again.

**The acceptance-criteria coverage prompt is not a question for this purpose**: it writes no register row and does not by itself bring this gate into scope, and no other question, whether asked beside it or later in the session, shares that exemption ([`context/coverage-prompt.md`](context/coverage-prompt.md)).

**Confirmation gate (`me` and `auto`):** that no question is left to ask does not end the interview on its own. Before persisting the contract or handing off, restate the shared understanding, opening with the one-line problem, and get the user's explicit confirmation that it is reached. Do not act on the interview's output until they confirm. `lock` confirms the problem with one question, registered like any row; its invocation confirms the rest (its STOP-on-gap rule still applies).

**Where the one-line problem comes from.** Take it from the ledger's `## Problems` section or a register answer that states it; when neither records one, say the problem is not stated, never write one of your own.

**Closing summary (`me` and `auto`).** Before the recap, the restatement groups what was agreed:

- **Project glossary changes** *(first)*: every project-glossary term added, renamed or removed ("Domain-aware behaviors" names the three glossaries). When any term is new or renamed, this group is the first step after the interview: the glossary change, and for a renamed term `/docs-hygiene:rename-references <old> to <new>` (if enabled) (otherwise the summary lists the references to sweep by hand), land as their own reviewed change before `/planning:plan` and `/work-items:decompose` (if enabled), so the spec and tickets name only the settled terms.
- **Decisions:** for each decision changed since its read-back, what it does in one clause; then one line counting the rest.
- **Out of scope:** every item not already recorded as an accepted answer (those the recap carries), with where it goes (an issue, the PRD, later).
- **ADR verdicts** *(engineering sessions only)*: one line per decision, all of them, naming it in a few words with its verdict and the part of the "Admission test" of `/architecture:adr` (if enabled) it passes or fails, taken from the round's Decision record step ([`context/loop.md`](context/loop.md) "Frontier rounds", item 8): an ADR recorded with the part it passes (that step's invocation asks the skill to name it), the part the skill said it fails, or, for a decision never handed over, that no real alternative was weighed or that it is about scope or process. Where that step recorded an ADR candidate instead (`domain_docs: off`, no `architecture` plugin, or a handoff the user declined under `ask`), the line reads `ADR candidate, not checked`. The interview carries no copy of the test and never applies it itself.

The user can overrule a verdict in the same reply ("Q12: record it"). That hands the decision, its rationale and its alternatives to `/architecture:adr` (if enabled) via the Skill tool, saying the user asked for the record (under `ask` the overrule is that answer); under `domain_docs: off`, or without the `architecture` plugin, it is recorded as an ADR candidate in the decision's register row instead. With no register row to hold it (no ledger on disk), state the ADR candidate in full in the reply: the decision, its rationale and the alternative it rejected.

**Recap and procedure check (`me` and `auto`).** Before asking for confirmation, the restatement carries a Q&A recap: one line per `Q<N>` in the ledger's `## Open-question register`, shaped `Q<N> <status>: <question text> (<resolution>)`, generated from the register on disk, never from the transcript, so it survives a compaction. Generate it with `bash "${CLAUDE_PLUGIN_ROOT}/surface/round.sh" export-ledger --recap --ledger <memory_dir>/<topic-slug>/interview-checklist.md --out <memory_dir>/<topic-slug>/recap.md`, which reads the ledger alone and takes no `--dir`. Paste the contents of `recap.md` verbatim in place of a recap of your own: no paraphrased or hand-shortened line, and no HTML or collapsible block, which this conversation shows as raw tags. Each recap saves its rows beside the ledger (`interview-checklist.last-recap.json`, overwritten each time). After the first confirmation, add `--changed`: the recap then lists only the rows changed since the last recap, plus one line counting the rest by status; a lane spoke may keep the full recap on its own surface. **When every answer was accepted as recommended or confirmed after its read-back** ([`context/loop.md`](context/loop.md) "Drift check"), save a recap with the command above once each round's read-backs are confirmed, without pasting it, so the first confirmation pastes the `--changed` recap too: it lists only the answers changed since, with one line counting the rest. The restatement adds the intent, each `hedged:` row ([`context/loop.md`](context/loop.md) "Hedged flag") and each stated assumption the user has not yet seen, and, outside the ADR verdict lines, does not re-list the unchanged accepted answers (eval evidence: `interview-final-brief-changes-only`). Then run the procedure check beside the register gate, ledger only, and cite its exit code and `procedure=` field as the evidence that the procedure ran, never your own account of it:

```bash
bash "${CLAUDE_PLUGIN_ROOT}/scripts/check-open-questions.sh" \
  --ledger <memory_dir>/<topic-slug>/interview-checklist.md --procedure
```

A non-zero exit HALTS the confirmation request; stderr names each defect (a round missing from the register, a retired row with no resolution). Fix the ledger and re-run. One exception, only on a lane whose spoke says its restatement box offers commitment ticks: an exit 1 whose only `open` rows are accepted questions held open by unticked commitments (the rows that lane's status command lists as accepted, to confirm) lets the restate go out, because that box offers those ticks. Any other defect still halts it, and the Step 3 register gate still holds those rows until they are ticked. It checks only what a file can show. Not checked, and not implied by a green exit or by the recap: whether the Step 1 survey grounded the questions, whether the domain was classified, whether register rows were written at ask-time rather than answer-time, and whether the frontier was recomputed between rounds. `/planning:audit-answers` adversarially re-validates the answers; the recap shows the user the Q&A and the check shows the procedure ran, and neither composes nor duplicates it. A run with no register skips both.

**Close the restatement with an active request.** When the restatement goes out in this conversation, it ends by asking the user to confirm it or to name the `Q<N>` numbers of the items to change, for example "Confirm this, or name the Q numbers to change." A run with no register asks the user to confirm it or say what to change. Never close on a yes/no check ("Sound good?", "Does this look right?"). When the recap command or the procedure check cannot be run (no Bash in the session), the restatement still goes out with that gap named in one line and no hand-written recap in its place; it is never replaced by setup questions or a request to run them. A check that ran and exited non-zero still halts, as above. Eval evidence: case `interview-final-confirm-active-reply`.

**`me` mode tightening:** "captured as named assumption" is NOT a valid stop for a *consequential* branch. Drive it to a decision (a decision MAY be "defer to post-V1", but it must be explicit and surfaced, never silent). The stop condition is an **empty decision-tree ledger** plus the confirmation gate. Not a question count.

### Step 4. Persist the Brief

Derive `<topic-slug>` from the task or current branch name (kebab-case, ≤40 chars, shared with `/planning:prd`, `/planning:design`, `/planning:plan`). The Brief (`PLAN.md`) and the working ledgers land in the memory slice `<memory_dir>/<topic-slug>/` (default `.work/`), per the lifecycle artifact protocol [`${CLAUDE_PLUGIN_ROOT}/reference/artifact-protocol.md`](${CLAUDE_PLUGIN_ROOT}/reference/artifact-protocol.md). *What* gets persisted follows the Step 1 domain classification.

**The memory slice is not a durable home.** It self-ignores and never reaches git, so it is lost with the checkout. Durable outcomes go to the pull request body or the linked issue: a decision that passes the ADR admission test also becomes an ADR, and a follow-up becomes a tracker item. That close-out belongs to `/planning:plan`. So when the user asks where to keep something past this branch, never offer the memory slice: name the destination (the PR body, the linked issue, an ADR, or a tracker item), and the slice holds the Brief only until it is published there.

**General (non-engineering) sessions** persist a shared-understanding summary, the decisions reached and their rationale, to the memory slice (nothing downstream enforces against it), or inline when the user wants no artifact. NEVER create or edit a PLAN.md Brief for a general decision: the `## Brief`/`## Plan` structure is the engineering shape. In `me` mode, the continuation discipline below still applies, with the summary standing in for the Brief.

**Engineering sessions** write the Brief section into `<memory_dir>/<topic-slug>/PLAN.md` (default `.work/`) as it locks, **except `scope` action**, which never writes `PLAN.md` (see below). The rest of this step, everything below, is the Brief machinery and is engineering-only.

**`scope` action (ad hoc, no Brief).** When the action is `scope`, do **not** create or edit
`PLAN.md` in the memory slice. After the Step 3 register gate passes, emit a **`Scope decisions:`**
section in chat (one `- <question>: <answer>` line per resolved row) and keep the open-question
ledger in the memory slice as the durable record. With no Brief to hold them, every `deferred` and
`blocked` row is returned in the same section as a `Deferred: Q<N> <question> (arbiter: <tag>)` or
`Blocked: Q<N> <question> (arbiter: <tag>)` line, each leading with its `Q<N>` id and carrying its
arbiter (`/planning:plan` by default, `USER-RESERVED` under the rule in
[`context/loop.md`](context/loop.md) "Brief template (the literal shape)"), so a choice never
silently disappears. A `Blocked:` line, and a `Deferred:` line tagged `USER-RESERVED`, tells the
caller to stop and ask the user that question before going on. The caller owns where these lines
land (for example a repo-sweep step commit). Skip the Step 4 `--brief` cross-check and skip
`/planning:plan` handoff.

**`me` mode persists incrementally, not just at the end.** Lock each answer into the decision-tree ledger (`interview-checklist.md`) + the relevant PLAN.md Brief section the moment it resolves, except in **`scope` action**, which never writes PLAN.md sections. So a crash, context clear, or overflow never loses resolved branches, and the session can continue elsewhere at any round boundary with nothing left to flush. When the user or the harness signals it, or when branches keep opening faster than they close (Step 5), recommend routing the next step with `/session-flow:workflow` (if enabled); otherwise Step 5's fallback. Never on your own estimate of remaining context. Target the light V1-spec Brief shape (scope / schema / code-surface bullets). Keep it terse.

**When the Brief is persisted.** This is the one home for when the Brief is written. In `me` mode each answer is written as it locks (above); in `auto` and `lock` the Brief is held as a draft and written in this step. Nothing downstream acts on the Brief, and nothing hands off, before the confirmation gate (Step 3) passes. A Brief that `round.sh export-brief` writes before then carries its `Restatement: UNCONFIRMED` stamp, so the cross-check below fails with `brief=unconfirmed` until the user confirms; a Brief written by hand carries no stamp, and the confirmation gate alone holds it.

PLAN.md holds `## Brief` + `## Plan` sections. `/planning:interview` writes only the Brief section; the Plan section stays empty until `/planning:plan` fills it.

**Cross-check the Brief once it exists.** Immediately after writing it, re-run the register gate with `--procedure --brief <memory_dir>/<topic-slug>/PLAN.md`, plus any flag the resolved lane's spoke adds to it, which may check the Brief against that lane's own export. This run proves every `deferred` and `blocked` row actually reached `### Deferred questions`, and that the Brief carries all nine template headings (TLDR, Problem, Goal, Work size, Constraints, Acceptance criteria, Captured assumptions, Out-of-scope, Deferred questions); the Step 3 run could not check either because the file was not written yet. It matches on the `Q<N>` id, so each deferred entry must lead with one. A non-zero exit means the Brief is missing a question the ledger retired or a template heading: fix the Brief, do not retire the row. Exit 1 with `brief=unconfirmed` means the Brief is stamped `Restatement: UNCONFIRMED`: the user confirms the latest `restate`, then the Brief is exported again. The gate reads only the stamp and cannot see a Brief edited after a Confirm; after such an edit, post a new `restate`, get a fresh Confirm and export again. A general session writes no Brief and skips this. An unattended run that exits without the lock, as [`context/loop.md`](context/loop.md) "Unattended path" says, skips this cross-check too.

If a PLAN.md Brief exists and user chose **revise**, edit the Brief in-place. If **start fresh**, append a dated scope-change note to the top of the Brief capturing why before rewriting. Never silently overwrite: that note is the Brief's only history (Step 1).

Section schema: write the literal `## Brief` template (TLDR / Problem / Goal / Work size / Constraints / Acceptance criteria / Captured assumptions / Out-of-scope / Deferred questions) per [`context/loop.md`](context/loop.md) "Brief template (the literal shape)"; Problem and Work size follow [`../../context/problem-framing.md`](../../context/problem-framing.md). `### Acceptance criteria` stays plain bullets in both formats, tagged or not, per [`context/ears.md`](context/ears.md); it is never converted to checkboxes. Each **Deferred question** leads with its **`Q<N>` id**, the tie back to its register row and what the Step 4 gate greps this section for, and carries an **arbiter tag** (`/planning:plan` default, or `USER-RESERVED` when its resolution could change acceptance criteria / out-of-scope / constraints). Both are required; loop.md covers when to use which.

## Clashing terms, prototypes and fact lookups

- **A term that clashes with an existing concept.** When a term the interview asks about clashes with a concept the code or the glossary already names, the recommendation is a qualified name the interview proposes itself, so the user never has to add the qualifier; once agreed, it is written through the inline vocabulary update ("Domain-aware behaviors"), under `domain_docs`. Read [`context/term-clash.md`](context/term-clash.md) when a clash is found.
- **An outcome that feeds a prototype.** Ask what the prototype must prove, and split it into one small piece per question that can be built at once in separate worktrees. Read [`context/prototype-questions.md`](context/prototype-questions.md) once the quality bar is a throwaway prototype or the next step builds one.
- **A question that turns on a fact.** Look it up yourself; never send the user to find it. When a quick lookup does not settle it, run `/discovery:explore` (if enabled) (what the code does) or `/discovery:research` (if enabled) (an external fact) as a lookup ([`context/lookups.md`](context/lookups.md)); otherwise the same work inline; read what a live system holds now (a database, a tracker, a service) directly through its CLI or MCP tool; this dispatch is how the exploration recommendation in "What this skill does NOT do" is carried out, never a request that the user run it. Do not stall the round proving the fact beyond what the recommendation needs: in an engineering session, the Brief's `### Captured assumptions` lists each fact from such a lookup that a recommendation rests on, with its source and the tag `verify during build`. A fact only the user's environment or an unconnected system holds still takes the self-answer step's offer, and a decision is still the user's.
- **A structural question that would settle faster drawn together.** For a structural question ("Visual-first for structural questions"), end its Context with one line offering `/visualization:visualize` (if enabled) in collaborative canvas mode. Offer it on no other question. The ledger's recorded answer stays the record; the canvas is not saved.

## What this skill does NOT do

- **Does not deep-dive the codebase**. Step 1 is a fast survey; the codebase gate in Step 2 is a lightweight per-question check (Grep/Read/Glob). Neither is exploration-depth work. If a fact needs more than a quick lookup, dispatch the exploration capability for it as a lookup ([`context/lookups.md`](context/lookups.md)) rather than doing that depth of work in the round itself
- **Does not plan implementation**. The Brief says *what* and *what we are assuming*; `/planning:plan` says *how*. Resist drafting an approach mid-interview
- **Does not write code or run tests**, beyond the read-only run "Run it to settle it" allows. Discovery skill. In an engineering session it DOES write domain docs outside the topic's slices when the project keeps them: domain-vocabulary updates (inline, between questions) and ADRs (written through `/architecture:adr` (if enabled), else recorded as an ADR candidate in the register row) are first-class interview outputs alongside the Brief (a general session writes none)
- **Does not adversarially attack the user's idea**, except in the `product` action, where the user asked for the idea to be tested ([`context/product.md`](context/product.md)). That is `/planning:devils-advocate`. Domain scenario exploration (probing concept boundaries through invented edge cases) discovers domain semantics. It is not plan-attacking. If you find yourself wanting to push back on the goal itself, surface once, capture response, continue
- **Does not gate a quick change**. A change whose diff is quick to review and cheap to retry skips `/planning:interview`: build it, review the diff, and align on it there (the quick-change on-ramp of `/session-flow:workflow` (if enabled)). Behavior change alone does not force the interview. Work that fails either test, or whose diff turns out not to be quick to review, is **interview-first**, and auto-detect keeps that cheap (synthesize-on-clear, relentless-Q&A-on-fuzzy)
- **Does not fudge gaps in `lock` mode**. If a true unknown surfaces during synthesis, STOP and surface it. Fall back to `auto` or `me` instead of guessing
- **Does not export Gherkin**. Named as a deferred extension point so its absence reads as a decision rather than an oversight: nothing here emits `.feature` files or `Given`/`When`/`Then` scenarios, and the EARS tags are a bracketed prefix vocabulary on a plain bullet, not a step grammar. A Gherkin export is a separate slice against a separate contract, and none of it is built here
