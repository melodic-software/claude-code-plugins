## Summary

An eval-held pull request that compare mode refuses now merges first. Each compare run records that it cannot start, and pr-merge's release step reads those records back and removes the do-not-merge label that held it for the eval, but only once every plugin whose skill, agent or context text the PR changes (or, when it changes none, every plugin it changes) has its own refused run: a refusal for one plugin never lifts a hold over another plugin's cut. After merge, the affected cases run on the default branch, and a FAIL reverts the PR, through the follow-up `docs/review/evals.md` already prescribes for PRs that merge before their run.

## Fix

- **The compare run records the refusal and its target.** `compare-arms.sh` writes `refused=true` and exits 3 only for a real refusal (a plugin path the arms do not carry, a `select-plugins.mjs` refusal, arms that do not differ); bad input or a wrong target still exits 1. In `pr-run-plugin-evals.yml`, `Build the arm patches` records `cannot-start=compare-refused` only on exit 3 with that marker (a bare exit 3 fails the step), `compare-before` and `compare-after` do not run on it, and a `Compare Cannot Start: compare-refused` job succeeds. The compare run name is now `eval-compare pr=<n> head=<sha> target=plugins/<name>`, so a run reads back with the plugin it compared. `Compare Prepare` stays behind `CLAUDE_EVALS_DISABLED`, unchanged from main.
- **`release-eval-hold.mjs` reads the records back per plugin.** For a held PR with no record at its head, the compare runs naming that PR and head created since the hold was set are listed, paging back to the hold's start (at most 10 pages; a list cut short counts nothing). The PR's files are read (`evalPlugins`: each plugin with a changed path under `skills/`, `agents/` or `context/`, both sides of a rename). For every such plugin, the newest run at the head naming that plugin as its target decides: it must pass `runVouches`, sit on the default-branch tip, and show exactly one successful `Compare Cannot Start: compare-refused` job and no successful `Compare Record`; a record comment vouching for it hands the decision to the record path. An older run for that plugin (or one whose name carries no target) at that head since the hold that is still going, was re-run, or failed with `Compare Verdict` not succeeding (a LOSS or VOID) keeps the hold. A file list that does not read in full, a PR with no such plugin, a plugin with no refused run of its own, a missing record alone, other hold reasons, a body hold and a member veto all keep it, and a VALID record still wins.
- **The release comment carries the obligation.** It starts with `<!-- eval-hold-released head=<sha> cannot-start=compare-refused run=<run ids> -->`, links each plugin's run, and states that the PR merges first, its affected cases run on the default branch after, and a FAIL reverts it.
- **Docs.** `docs/review/evals.md` and the loop-lane contract's Cross-lane PR hold describe the release; the loop-lane CHANGELOG has an entry.
